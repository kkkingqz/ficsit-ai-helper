# @ficsitai/screen-chat

Экран «Чат с ИИ» (**V-6**, [#23](https://github.com/kkkingqz/ficsit-ai-helper/issues/23)): строки, типы свойств представления, контроллер и точка входа. Представление — у Gs2 в `web/ui-kit/screens/chat.js`, данные — из фасада `@ficsitai/screens-api`.

Зоны разведены по [ADR-032](../../../docs/ARCHITECTURE.md) и ответу [Gs2-25](../../../docs/team/questions/Gs2.md): представление `mountChat` — у Gs2 в `web/ui-kit/screens/chat.js`, экран — здесь.

## Что отдаётся представлению

```ts
import { DEFAULT_CHAT_STRINGS, type ChatViewModel, type MountChat } from "@ficsitai/screen-chat";

const view = mountChat(root, {
  presenter,                      // форматтер D-2, его даёт хост
  copy: DEFAULT_CHAT_STRINGS.view, // ChatViewCopy — замороженный набор ключей
  actions,                         // ChatActions — обработчики, события к экрану
});

view.update(model); // ChatViewModel
```

Правило разделения простое: представление — чистая функция от свойств. Оно не ходит в фасад, не хранит состояние между вызовами `update` и не придумывает слов. Любой его обработчик — событие к экрану, любое изменение на экране — новый `update`.

## Две группы строк

| Группа | Куда идёт | Зачем |
| --- | --- | --- |
| `ChatViewCopy` (`DEFAULT_CHAT_STRINGS.view`) | в `mountChat` как `copy` | всё, что представление показывает само: заголовки, подсказки, состояния истории, шаблоны, метки панелей |
| `ChatHostStrings` (`DEFAULT_CHAT_STRINGS.host`) | остаётся у экрана | то, чем экран заполняет поля модели: `messages[].time`, `messages[].status`, `error.text`, `rateLimit` |

Деление не формальность: `error.text` и пометки сообщений приходят в представление уже локализованными, поэтому слова для них должны жить там, где они создаются, — на экране. Набор ключей `ChatViewCopy` заморожен, недостающий ключ ловится сборкой, а не прочерком на экране. Нужен новый — скажите, добавлю: придумывать строки в представлении не надо.

Подмена — `createChatStrings({ view, host })`. Вложенные объекты заменяются целиком, чтобы половина подменённого `historyStates` не оставила экран с чужой половиной.

## Семантика, которая влияет на кнопки

- **Stop — это «перестать показывать», а не «остановить ход».** Foreman дочитывает ход, и ответ окажется в истории при следующем чтении. Полученный фрагмент остаётся на экране с пометкой `messageStatus.stopped`.
- **Повтора в API нет.** `actions.retry()` — это новый `chat.send` с тем же текстом и новым `turnId`; прежний ход остаётся в истории. Повтор доступен только при связи с сайдкаром.
- **`sending` против двойной отправки.** Экран ставит флаг в обработчике `send` и снимает при идентификаторе хода или ошибке, поэтому повторный Enter до появления хода ничего не отправляет.
- **Пустая история и недоступная — разные состояния.** `empty` значит «разговора ещё не было», `unavailable` — «прежние сообщения не загрузились»; путать их нельзя.

## Демонстрационные данные

`chatDemoModel(state)` даёт детерминированную модель для каждого из состояний `ready`, `empty`, `loading`, `streaming`, `sending`, `error`, `offline`. Это данные для вёрстки и дымовых проверок, не телеметрия: в экране их нет, он строит модель из фасада.

## Контроллер

```ts
import { createChatController } from "@ficsitai/screen-chat";

const controller = createChatController({ api, mountView: mountChat, root, presenter });
// controller.actions — то, что представление зовёт в ответ на игрока
// controller.getModel() — то, что ушло в представление последним update
// controller.destroy() — снять подписки и представление
```

Что он делает сам, и почему именно так:

- **Ход.** `send` ставит `sending` **до первого ожидания** — мод вправе держать отправку до 30 с, и без замка два Enter подряд уходили двумя ходами. Затем в ленту кладутся вопрос и пустой ответ ассистента с `id = turnId`. Текст дописывается событиями `chat.text`, `chat.tool` показывается пометкой сообщения (аргументов в событии нет), `chat.done` снимает поток.
- **События раньше номера хода.** Ответ на `chatSend` и поток событий идут разными соединениями, и на HTTP первый кусок обгоняет ответ на отправку. Такие события складываются и применяются сразу после присвоения `turnId`, в порядке прихода; события с чужим `turnId` отбрасываются. Отбросить ранние значило бы показать пустое сообщение и остаться «в потоке» навсегда.
- **Отмена.** `stop` зовёт `chatCancel`, а по `chat.cancelled` помечает ответ как остановленный и **помечает историю устаревшей**: Foreman дочитывает ход, и полный ответ ляжет в историю.
- **Живой ход и снимок истории не смешиваются.** Это главное правило здесь, и оно стоило трёх кругов ревью. Пока ход идёт, его показывают **только события**: снимок истории в ленту не вмешивается. Снимок становится лентой **после конца хода** (`chat.done`), и только когда ждёт дочитанный ответ отменённого — ради него перечитывание и нужно (Co-133). В этот момент живого хода уже нет, смешивать нечего, и ни вопрос, ни ответ не могут удвоиться.

  Почему не раньше: чтение **до** отправки возвращало обрубок (Foreman ещё дописывал отменённый ход), а чтение **на рубеже принятия** приносило снимок, который мог содержать уже весь новый ход — и дальше, как ни раскладывай, либо удваивался вопрос, либо ответ, либо терялся полученный текст. Все три варианта нашёл Gs, и причина у них одна: события несут номер хода, а записи истории — нет (Co-133: заполнить `turnId` нечем), поэтому соединять два источника приходилось по тексту.

  Если перечитывание не удалось или вернуло пустой снимок при непустой ленте — лента остаётся как есть, а пометка «перечитать» не снимается. Пустой ответ при живом разговоре — признак сбоя на той стороне, а не пустой истории.

- **Повтор.** Текст запоминается **до** ответа мода: повторяют обычно тот ход, который не состоялся. `retry` — это новый `chat.send` с тем же текстом и новым `turnId`.
- **Разрыв связи.** По `api.status` с `sidecarConnected: false` поток снимается, показанные сообщения остаются — исчезнувшая лента выглядела бы как потерянный разговор, хотя он цел.
- **Коды в слова.** `SIDECAR_UNAVAILABLE`, `MOD_INERT`, `API_VERSION_MISMATCH`, `RATE_LIMITED` и прочее превращаются в текст из `ChatHostStrings`; повтор предлагается только там, где он может помочь.

## Точка входа

`index.html` с корнем `<div id="ficsitai-chat">` и **одним внешним модулем** `dist/boot.js`. Страница одна и та же в игре и в браузере: транспорт выбирает фасад. Представление и форматтер грузятся по адресу (`/ui-kit/screens/chat.js`, `/ui-kit/components.js`), а не импортом пакета, — витрина и экран собираются порознь.

**Ни одного встроенного скрипта**, и это не стиль, а требование изоляции: страницы в игре отдаются с `script-src 'self'` (ARCHITECTURE §6.3.1, §12 п. 11), под неё не проходят ни встроенный модуль, ни карта импорта, и прежняя страница в игре не запускалась вовсе (решение Co-128). Отсюда три следствия:

- `autoMount()` зовёт `src/boot.ts`, а не разметка;
- имя пакета фасада развязывает шаг сборки `scripts/relink.mjs` после `tsc`: `@ficsitai/screens-api` → `../../api/dist/index.js`. Карта импорта не нужна, а путь верен и в браузере, и в игре — корень страниц в игре это содержимое `web/`;
- горячую перезагрузку `boot.ts` подключает динамическим импортом только вне игры (`blu_event` на странице ставит мод): в игре файла нет, и запрос давал бы 404.

Проверять это нужно под настоящей политикой: страница, отданная без CSP, ничего не доказывает. Я проверял прокси, который добавляет `script-src 'self'; style-src 'self'` перед dev-сервером.

```bash
# из web/screens/api
node dist/dev/cli.js --root web --port 5173
# http://127.0.0.1:5173/screens/chat/index.html
```

Корень — `web`, а не `web/screens`: странице нужны и `/ui-kit/`, и `/screens/api/dist/`.

## Сборка и проверки

```bash
npm install
npm run typecheck
npm test
npm run build
```

`test/controller.test.ts` держит поведение хода против поддельного фасада: формы и коды там настоящие, из контракта. Отдельный блок — замечания ревью Gs на [#62](https://github.com/kkkingqz/ficsit-ai-helper/pull/62): дочитанный ответ приходит перечитыванием после конца хода; история, опередившая события, ответ не удваивает; раннее терминальное событие не скрывает полученный текст; отказ истории не стирает показанное; повтор того же вопроса после Stop не теряет новый ответ; замок до первого ожидания; сохранность номера отменённого хода при отказе отправки; события, обогнавшие ответ на отправку. Каждая из этих проверок падает на версии до правки — иначе они не проверяли бы ничего.
