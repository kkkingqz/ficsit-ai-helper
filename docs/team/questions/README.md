# Зачем так

Нужно место, где участники спрашивают друг друга, и при этом **никто не правит чужие файлы** ([OWNERSHIP.md](../OWNERSHIP.md)). Поэтому не один общий файл на всех — он бы конфликтовал при каждой одновременной правке, — а **файл на человека, и писать в него может только его владелец**.

Вопрос живёт в файле того, кто спрашивает. Ответ — в файле того, кто отвечает. Никто никогда не пишет в чужой файл, и слияния конфликтовать не могут в принципе.

| Файл | Владелец |
|---|---|
| [King.md](King.md) | King |
| [Co.md](Co.md) | Co |
| [Gs.md](Gs.md) | Gs |
| [Gf.md](Gf.md) | Gf |
| [Co2.md](Co2.md) | Co2 |
| [Cf3.md](Cf3.md) | Cf3 |
| [Gs2.md](Gs2.md) | Gs2 |
| [Co3.md](Co3.md) | Co3 |
| [Gf2.md](Gf2.md) | Gf2 |

**В начале каждого хода, до работы по задаче:**

1. `/usr/bin/git fetch origin` и `rebase` в своей копии — иначе вопросы к тебе просто не видны.
2. **Вопросы к тебе без ответа — ответить.** Не можешь сейчас — одной строкой в своём файле назови срок. Молчание не нейтрально: у каждого вопроса написано, что автор сделает без ответа, и это становится решением за тебя.
3. **Свои вопросы, на которые ответ уже есть, — прочитать и перевести в `закрыт`.** Статус меняет только автор, поэтому отвеченный вопрос висит в чужом `grep` как нетронутый, пока ты его не закроешь.
4. **Прочитать уведомления в своей очереди и подтвердить ознакомление.**
5. Только потом — своя задача.

# Как спросить

Добавь в **свой** файл блок:

```markdown
## <Роль>-7 → <Кому> · <дата> · открыт

Текст вопроса: что именно непонятно и что ты собираешься сделать, если ответа не будет.
```

- **Номер** — твой префикс и счётчик: `Co-7`, `Gf-3`. Счётчик свой, поэтому номера не могут совпасть у двух людей.
- **Адресат** — после `→`. Можно нескольких: `→ Gf, Gf2`. Для всех — `→ все`.
- **Состояние** — `открыт`, `отвечен`, `закрыт`. Меняет его **только автор вопроса**: ответ получил, устроил — закрыл.
- Пиши, что сделаешь без ответа. Тогда отсутствие ответа тоже решение, а не тупик.

# Как найти вопросы к себе

Из корня рабочей копии запусти команду со своей ролью. Пример для Gs.

```bash
python3 tools/questions.py Gs --answered
```

Вывод показывает вопросы к роли, непрочитанные уведомления и ответы на свои вопросы, которые ещё нужно закрыть. Для истории добавь `--all`. Сводку по ролям даёт `python3 tools/questions.py --stats`.

# Как подтвердить ознакомление

Прочитай весь блок уведомления в файле автора. Подтверди каждое прочитанное уведомление, которое скрипт показывает в твоей очереди. Команда принимает один или несколько ID.

```bash
python3 tools/questions.py Gs ack Co-40 Co-42
```

Скрипт добавит отметку в собственный файл роли. На ветке `work/<роль>` можно запустить `python3 tools/questions.py ack Co-40` без указания роли. На задачной ветке укажи её явно.

Отметку также можно записать вручную в своём файле вопросов.

```markdown
## <Роль>-N → <Автор> · ознакомлен с <ID> · <дата>

Ознакомлен с уведомлением <ID>.
```

После отметки уведомление исчезает из обычного вывода. Отметку закоммить вместе с остальными изменениями своего файла вопросов и отправь в `main`. Отметка означает, что уведомление прочитано. Поручения из него остаются открытыми до выполнения.

# Как ответить

Добавь в **свой** файл блок со ссылкой на номер вопроса:

```markdown
## <Роль>-4 → <Кому> · ответ на <номер> · <дата>

Ответ.
```

Автор вопроса после этого ставит у себя `закрыт`. Если ответ не устроил — не спорь в двух файлах, задай следующий вопрос со ссылкой на ответ.

# Чего здесь не делать

- **Срочное — не сюда.** Файлы читают раз в день. Блокирующее идёт в задачу milestone, а если встал критический путь — сразу Co и King (правило 3 [KICKOFF](../KICKOFF.md)).
- **Решения — не сюда.** Архитектурное решение записывается в `ARCHITECTURE.md` на воротах: пишет Co, утверждает King. Вопрос может привести к решению, но сам решением не становится.
- **Обсуждение задачи — в задаче.** Если вопрос про конкретный пункт чек-листа, его место в комментарии к задаче milestone, где его увидят все исполнители.
- Не редактируй чужие блоки, даже чтобы поправить состояние или опечатку.
