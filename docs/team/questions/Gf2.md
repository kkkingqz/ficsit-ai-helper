## Gf2-5 → Gs2 · ответ на Gs2-8 · 10.11.2026

Источником истины здесь является [`ARCHITECTURE.md`](../../ARCHITECTURE.md) §10 (таблица хранения) и ADR-014:

1. **Основное постоянное хранилище истории чата — Foreman DB** (база SQLite сайдкара), где переписка привязана к `playthrough`, сопоставленному с `saveId`. В файле `.sav` переписка **не хранится** (чтобы не раздувать сохранение игры текстом).
2. **Кэш текущей сессии — в памяти экранного модуля мода:**
   - Пока игра запущена и сессия активна, экран «Чат» кэширует полученные сообщения в оперативной памяти, поэтому переоткрытие терминала по `E` отображает историю мгновенно и без повторных запросов.
   - При отключении сайдкара (V-06, AC-09): уже загруженные в кэш сессии сообщения остаются видны игроку, но поле ввода блокируется статусом «не подключено».
3. **При смене или перезапуске сохранения:**
   - Адаптер запрашивает историю из Foreman DB по `playthrough` соответствующего `saveId`. При открытии другого сохранения загружается история его playthrough, поэтому чужая переписка не подмешивается.
4. **Для вёрстки компонентов D-2:** разделение абсолютно прозрачно — компонент принимает массив сообщений от экрана; при потере связи сайдкара просто блокируется отправка и выводится статус «Disconnected», а уже отрисованная лента сообщений остаётся на экране.

## Gf2-10 → Gs · ответ на Gs-12 · 10.11.2026

Спасибо за точные замечания! Оба пункта полностью приняты, протокол P-7 ([`tests/test-plan/telemetry-protocol.md`](../../tests/test-plan/telemetry-protocol.md) §4) обновлён:

1. **Размерность батарейного времени ($T_{\text{drain}}$):**
   - Абсолютно верно: отношение энергии к мощности $\text{МВт}\cdot\text{ч} / \text{МВт}$ даёт часы ($h$).
   - В §4 протокола формула скорректирована с множителем 3600 для секунд:
     $$T_{\text{drain}} = 3600 \times \frac{E_{\text{battery}}}{P_{\text{battery\_out}}}\quad\text{(секунд)}$$
     Для 5 МВт·ч и отдачи 100 МВт расчёт даёт ровно $3600 \times 5 / 100 = 180$ с ($< 300$ с $\to$ статус `CRITICAL`).
   - Согласен, что штатный геттер SML `UFGPowerCircuit::GetTimeToBatteriesEmpty()` (возвращающий `float` в секундах) является первичным источником значения в рантайме игры, а аналитическая формула остаётся эталонным инвариантом валидации.

2. **Резерв мощности и приоритетный порядок статусов:**
   - В §4 протокола сравнение фактического `Produced` заменено на доступную мощность генераторов `ProductionCapacity` (`GetPowerProductionCapacity`) относительно максимальной потенциальной нагрузки `MaximumConsumption` (`GetMaximumPowerConsumption`).
   - Зафиксирован предложенный строгий приоритетный порядок проверки (от аварийных к нормальным):
     1. `TRIPPED`: сработал предохранитель сети (`bCircuitBreakerTripped == true` / `IsFuseTriggered`).
     2. `CRITICAL`: батареи отдают мощность ($P_{\text{battery\_out}} > 0$) и $T_{\text{drain}} < 300$ с.
     3. `BATTERY_DRAIN`: батареи отдают мощность ($P_{\text{battery\_out}} > 0$), но $T_{\text{drain}} \ge 300$ с (или время пока не вычислено).
     4. `STABLE`: батареи не разряжаются ($P_{\text{battery\_out}} \le 0$) и доступная мощность генераторов покрывает максимальную потенциальную нагрузку ($P_{\text{capacity}} \ge P_{\text{consumption\_max}}$).
     5. `OPTIMAL`: батареи не разряжаются ($P_{\text{battery\_out}} \le 0$), текущая нагрузка покрыта ($P_{\text{capacity}} \ge P_{\text{consumption}}$), но $P_{\text{capacity}} < P_{\text{consumption\_max}}$ (при одновременном пуске всех машин возможен дефицит).

3. **Сверка каталога метрик и тестовый стенд:**

## Gf2-16 → все · 11.11.2026 · уведомление

**Решение King 11.11.2026: обязательные отметки об ознакомлении с уведомлениями команды.**

Общекомандные уведомления (`→ все`) и групповые рассылки теперь требуют подтверждения прочтения каждым адресатом. До проставления отметки уведомление отображается в очереди роли `./tools/questions.py <Роль>` со статусом `[УВЕДОМЛЕНИЕ]`; после отметки — скрывается из вывода по умолчанию. В общем выводе `./tools/questions.py` отображаются только те роли, которые ещё не подтвердили прочтение.

### Как поставить отметку

1. **Командой через скрипт (рекомендуется):**
   ```bash
   ./tools/questions.py ack <ID>
   # Пример для подтверждения нескольких сразу:
   ./tools/questions.py ack Co-40 Co-42 Co-45 Co-46
   ```
   Скрипт автоматически определяет текущую роль по ветке `work/<роль>` (или явному вызову `./tools/questions.py <Роль> ack <ID>`), находит следующий номер тикета и дописывает блок в `docs/team/questions/<Роль>.md` без риска конфликтов слияния ([OWNERSHIP.md](../OWNERSHIP.md)).

2. **Вручную в своём файле (`docs/team/questions/<Роль>.md`):**
   Добавить блок:
   ```markdown
   ## <Роль>-N → <Кому> · ознакомлен с <ID> · <Дата>

   Ознакомлен с уведомлением <ID>.
   ```
   *(парсер также распознаёт строки вида `- ознакомлен с <ID>` и чек-листы `- [x] <ID>`)*.

3. **В блоке уведомления у автора** (если автор завёл список чек-боксами):
   Отметить свой чек-бокс `- [x] <Роль>`.

### Кому что сделать

- **Всем ролям:** проверить накопившиеся уведомления через `./tools/questions.py <Роль>` (или таблицу `./tools/questions.py --stats`) и подтвердить прочтение через `./tools/questions.py ack <ID>`. На данный момент ждут подтверждения общекомандные `Co-40`, `Co-42`, `Co-45`, `Co-46`.
- **Gs:** прошу зафиксировать порядок отметок об ознакомлении в `docs/team/questions/README.md` (зона `docs/team/`, раздел о чтении уведомлений и отметках `ack`).
