# Статус и краткое резюме

| Поле | Значение |
|---|---|
| Документ | FICSIT AI — Release Architecture |
| Версия | 2.1-draft · 05.11.2026 (заменяет 2.0-draft от 04.11.2026) |
| Статус | Проект архитектуры на согласование; не описание уже реализованного продукта |
| Целевой стек | Satisfactory 1.2, SML 3.12, Windows game client |
| Топология | **Только одиночная игра.** Dedicated Server, listen server и мультиплеер вне v1.x |
| Главный приоритет | Переиспользование готовых решений там, где задача объективно сложна |

**Назначение.** FICSIT AI — мод к Satisfactory и локальный сервис-компаньон, превращающие FICSIT Foreman в доступного прямо в игре инженерного помощника. Игрок взаимодействует с ним текстом (позже голосом), через размещаемый терминал и экипируемое устройство. Помощник получает реальные игровые данные, планирует производство, показывает производственные графы, управляет декларативными экранами и формирует запросы на создание простых Blueprint.

**Ключевое изменение 2.0-draft.** Проект отказывается от поддержки мультиплеера и Dedicated Server в пределах v1.x. Это решение принято не для экономии, а чтобы убрать с критического пути интеграционные неизвестные, каждая из которых могла опрокинуть архитектуру: сетевой канал между внешним сервисом и игровым сервером, доставка Blueprint клиенту в отсутствие локального игрока, репликация экранов и ACL. Полный разбор последствий — в §17.2.

**Ключевые изменения 2.1-draft** (по результатам проверки исходников Foreman и поиска готовых планировщиков, §17.1):

- Между модом и Foreman появляется тонкий **адаптер сайдкара**. Для Foreman он единственный MCP-сервер, мод подключается к нему исходящим соединением. Входящего слушателя в игровом процессе нет, Foreman не патчится (ADR-012).
- **Планировщик производства — адаптированное ядро Satisfactory Build Calculator** (MIT, C++, SML 3.12), а не собственная разработка (ADR-013).
- **Подтверждений игрока нет.** Пишущие инструменты модели создают только объекты мода: заметки, экраны, чертежи в библиотеке. Ни один не изменяет мир, все применяются после валидации (ADR-009).
- Состояние мода хранится **в сохранении** с идентификатором `saveId`; снаружи — только телеметрия и кэш рендера (ADR-014).
- Мод определяет мультиплеер **в ходе сессии**, а не только при загрузке; контент регистрируется всегда, отключается поведение (ADR-016).
- Модель получает каталог через **поисковые инструменты**, а не одним ответом (ADR-017).
- **Паритет ручного и AI-пути:** каждое действие, доступное модели, игрок может выполнить вручную через UI без LLM. UI и модель вызывают одни и те же операции из общего реестра (§7.5, ADR-018).
- Первый результат работ — **вертикальный срез v0.1** (§13).

**Главное ограничение проекта.** Не разрабатывать собственные решения там, где готовый проект уже предоставляет функциональность или исходный код **и где задача объективно сложна**: сериализация Blueprint, маршрутизация лент и труб, LLM-оркестрация, STT/TTS. Обратное тоже верно и теперь записано явно: не встраивать чужой код там, где собственная реализация проще его извлечения (§2). Отсутствие у стороннего мода публичного API не является основанием объявлять его runtime-зависимостью: такой компонент заимствуется/адаптируется при соблюдении лицензии.

**Архитектурный принцип.** Один `ProductionPlan` описывает производство; один `ScreenDefinition` описывает его отображение; один `BlueprintRequest` используется и ручным редактором, и LLM. **Модель не может ничего, чего не может игрок вручную:** каждый её инструмент — это операция мода с ручной точкой входа в UI, работающая без LLM (ADR-018). AI вызывает закрытый набор таких операций, **authority-слой мода валидирует** каждый вызов по схеме и живому каталогу. Инструментов, изменяющих игровой мир, у модели нет. В одиночной игре этот слой перестаёт быть границей процессов, но остаётся обязательной границей кода — он изолирует LLM, а не других игроков (ADR-009).

# 1. Цели, границы и критерии успеха

**Нефункциональные цели.** Реагирующий на клавиши HUD, предсказуемая нагрузка на GameThread, сохранение экранов и планов между перезапусками, изоляция LLM от опасных игровых операций, отсутствие обязательных сторонних модов, установка без ручной настройки контейнеров.

## 1.2 Отложенные версии

Каждая версия ниже закрывает один риск и не блокирует предыдущую.

| Версия | Содержание | Главный риск версии |
|---|---|---|
| v1.1 | Blueprint Builder: ручная форма и общий валидатор | Поведение `FBuildPlanGenerator` под программным вводом |
| v1.2 | AI-компоновщик экранов: `create_screen`/`update_screen`/`assign_screen` | Качество вывода LLM в рамках белой схемы |
| v1.3 | Голосовой контур: PTT → STT → Foreman → TTS; локальный сайдкар | Аудио в UE/Proton (бывший R-07) |
| v1.4 | Интерактивный редактор графа (drag, пересчёт на холсте) | Наращивание интерактивности на виджет графа (§6.4, R-02) |
| v2.0 | Мультиплеер и Dedicated Server | Всё, что снято этим документом; потребует ADR-серии заново |

Механика `ScreenDefinition` и `BlueprintRequest` проектируется и фиксируется **в v1.0**, хотя AI-путь к ним появляется в v1.2 и v1.1 соответственно: контракт должен быть один с самого начала, иначе ручной и AI-путь разъедутся.

**Правило версий (ADR-018):** инструмент модели появляется не раньше своего ручного пути. Ручная форма Blueprint Builder и инструменты чертежей выходят вместе в v1.1, редактор экранов и экранные инструменты — вместе в v1.2.

## 1.3 Что не входит

Мультиплеер, Dedicated Server, listen server; автоматическое строительство фабрики в мире; CAD/оптимизатор произвольной 3D-геометрии; свободный исполняемый код/HTML от LLM; автономный NPC; управление транспортом или оборудованием без подтверждения; замена интерфейса всего Satisfactory; поддержка сторонних машин с нестандартной геометрией в генераторе чертежей. **Это не ограничивает получение рецептов модовых машин из игры:** данные присутствуют, даже если генератор чертежей не умеет их размещать.

# 2. Стратегия готовых компонентов

Под «зависимостью» понимается мод/сервис, который конечный пользователь должен установить. «Переиспользовать код» означает включить или адаптировать функциональность в наш мод с соблюдением лицензии и атрибуции. Эти подходы не смешивать.

**Уточнение принципа относительно 1.0-draft.** Переиспользование оправдано, когда стоимость извлечения ниже стоимости реализации. Для сериализатора Blueprint, контроллера лент/труб и планировщика производства это верно с большим запасом. Принцип «не писать заново» не должен превращаться в обязательство встраивать чужой код в простые места: решение принимается по каждому компоненту отдельно, после чтения его исходников.

| Компонент | Решение | Обоснование и статус |
|---|---|---|
| SML 3.12 | **Обязательная runtime-зависимость** | Регистрация машины/предмета, Widget Hooks, модовая упаковка; подтверждено документацией |
| FICSIT Foreman | **Внешний сервис, vanilla** | Chat REST/SSE, MCP-клиент, Work Orders, история. Не форкается и не патчится: подключается через адаптер сайдкара (§3.4, ADR-012). Apache-2.0 |
| Адаптер сайдкара | **Пишем сами**, Node/TS | Тонкий процесс без игрового состояния: MCP-сервер для Foreman, канал к моду, авторизация в Foreman (§3.3). Официальный TS SDK MCP |
| Satisfactory Build Calculator (SBC) | **Переиспользовать ядро планировщика**, v1.0 | `FSBCProductionData` + `FSBCProductionCalculator`: live-разблокировки, модовые рецепты, альтернативы, Power Shards, Somersloops, мощность. Ядро отделено от UI. MIT, SML 3.12 (§8.3, ADR-013) |
| Factory Spawner 2.3.0 | **Переиспользовать C++-ядро**, v1.1 | `FBuildPlanGenerator` формирует машины, конвейеры, трубы, питание и Blueprint; MIT; прямого кросс-модового API нет |
| Ficsit Remote Monitoring | **Референс кода телеметрии, не зависимость** | Знает, где в подсистемах лежат данные фабрики. Каталог теперь покрывает SBC, поэтому FRM нужен только для телеметрии. **Лицензия не подтверждена** — см. §2.2 |
| HiGHS | **Кандидат v1.x** | LP-решатель, MIT, C++. Нужен, когда понадобятся циклы рецептов, баланс побочных продуктов и оптимизация (§8.3) |
| Image Screens | **Референс, вероятно не нужен** | В одиночной игре экран в мире делается render target'ом в процессе (§6.6) |
| Remote Factory | **Референс UX, не зависимость** | Переносной интерфейс + размещаемый объект |
| Graphviz | **Опционально, v1.3+** | В v1.0 раскладка графа в процессе (§6.4) |
| STT / TTS | **Готовые inference-сервисы**, v1.3 | Аудиодвижок с нуля не писать |

**Текущая подтверждённость.** По состоянию на 04.11.2026 SMR подтверждает совместимость SML 3.12. Для Factory Spawner проверены C++-точки `Generate`, `SpawnPipeAndConnect` и `WriteBlueprintToArchive`; в одиночной игре `FirstPlayerController` — это и есть игрок, поэтому главное препятствие прежней редакции (R-01) снято. Для SBC 05.11.2026 проверено: ядро планировщика (около 590 строк) отделено от виджета, рецепты синхронизируются из `AFGRecipeManager::GetAllRecipes`, сборка под SML 3.12. Наличие собранного мода не подтверждает наличие доступного API для сторонних модов.

## 2.1 Решения «не писать заново» и «писать самим»

Не писать заново:

- Систему Work Orders, учётных записей, LLM tool calling и управление историей — всё остаётся в Foreman.
- **Планировщик производства** — адаптировать ядро SBC (§8.3, ADR-013).
- Контроллер конвейеров/труб и сериализатор Blueprint — адаптировать Factory Spawner (v1.1).
- Аудиодвижок, STT и TTS — готовые сервисы (v1.3).
- Рецептурную базу — читать из игры, не переносить вручную.

Писать самим:

- **Адаптер сайдкара** — связка мода с vanilla Foreman (§3.3, ADR-012).
- **Послойную раскладку и отрисовку графа** — своя, в UMG, если виджет SBC не окажется дешевле (§6.4, ADR-007).
- **Телеметрию** — напрямую из игровых подсистем, без промежуточного HTTP (§8.2, ADR-003).
- Контракты, валидатор, интеграцию и жизненный цикл состояния.

## 2.2 Открытые лицензионные вопросы

1. **Лицензия Ficsit Remote Monitoring не установлена.** Он рассматривается как источник кода телеметрии: если заимствование не разрешено, сбор телеметрии пишется с нуля и требует отдельной оценки. Каталог от этого вопроса больше не зависит (его покрывает SBC). **Проверить до начала работ по §8.2.**
2. **Собственная лицензия мода не названа.** Apache-2.0 у Foreman (внешний сервис, не линкуется) и MIT у SBC и Factory Spawner позволяют выпустить мод под MIT или Apache-2.0. Зафиксировать выбор в репозитории.
3. Заимствованный код (SBC, Factory Spawner) — в отдельном каталоге `third_party/` с `LICENSE`, `NOTICE` и перечнем внесённых патчей по файлам.

# 3. Логическая архитектура

![Компонентная схема FICSIT AI](assets/components.png){ width=6.0in }

Архитектура состоит из **двух рантаймов**: игровой процесс и локальный сайдкар (Foreman и адаптер, один установщик). В 1.0-draft их было пять (клиент, серверное расширение SML, Game Bridge, Foreman, FRM).

## 3.1 Игровой процесс: презентационный слой

`AI Terminal` (строительный объект), `AI Assistant` (экипируемый предмет), **единственный** `UI Controller`, виджеты UMG, представление производственного плана, HUD, отрисовка экрана в мире, локальные настройки клавиш. Терминал и предмет открывают один и тот же контроллер с разными layout-пресетами: у терминала полная сетка, у экипировки компактная раскладка (ADR-001, §6.2).

## 3.2 Игровой процесс: authority-слой

Единственный путь от любого внешнего вызова к изменению состояния мода. Содержит: `OperationRegistry`, `CatalogProvider` (на основе слоя данных SBC: `AFGRecipeManager` и зарегистрированные в SML классы), `TelemetrySampler`, `Planner` (адаптированное ядро SBC), `Validator` и — с v1.1 — адаптированное ядро Factory Spawner.

**`OperationRegistry`** — единый реестр операций мода (ADR-018). У каждой операции: идентификатор, JSON Schema аргументов и результата, обработчик и ручная точка входа в UI. Формы UI и инструменты модели вызывают одни и те же операции и проходят один и тот же `Validator`. Описания инструментов для адаптера генерируются из реестра; операция без ручной точки входа не может быть выставлена модели.

**Инвариант.** Набор инструментов модели закрыт и не содержит операций, изменяющих игровой мир: только чтение, расчёт, заметки, экраны (v1.2) и создание чертежа в библиотеке (v1.1). Каждый вызов проходит `Validator` (схема, лимиты, сверка с живым каталогом); подтверждений игрока нет (ADR-009). Ни один обработчик ответа сайдкара не вызывает мутирующее API мира; это проверяется ревью и тестом. Шов сохраняется ровно в таком виде, чтобы будущий мультиплеер стал портированием, а не переписыванием (ADR-011).

## 3.3 Адаптер сайдкара и канал к моду

Тонкий Node/TS-процесс в составе сайдкара, без игрового состояния (ADR-012). Обязанности:

1. **MCP-сервер для Foreman.** Адаптер — единственный `MCP_URL` Foreman. Он отдаёт модели инструменты мода (§7.1), сгенерированные из `OperationRegistry`, и может проксировать отдельные инструменты `sf-mcp`.
2. **Белый список.** Адаптер выставляет модели только инструменты из белого списка (ADR-018): операции мода и те инструменты `sf-mcp`, у которых есть ручной путь в игровом UI. Остальные инструменты `sf-mcp` (чтение загруженного `.sav`, планирование, справочные запросы по каталогу) скрыты: они дублируют live-операции мода, и модель получила бы два разных ответа на один вопрос. Встроенные инструменты Work Orders живут в самом `ff-server`, через MCP не проходят и адаптером не фильтруются — их ручной путь описан в §7.5.
3. **Чат.** Мод обращается к стабильному API адаптера, адаптер — к API Foreman. Изменения API Foreman гасятся в одном месте.
4. **Авторизация.** Адаптер сам регистрирует локальный аккаунт Foreman (email и пароль генерирует установщик) и держит сессию. Мод ничего не знает о логине.
5. **Сопоставление** `saveId` (§10) с playthrough Foreman: адаптер находит или создаёт playthrough для текущего сохранения.
6. **Согласование версий** с модом (`apiVersion`, §5.5).

**Канал мод ↔ адаптер.** Мод сам открывает исходящее соединение к адаптеру на `127.0.0.1` (WebSocket или HTTP long-poll — выбрать в Spike S2) с токеном из локального конфига. По этому каналу адаптер передаёт моду вызовы инструментов, а мод возвращает ответы и события. Входящего слушателя в игровом процессе нет. Требования к моду: сетевой код вне GameThread; любое обращение к игровому состоянию — через задание в GameThread и снапшот-ответ; переподключение без влияния на игру.

## 3.4 Foreman (локально)

Остаётся как есть: `ff-server`, `sf-mcp`, собственная БД (SQLite), chat-цикл, Work Orders, история. Не форкается и не патчится. Его планировщик и данные `sf-game-data-graph` **не используются для расчётов** — планирование выполняется в моде (§8.3); встроенные данные Foreman остаются для справочных ответов, когда игра не подключена.

**Проверено по исходникам Foreman (05.11.2026)** — эти факты и определили схему с адаптером:

- `ff-server` подключается к **одному** MCP-серверу (`MCP_URL`). Класс `McpAggregateGateway` для нескольких серверов в коде есть, но не подключён.
- MCP-клиент Foreman не отправляет заголовков; токен к адаптеру передаётся в query-строке `MCP_URL`.
- Клиент внедряет `savePath` текущего playthrough в аргументы вызовов; адаптер удаляет его из вызовов инструментов мода.
- Чат (`POST /api/playthroughs/:id/chat`, ответ потоком SSE) закрыт сессией Better Auth через cookie; аккаунты поддерживают MFA.
- Инструменты Foreman по сохранению читают загруженный `.sav`, а не живую игру.
- Инструменты Work Orders (`create_work_order`, `create_child_work_order`, `create_explore_order`) встроены в `ff-server` и добавляются к MCP-инструментам внутри него. У Work Orders есть REST: создание `POST /api/playthroughs/:id/work-orders`, правка плана, шагов и переходы статусов — это ручной путь без LLM.
- Поставка Foreman — три Docker-сервиса (`sf-mcp`, `ff-server`, `ff-client`); Prisma поддерживает SQLite.

Интерфейс: мод → адаптер → `POST /api/playthroughs/:id/chat` и поток SSE; Foreman → адаптер → мод для вызовов инструментов. Все соединения — loopback.

## 3.5 Чего в архитектуре больше нет

| Было в 1.0-draft | Почему убрано |
|---|---|
| Серверное расширение SML как отдельный деплой | В одиночной игре это тот же процесс; остаётся authority-слоем (§3.2) |
| Game Bridge | Его задачи распались: состояние → сохранение и локальные файлы мода, телеметрия → в процессе, изображения → render target. Остался только тонкий адаптер без игрового состояния для связи с Foreman (§3.3) |
| FRM как обязательный мод | Потребитель данных теперь в том же процессе; HTTP-сервер посередине не нужен (§8.1) |
| Канал Bridge → SML server extension | Самая несспроектированная часть прежней редакции; исчезла вместе с сетевой границей |
| TLS, публикация портов, pairing-токены с `worldId`/`playerId` | Всё на loopback, один локальный пользователь (§12) |
| Входящий MCP-слушатель в игре (2.0-draft) | Заменён исходящим каналом мода к адаптеру; закрыт R-13 (§3.3) |
| Очередь подтверждений (2.0-draft) | У модели нет инструментов, изменяющих мир (§7) |
| Собственный планировщик (2.0-draft) | Заменён ядром SBC (§8.3) |

# 4. Развёртывание

| Что | Где | Обязательность |
|---|---|---|
| Satisfactory 1.2 + SML 3.12 + `FicsitAI` | Машина игрока | Обязательно |
| Сайдкар: адаптер + Foreman (`ff-server`, `sf-mcp`) + SQLite | Та же машина, один установщик | Обязательно для AI-функций; ручные функции, включая планировщик, работают без него |
| STT/TTS | Та же машина или внешний провайдер | v1.3 |

Веб-интерфейс Foreman (`ff-client`) в пакет не входит. Сетевых границ нет: весь обмен идёт по loopback. Порты наружу не публикуются, сертификаты не нужны.

## 4.1 Упаковка и установка

**Это главный UX-риск проекта.** В одиночной игре игрок сам себе администратор. Требование «установите Docker и поднимите несколько контейнеров» ограничивает аудиторию мода сотнями человек вместо десятков тысяч.

Решение для v1.0 (ADR-015):

- **Один установщик сайдкара:** портативный Node, бандлы `ff-server`, `sf-mcp` и адаптера, база SQLite и маленький launcher. Объём порядка 50–80 МБ. Поставка нативного движка Prisma проверяется в Spike S5. Мод ставится обычным образом через SMM.
- **Установщик генерирует** токен канала мод ↔ адаптер и учётные данные локального аккаунта Foreman, записывает их в конфиги мода и сайдкара. Ключ LLM-провайдера игрок вводит один раз; он хранится у сайдкара.
- **Мод запускает сайдкар** при старте игры: если сайдкар уже работает, мод подключается к нему, иначе стартует процесс. При выходе из игры мод останавливает сайдкар, если сам его запускал.
- **Docker-compose** допустим как альтернативный путь для тех, кто его предпочитает, но не как основной.
- Мод сам обнаруживает неподнятый сайдкар и показывает внятное состояние, а не ошибку соединения.

Критерий приёмки упаковки: от скачивания до первого ответа помощника — без ручного редактирования конфигов, кроме ввода ключа LLM-провайдера.

## 4.2 Поведение в мультиплеерной сессии

Мод регистрирует новые классы акторов (терминал, предмет), поэтому в мультиплеере он принципиально требует установки у всех участников — «client-only мод с размещаемым объектом» в MP невозможен. Промежуточного варианта нет, и это подтверждает решение §1.1.

Важно, что «одиночность» — не постоянное свойство сессии: в Satisfactory к уже идущей игре могут подключиться другие игроки, если это разрешают настройки приватности. Поэтому проверка только при загрузке недостаточна (ADR-016):

1. **Контент регистрируется всегда:** рецепты, схемы, классы терминала и предмета. Снятие регистрации опаснее для сохранений и разблокировок, чем отключение поведения.
2. **Поведение отключается в рантайме.** При входе первого удалённого игрока мод становится инертным: закрывает UI, прячет HUD, отключается от адаптера, терминал показывает «недоступно в мультиплеере» с указанием причины. Когда удалённые игроки уходят, мод возобновляет работу. Тот же режим включается сразу, если сессия загружена как мультиплеерная.
3. **Мод помечается в SML как обязательный на удалённой стороне** (`RequiredOnRemote` в `.uplugin`; проверить в Spike S1), чтобы игрок без мода не мог подключиться и вызвать десинк.
4. Уже размещённые терминалы не ломают загрузку сохранения в любой сессии.

Это задача v1.0 и отдельный критерий приёмки (AC-10), а не «потом».

# 5. Модель данных: четыре базовых контракта

## 5.1 `GameCatalog` (read-only)

Нормализованные сущности `Item`, `Recipe`, `Machine`, `Schematic`, `UnlockState`. Ключ — устойчивое игровое `className`; отображаемое имя и локализованная подпись хранятся отдельно. У рецепта: список ингредиентов/продуктов, длительность, производство в минуту, `producedIn`, `isAlternate`, `unlocked`. У машины: класс, семейство, энергопотребление, доступность для строительства, порты.

Источник истинности — **только игровые подсистемы текущего процесса**. Прежнее разделение «FRM даёт перечень, SML даёт статус разблокировки» устранено: оба берутся из одного места, поэтому инвариант «известный рецепт ≠ разблокированный в этом сохранении» теперь поддерживается одним кодом, а не сверкой двух источников.

**Обновление:** полная сборка при загрузке сохранения и после изменения состава модов; инкрементальное обновление разблокировок по игровым событиям; версия каталога (`catalogRevision`) для инвалидации кэшей UI.

`GameCatalog` — внутренняя модель мода; наружу (модели) он отдаётся только частями, через поисковые инструменты (§7.1).

## 5.2 `ProductionPlan`

Идентификатор, `saveId` сохранения-владельца (§10), версия, `catalogRevision`, целевой ресурс и расход/мин; список производственных групп (машина, рецепт, количество, такт, плановая скорость), соединений (item, source group, target group, quantity/min, единицы), выбранных альтернативных рецептов, источников сырья, сводные показатели энергии и машин, перечень предупреждений планировщика.

План — **вычисляемая модель**, а не рисунок. Таблица, граф и Foreman работают с одним объектом; отрисовка — только представление. План хранит `catalogRevision`, при котором был посчитан: при расхождении с текущим UI помечает план как требующий пересчёта, а не молча показывает устаревшие числа.

Коды предупреждений v1.0: `BYPRODUCT_NOT_BALANCED` (побочный продукт посчитан, но не сведён в баланс), `RECIPE_LOCKED` (рецепт не разблокирован в этом сохранении), `CATALOG_STALE` (каталог изменился после расчёта). Цикл рецептов — не предупреждение, а ошибка расчёта `RECIPE_CYCLE_UNSUPPORTED`: план не строится (§8.3).

## 5.3 `ScreenDefinition`

Исправления относительно 1.0-draft: `layout` и `area` были несовместимы (`grid` с именованными значениями `left`/`right`/`bottom`), поля темы и прав присутствовали в тексте и отсутствовали в примере, `source` был неструктурированной строкой.

Поля: `schemaVersion`, `id`, `scope`, `title`, `layout`, `theme`, `widgets[]`. Каждый виджет: `id`, `type`, `slot`, `source`, необязательные `options` и `refreshSec`.

- `scope` — `personal` | `terminal`. Значение `shared` удалено вместе с мультиплеером.
- `layout` — **перечисление пресетов** (`slots-1`, `slots-2`, `slots-3`, `hud-compact`), а не свободная сетка. Слоты именованные: `main`, `side`, `foot`. Перечисление вместо произвольной геометрии резко сокращает число невалидных состояний, которые может породить LLM. Свободная сетка — кандидат на v1.2 после накопления реальных экранов.
- `source` — структурированный объект `{"kind": "...", "id": "..."}`, где `kind` — перечисление (`plan`, `metric`, `work_orders`, `notes`, `static`). Валидируется не только синтаксически: `id` сверяется с живым каталогом метрик и существующими планами, иначе виджет отклоняется с указанием причины.
- `refreshSec` — необязательное; клиент **зажимает** значение в допустимый диапазон, а не отклоняет определение, и у тяжёлых источников есть нижний порог (§8.2).

Типы виджетов v1.0: `text`, `metric`, `table`, `timeseries`, `production_graph`, `notes`, `work_orders`. Тип `image` удалён — пайплайна изображений в v1.0 нет; вернётся вместе с сайдкаром.

Клиент создаёт виджеты только из белого списка и отвергает незнакомые поля и типы. В JSON нет HTML, JS, Unreal class paths или сетевых URL.

**Правило, отложенное вместе с мультиплеером.** В 1.0-draft `notes` мог попасть на общий терминал, что было утечкой (бывший R-06). В одиночной игре ограничение не нужно, но его надо восстановить как жёсткое правило белого списка (`notes` недопустим при `scope=terminal`) одновременно с появлением MP. Зафиксировано в §15, ADR-005.

## 5.4 `BlueprintRequest`

Исправление относительно 1.0-draft: там текст §5.4 и пример §11.2 перечисляли разные поля (`belts`/`pipes`/`power` плоско против вложенного `connections`; `naming` против `outputName`). Ниже — единственный канонический набор, совпадающий с `contracts/blueprint.example.json`.

Поля: `schemaVersion`, `requestId`, `machineClass`, `recipeClass`, `count`, `clockPercent`, `clockApplied`, `layout`, `connections{belts,pipes,power}`, `outputName`. Поле `targetPlayer` удалено — адресат один.

- `requestId` обеспечивает идемпотентность: повторный вызов с тем же `requestId` не создаёт второй чертёж.
- `clockPercent` + `clockApplied`: открытый вопрос 1.0-draft состоял в том, выставляет ли генератор такт в самом чертеже (оверклок требует power shards и задаётся после размещения). Контракт теперь отвечает честно: `clockApplied=false` означает, что значение использовано только в расчёте `plannedRate`, а в построенном чертеже такт не выставлен. Уточняется spike'ом v1.1.

Отдельные `PreviewResult` и `CreateResult`. `PreviewResult` содержит `valid`, массивы `errors` и `warnings` с машиночитаемыми кодами, оценки входов/выходов, мощности и габаритов, предложение разбиения на модули. Код предупреждения `MANIFOLD_RAMP_UP` обязателен: у манифолда известен эффект разгона и голодающей последней машины, и preview должен об этом сообщать, а не только считать суммарный поток.

Порядок: dry-run и валидация → создание через authority-слой. Отдельного подтверждения нет: чертёж только появляется в библиотеке, в мир его ставит сам игрок. В ручной форме (v1.1) создание запускает кнопка игрока; при вызове из чата `PreviewResult` и итог показываются в ответе. Запрос с `errors` отклоняется с указанием причины.

## 5.5 Версионирование и совместимость

В 1.0-draft `schemaVersion` был у сущностей, но согласования версий компонентов не было. Теперь:

- У мода и адаптера единый `apiVersion`. Мод присылает свой при подключении; при несовпадении мажорной версии AI-функции отключаются с **видимым игроку сообщением**, ручные продолжают работать.
- Версию Foreman изолирует адаптер: мод не зависит от API Foreman напрямую. Установщик фиксирует проверенную версию Foreman.
- Мод и сайдкар поставляются одним установщиком с согласованными версиями, чтобы пользователь не смешивал сборки.
- У сущностей сохраняется `schemaVersion` и миграции при загрузке.
- JSON Schema контрактов лежат в `contracts/schemas/`, примеры проверяются по ним в CI.

## 5.6 Единицы

Твёрдые предметы — `items/min`, жидкости и газы — `m3/min`, мощность — MW. Игра хранит жидкости во внутренних единицах (1 м³ = 1000); перевод выполняется один раз, на границе `CatalogProvider`. Остальной код и все контракты работают только в единицах выше.

# 6. Интерфейсы игрока и UX

## 6.1 AI Terminal

Открывается по E; показывает тот же UI-контроллер, что и переносное устройство, с пресетом полной сетки. У физического экрана два режима: лёгкий world-display (render target, обновляется по изменению) и полный интерактивный UMG при открытии. Настройка терминала хранится как ссылка `terminalId → screenId`, не как копия разметки.

Открытый вопрос, перенесённый из 1.0-draft: требует ли терминал питания или декоративен. Решение влияет на игровой баланс, не на архитектуру.

## 6.2 AI Assistant

Крафтится обычным игровым способом и занимает стандартный ручной слот. ЛКМ открывает интерфейс, горячая клавиша переключает HUD. Критерий активности — «в активном слоте/выбран в руке», а не наличие в инвентаре: это даёт однозначное включение и скрытие HUD при переключении оборудования. Не зависеть от PowerSuit или сторонних расширений слотов.

**Layout-пресеты по поверхности.** У терминала (большой экран, мышь, игрок стоит) и у экипировки (быстрый доступ, возможно на ходу) разная эргономика, и буквально один и тот же экран плохо подходит обоим. Контроллер и набор виджетов общие, раскладка выбирается пресетом: `slots-3` для терминала, `hud-compact` или `slots-1` для экипировки. Поле `layout` в `ScreenDefinition` это и обеспечивает.

## 6.4 Представление производственного плана

Решение изменено относительно 1.0-draft (ADR-007). Прежний базовый путь — выделение интерактивного graph UI из Satisfactory Build Calculator — перестал быть обязательным для v1.0: это был единственный оставшийся риск, способный опрокинуть релиз.

**Уточнение 2.1-draft.** Ядро планировщика SBC берётся в v1.0 (§8.3), и у того же проекта есть виджет графа с pan/zoom (`SBCCalculatorWidget`, около 1600 строк). До реализации своего графа в Milestone 1 этот виджет оценивается: если адаптировать его дешевле, чем написать свою раскладку, берём его.

В v1.0 два уровня, первый из которых гарантирован:

1. **Таблица** — авторитетное представление: группы машин, количество, такт, входы/выходы в единицах в минуту, сырьё, суммарная мощность, предупреждения. Вся ценность AC-03 («какие машины, сколько, сколько энергии») достигается здесь.
2. **Послойный граф, read-only** — отрисовка в UMG: продольное расслоение DAG по длиннейшему пути, упорядочивание узлов внутри слоя для сокращения пересечений, рёбра с подписью потока. Pan/zoom и выбор узла с переходом в таблицу. Перетаскивания и правки на холсте нет.

Производственная цепочка — DAG из нескольких десятков узлов с естественными уровнями (сырьё → промежуточные → целевой), поэтому послойная раскладка здесь предсказуема и не требует внешнего движка. Graphviz в v1.0 не нужен.

Интерактивная правка на холсте появляется в v1.4 — наращиванием интерактивности на то представление, которое будет выбрано в v1.0 (своё или виджет SBC).

## 6.5 HUD

Набор маленьких прозрачных `ScreenWidget`, а не второй независимый UI: текстовые подсказки, задачи, показатели мощности, мини-представление плана, временные графики, уведомления. Готовые профили `minimal`, `production`, `power`, `work-order`; виджеты включаются, скрываются и переставляются. Управление — назначаемыми клавишами, а с v1.2 ещё и теми же Screen-инструментами. HUD локален игроку.

## 6.6 Экран в мире

Решение упрощено относительно 1.0-draft. Прежняя схема (внешний рендер PNG, доставка клиенту по подписанному адресу, запрет на создание текстур на DS) существовала из-за headless-сервера. В одиночной игре композиция рендерится в **render target** в том же процессе и применяется к материалу меша терминала — штатный приём UE, без внешнего сервиса и без пайплайна изображений.

Обновление — по изменению содержимого (`renderRevision`), не покадрово. Никаких высокочастотных стримов. Подход Image Screens остаётся референсом на случай нетривиальностей с материалом, но зависимостью не является.

# 7. Граница доверия LLM

Эта граница — главная причина, по которой authority-слой сохраняется в одиночной игре. Отказ от мультиплеера снял угрозы со стороны других игроков, но не изменил ни одной угрозы со стороны модели. Защита строится не на подтверждениях, а на закрытом наборе инструментов без доступа к миру и строгой валидации каждого вызова (ADR-009).

## 7.1 Инструменты

Мод предоставляет инструменты через адаптер сайдкара (§3.3). Каждый инструмент — операция из `OperationRegistry` с JSON Schema, лимитами размера/частоты и ручной точкой входа в UI (§7.5). Ни один инструмент не изменяет игровой мир. Каталог отдаётся только поисковыми инструментами с пагинацией, по умолчанию — только разблокированное в текущем сохранении (ADR-017): полный каталог из сотен рецептов в одном ответе переполнил бы контекст модели.

| Инструмент | Версия | Что делает | Ручной путь в UI |
|---|---|---|---|
| `search_items`, `get_item`, `list_machines` | v1.0 | Поиск по каталогу | Planning → браузер каталога: поиск, карточка предмета, вкладка машин |
| `get_recipes` | v1.0 | Рецепты по продукту или ингредиенту, флаг `unlockedOnly` | Браузер каталога: «из чего делается», «где используется» |
| `compute_plan` | v1.0 | Расчёт ядром SBC в моде, результат — `ProductionPlan` | Planning: цель, расход/мин, альтернативы → «Рассчитать» |
| `get_plan` | v1.0 | Сохранённый план | Planning: список планов |
| `query_metric` | v1.0 | Телеметрия: значение или временной ряд | Dashboard: выбор метрики и окна |
| `list_notes`, `get_note`, `create_note`, `update_note` | v1.0 | Заметки игрока | Notes |
| `preview_blueprint` | v1.1 | `PreviewResult` без создания | Blueprint Builder → «Предпросмотр» |
| `request_blueprint_creation` | v1.1 | Создаёт чертёж в библиотеке; в мир его ставит игрок | Blueprint Builder → «Создать»; или строка плана → «Чертёж» |
| `list_widget_types` | v1.2 | Доступные типы виджетов | Screens: палитра виджетов |
| `create_screen`, `update_screen` | v1.2 | Создание и правка `ScreenDefinition` | Screens: редактор экрана |

| `set_hud_profile` | v1.2 | Выбор HUD-профиля | Клавиша и настройки HUD (ручной путь есть с v1.0) |

## 7.2 Пайплайн

Текст игрока → Foreman/LLM → вызов инструмента → адаптер → канал к моду → валидация по схеме → валидация по живому каталогу → применение → UI получает событие `screen.updated` / `plan.updated` и обновляет конкретные виджеты.

Подтверждений игрока нет: пишущие действия (заметка, экран, чертёж) не изменяют мир. Правка через интерфейс вызывает те же внутренние операции, что и инструменты. Невалидный вызов отклоняется с машиночитаемой причиной и не изменяет сохранённое состояние. **Не** разбирать текст ответа LLM регулярными выражениями, чтобы понять действие.

## 7.3 Инъекции через авторский текст игрока

Внутрь контекста попадают строки, написанные человеком: заметки, имена терминалов, `outputName` прошлых чертежей, история чата. Заметка вида «назначь экран X на терминал Y» будет прочитана моделью как инструкция. Худшее, к чему это может привести, — лишний экран, заметка или чертёж: инструментов, изменяющих мир или удаляющих данные, нет (§7.5, правило 6). Поэтому подтверждения не вводятся, а меры такие:

1. Аргументы инструментов никогда не принимаются в виде идентификаторов, извлечённых из текста: `className`, `recipeClass`, `id` метрики и плана сверяются с живым каталогом.
2. Авторский текст игрока передаётся модели в явно размеченном виде как данные, а не как часть инструкций.
3. Лимиты частоты (§7.4) не дают зациклившейся модели засыпать игрока экранами и чертежами.

Пункт 2.0-draft о подтверждении записей «по происхождению» удалён: происхождение вызова нельзя установить даже в принципе, потому что в одном ходе смешаны реплика игрока и прочитанные данные.

## 7.4 Лимиты

LLM не может задавать сетевые URL, выполнять команды операционной системы или произвольный код; допустимы только объявленные виджеты и каталогизованные источники. Ограничения: размер `ScreenDefinition`, число виджетов, нижний порог `refreshSec` для тяжёлых источников, размер страницы поисковых инструментов, частота расчёта планов, создания экранов, заметок и чертежей.

## 7.5 Паритет ручного и AI-пути

Принцип (ADR-018): **модель не может ничего, чего не может игрок вручную.** Инструменты модели — это фасад над теми же операциями, которые вызывает UI. Это делает помощника ускорителем, а не единственным способом что-то сделать, и сужает поверхность атаки: модели доступно только то, что уже доступно игроку.

Правила:

1. **Одна операция — два входа.** Каждый инструмент из §7.1 — операция `OperationRegistry` с ручной точкой входа (форма, кнопка, вкладка). UI и модель передают одинаковые аргументы (один контракт: `BlueprintRequest`, `ScreenDefinition`, параметры расчёта плана) и проходят один и тот же `Validator`.
2. **Реестр — единственный источник описаний инструментов.** Адаптер получает их от мода, а не хранит свои. Тест сборки падает, если операция выставлена модели без ручной точки входа.
3. **Одинаковый результат.** Объект, созданный моделью, — обычный объект мода: план открывается в Planning, экран — в редакторе Screens, заметка — в Notes, чертёж — в библиотеке. Игрок правит его вручную так же, как созданный им самим.
4. **Ручной путь не зависит от LLM.** Операции мода работают и без сайдкара (FR-10). Work Orders живут в Foreman, поэтому их ручной путь требует запущенного сайдкара, но не LLM: формы вкладки Work Orders → адаптер → REST Foreman.
5. **Версии.** Инструмент появляется не раньше своего ручного пути (§1.2).
6. **Обратное не требуется.** Не каждая ручная операция становится инструментом: удаление заметок, экранов и планов, настройки клавиш и конфигурация остаются только ручными. Это дополнительно ограничивает возможный вред от модели (§7.3).

**Пример: чертёж из n плавилен.** Вручную: Blueprint Builder → машина «Плавильня», рецепт «Железный слиток», количество n, коллекторы и питание, имя → «Предпросмотр» (`PreviewResult` с потоками, габаритами и предупреждениями) → «Создать». Быстрее: в таблице плана у группы плавилен кнопка «Чертёж» заполняет ту же форму машиной, рецептом и количеством из группы. Через модель: фраза в чате → `preview_blueprint` → `request_blueprint_creation` с тем же `BlueprintRequest`. Во всех трёх случаях вызывается одна операция, и результат одинаков.

**Пример: график мощности.** Вручную: Dashboard → метрика `power.consumption`, окно 15 минут. Через модель в v1.0: `query_metric` возвращает ряд, и модель отвечает текстом. С v1.2 модель может поставить такой же график на экран через `create_screen` — тот же виджет `timeseries`, что игрок добавляет в редакторе Screens.

# 8. Данные и вычисления

## 8.1 Каталог из игры

`CatalogProvider` читает `AFGRecipeManager` и зарегистрированные в SML классы напрямую. Это охватывает альтернативные и корректно зарегистрированные модовые рецепты и даёт точный ответ на вопрос «можно ли использовать это прямо сейчас».

Отправная точка реализации — слой данных SBC (`FSBCProductionData::SynchronizeRuntimeRecipes`): он уже обходит `AFGRecipeManager::GetAllRecipes`, читает продукты, ингредиенты, длительность и машины рецептов и подхватывает рецепты других модов в рантайме. `CatalogProvider` становится единственным владельцем этих данных; планировщик получает их из него.

Прежняя схема с `getRecipes`/`getSchematics` из FRM устранена, и вместе с ней — необходимость сверять два источника. Бывший R-03 (`getRecipes` возвращает и закрытые рецепты) закрыт не обходным путём, а исчезновением второго источника.

## 8.2 Телеметрия

`TelemetrySampler` собирает фактические значения из игровых подсистем: производство ресурса/мин, потребление и генерацию электричества, активность машин, суммарные входы/выходы по выбранной группе. Значения несут `source=live` либо `source=planned`, временную метку, единицу, точность и scope.

Структура данных фабрики нетривиальна, и FRM уже проделал работу по поиску нужных подсистем. Его код — основной референс при реализации телеметрии, при условии разрешения из §2.2.

**Нагрузка на GameThread остаётся риском и меняет только форму.** HTTP-раунд-трипа больше нет, но тяжёлая агрегация по подсистемам в игровом потоке каждый тик просадит FPS так же надёжно, как частый опрос FRM. Правила:

- Сбор по расписанию, не по запросу UI; UI читает последний снапшот.
- В GameThread выполняется только снятие значений; агрегация, расчёт производных и сглаживание — на воркере.
- Предлагаемые интервалы до измерения: мощность 2–5 с, агрегаты фабрик 5–15 с, каталог только по событию изменения.
- Кольцевой буфер временных рядов в памяти мода, персистится вместе с состоянием.
- **Частота обновления виджета не выше частоты данных.** В 1.0-draft HUD обновлялся «1–2 раза/с» при данных раз в 2–5 с, то есть перерисовывал интерполяции устаревших чисел. Виджет показывает значение с метаданными свежести и перерисовывается при поступлении нового снапшота.

## 8.3 Планировщик: ядро Satisfactory Build Calculator

Решение изменено в 2.1-draft (ADR-013): вместо собственной разработки адаптируется готовое ядро SBC. Вход: целевой предмет, расход/мин, выбранные альтернативные рецепты, Power Shards и Somersloops по группам. Выход: `ProductionPlan` (§5.2).

**Что берётся.** `FSBCProductionCalculator` строит дерево производства от цели вниз: число машин = требуемый поток ÷ (производство рецепта × такт × усиление), мощность с учётом разгона и Somersloops, генераторы, побочные продукты у узлов. Данные он получает из `CatalogProvider` (§8.1), то есть считает по рецептам, реально разблокированным в текущем сохранении, включая модовые.

**Что меняется при адаптации** (код в `third_party/sbc/` с перечнем патчей, §2.2):

- Вход из `CatalogProvider` вместо загрузки собственных `Data/*.json`.
- Выход — наш `ProductionPlan` (группы, соединения, сырьё, итоги, предупреждения) вместо дерева узлов виджета.
- Отвязка от локализации SBC (`ESBCLanguage`): имена берутся из `GameCatalog`.
- Правило «известный рецепт ≠ разблокированный»: закрытый рецепт даёт `RECIPE_LOCKED`.

**Ограничения v1.0 — видны в UI, а не скрыты:**

1. **Побочные продукты** (нефтепереработка, алюминий) считаются и показываются у групп, но не сводятся в общий баланс: `BYPRODUCT_NOT_BALANCED`.
2. **Циклы рецептов** (переработанные пластик и резина): расчёт останавливается с ошибкой `RECIPE_CYCLE_UNSUPPORTED` и объяснением, какой рецепт замкнул цикл.

**Путь развития (v1.x).** Слой данных и контракт остаются, расчёт заменяется LP-моделью на HiGHS (MIT, C++, встраивается в мод). Это снимает оба ограничения и добавляет оптимизацию (минимум энергии, минимум сырья, несколько рецептов на один продукт).

**Рассмотренные альтернативы** (поиск 05.11.2026):

| Вариант | Почему не выбран |
|---|---|
| Планировщик Foreman (`ingredient_tree`, `full_production_line`) | Статические данные, не знает разблокировок сохранения; нужен запущенный сайдкар (нарушает FR-10) |
| FactorioLab | LP через GLPK (GPL), браузерное Angular-приложение, статические данные |
| KirkMcDonald satisfactory-calculator | Свой симплекс на JS, Apache-2.0, последний коммит 10.2024, статические данные |
| ERP for Factory Games | Хостинг-сервис на .NET с OR-Tools, тяжело для локального мода |
| SatisfactoryTools | Расчёт на удалённом API, офлайн не работает |
| Ficsit Companion | Ручной узловой редактор без решателя |
| satisfactory-solver (kiligir) | Нет лицензии |

Планировщик Foreman моделью не используется: адаптер не включает его инструменты в белый список (§3.3), и `compute_plan` остаётся единственным источником расчёта. Это сохраняет закрытым бывший R-04 (расхождение live-данных и статического графа) и обеспечивает FR-10: планирование работает при остановленном сайдкаре.

## 8.4 `plannedRate` против `actualRate`

Две независимые величины: `plannedRate` = рецепт × число машин × такт; `actualRate` = наблюдаемое в игре. В таблице, графе и HUD не смешивать без подписи. Числа считает мод (планировщик и телеметрия); LLM только объясняет результат.

# 9. Создание Blueprint (v1.1)

## 9.1 Ядро

Используется проверенное ядро Factory Spawner: `FBuildPlanGenerator::Generate(TArray<FFactoryCommandToken>)`. Чатовый ввод заменяется программным API, компоновка `single_row` ограничивается известными типами машин. Существующая реализация создаёт splitter/merger, pipe cross, belt/lift, power wire и пишет Blueprint через игровой subsystem.

**Главное упрощение относительно 1.0-draft.** Бывший R-01 состоял в том, что генератор опирается на `FirstPlayerController` и пишет чертёж в текущий subsystem, а на Dedicated Server локального игрока нет. В одиночной игре `FirstPlayerController` — это и есть игрок, и Factory Spawner именно так и работает сегодня. Spike D прежней редакции из «может опрокинуть архитектуру» превращается в обычную задачу интеграции.

## 9.2 Изменения в адаптированном ядре

Экспорт/обёртка программного API; идемпотентность по `requestId`; генерация уникального имени, не перезаписывающего чертежи `FactorySpawner`; валидация количества, класса, рецепта и разблокировки; проверка габаритов; расчёт нагрузки по лентам и трубам с предупреждением `MANIFOLD_RAMP_UP`; корректная обработка ошибок без частично связанных объектов; выяснение, применим ли `clockPercent` в самом чертеже (§5.4).

## 9.3 Ограничения v1.1

Только шаблонные ряды; ввод и вывод в отдельных коллекторах; раздельные входы для нескольких ингредиентов; питание; предлагаемое разбиение превышающего размер ряда на модули. Распределение напора в трубах и идеальный баланс сложных заводов не гарантируются: игрок видит ограничения и решает вручную.

# 10. Хранение и жизненный цикл

Решение изменено в 2.1-draft (ADR-014). FR-10 по-прежнему требует, чтобы состояние было доступно без сайдкара, поэтому оно хранится у мода. Но ключ по имени файла сохранения ненадёжен: автосохранения ротируются, файлы переименовывают и копируют. Поэтому компактное состояние хранится **прямо в сохранении**, а снаружи остаётся только объёмное и восстановимое.

**Идентификатор сохранения.** Save-persistent subsystem мода при первой загрузке генерирует GUID `saveId` и хранит его в сохранении. Все внешние данные и playthrough Foreman привязаны к `saveId`.

| Где | Что хранится | Не хранить |
|---|---|---|
| Satisfactory save (subsystem мода) | `saveId`, `ProductionPlan`, `ScreenDefinition`, HUD-профили, заметки, привязки `terminalId → screenId`; установленные терминалы и их игровые параметры | токены, ключи, переписка, телеметрия |
| Локальные файлы мода (ключ — `saveId`) | кольцевые буферы телеметрии, кэш отрендеренных экранов | ключи LLM-провайдера |
| Foreman DB | аккаунт, playthrough (сопоставлен с `saveId`), переписка, Work Orders | игровые значения каждого тика, копии каталога |
| Локальный конфиг | hotkeys, аудио, адрес адаптера, токен канала мод ↔ адаптер | — |

Состояние в сохранении — килобайты JSON, поэтому прежнее возражение «не хранить длинные JSON-схемы в save» к нему не относится. Следствия: загрузка старого сохранения возвращает его планы и экраны (ветвление сохранений корректно само собой); копия сохранения на другой машине переносит и состояние; у копий одного сохранения общий `saveId`, поэтому они делят внешнюю телеметрию и playthrough — это допустимо.

Порядок восстановления: загрузка сохранения (с ним — состояние мода) → сборка каталога → отрисовка экранов из кэша → подключение к адаптеру, если сайдкар поднят → доступность AI-функций.

Безопасное удаление: терминал пропадает из save, но его `ScreenDefinition` остаётся в состоянии мода, чтобы не терять дизайн. Удаление мода не должно повреждать сохранение.

## 10.1 Кэш отрендеренного экрана

§14 1.0-draft обещала «физический экран показывает последнюю PNG», но клиентское хранение этого изображения нигде не описывалось, то есть обещание деградации было невыполнимым. Теперь: кэш по ключу `saveId + screenId + renderRevision`, персистентный, читается до подключения сайдкара. Терминал, у которого содержимого ещё не было, показывает документированное пустое состояние, а не ошибку.

# 11. Сбои, ограничения производительности и деградация

| Сбой | Ожидаемое поведение |
|---|---|
| Сайдкар/Foreman не поднят | Мод пытается запустить сайдкар (§4.1); пока его нет — работают все ручные вкладки, планировщик, метрики, сохранённые экраны; AI-вкладки показывают состояние «не подключено» с подсказкой |
| Несовпадение `apiVersion` мода и адаптера | AI-функции отключены с видимым сообщением; ручные работают |
| Адаптер не может войти в Foreman или API Foreman изменился | Чат показывает причину; инструменты мода и ручные функции не затронуты |
| LLM-провайдер недоступен | Foreman отвечает ошибкой, чат показывает причину, остальное работает |
| STT/TTS недоступен (v1.3) | Текстовый чат и управление клавишами сохраняются |
| Ошибка Blueprint (v1.1) | Не создавать частично связанные объекты; показывать причину; сохранять запрос для исправления |
| Цикл рецептов в плане | Расчёт останавливается с `RECIPE_CYCLE_UNSUPPORTED` и объяснением, а не молчаливый неверный результат (§8.3) |
| Мультиплеерная сессия или вход другого игрока | Мод инертен, пока в сессии есть удалённые игроки; сообщение игроку; сессия стабильна (§4.2) |
| Обновление игры сломало SML | Мод не загружается средствами SML, сохранение не повреждается |

**Начальные, проверяемые нагрузочные цели** (не гарантии до измерений): открытие кэшированного UI без обращения к сайдкару; перерисовка виджета по поступлению снапшота, не по таймеру; снятие телеметрии в GameThread в пределах бюджета доли миллисекунды на выборку, агрегация вне GameThread; экран в мире обновляется по `renderRevision`; десятки размещённых терминалов не создают линейного роста затрат в кадре (неактивные терминалы не рендерят). Перед релизом профилировать GameThread и GPU.

# 12. Доступы и безопасность

Мультиплеерные пункты 1.0-draft (pairing-токены с привязкой к `worldId`/`playerId`, ACL терминалов, роли owner/editor/viewer, запрет публикации портов) удалены вместе с топологией. Пункты, относящиеся к изоляции LLM, сохранены полностью — они не зависели от мультиплеера.

1. В игровом процессе нет входящих слушателей. Адаптер слушает только loopback; мод подключается к нему с токеном из локального конфига, сгенерированным установщиком.
2. MCP-эндпойнт адаптера для Foreman слушает только loopback; токен передаётся в query-строке `MCP_URL`, потому что MCP-клиент Foreman не отправляет заголовков. Foreman пишет `MCP_URL` в локальный лог при старте — для loopback-токена это допустимо; поддержку заголовков можно предложить Foreman upstream.
3. Ключ LLM-провайдера хранится у сайдкара, не в игровых файлах и не в сохранении. Учётные данные локального аккаунта Foreman — в конфиге сайдкара.
4. Все внешние вызовы валидируются JSON Schema; действуют лимиты размера и частоты (§7.4).
5. У модели нет инструментов, изменяющих мир. Создание экранов, заметок и чертежей проходит authority-слой; идемпотентность через `requestId`.
6. Модель не может ничего, чего не может игрок вручную: инструменты генерируются из `OperationRegistry` и выставляются только при наличии ручной точки входа (§7.5).
6. Идентификаторы в аргументах инструментов сверяются с живым каталогом, а не принимаются из текста (§7.3).
8. Запрещены блокирующие сетевые вызовы в GameThread и зависимость игрового тика от внешнего сервиса.
9. Состояние привязано к `saveId` и хранится в самом сохранении: план из другого сохранения не применяется молча.

# 13. План разработки

Spike'и 1.0-draft A–E сократились: два из них (канал до игрового сервера, доставка Blueprint на DS) исчезли вместе с топологией, один отложен в v1.4. В 2.1-draft S2 и S3 переформулированы под адаптер и ядро SBC, а первым результатом работ стал вертикальный срез v0.1.

| Этап | Deliverable | Условие завершения |
|---|---|---|
| Spike S1 | Один UMG UI из двух объектов | Терминал и предмет открывают один контроллер с разными пресетами; `RequiredOnRemote` и событие входа удалённого игрока проверены |
| Spike S2 | Адаптер и канал к моду | Foreman видит инструменты `sf-mcp` и мода через адаптер; адаптер сам входит в Foreman; вызов инструмента доходит до мода по исходящему каналу, ответ собран вне GameThread, FPS не просел |
| Spike S3 | Каталог, планировщик, телеметрия | Ядро SBC в моде считает по `CatalogProvider`: vanilla и modded рецепты, статус разблокировки верен; телеметрия из подсистем в бюджете GameThread (после проверки лицензии FRM, R-12) |
| Spike S4 | Экран в мире | Render target на меше терминала, обновление по ревизии, кэш читается до подключения сайдкара |
| Spike S5 | Упаковка | Установщик ставит портативный Node, бандлы и SQLite; мод запускает сайдкар; путь от скачивания до первого ответа без ручных правок конфигов |
| **v0.1 — вертикальный срез** | Терминал + вкладка Planning (только таблица) + чат через адаптер | Проверен весь технический путь (S2, S3) и интерес игроков до вложений в граф, HUD и экран в мире |
| Milestone 1 | Ручной контур | `OperationRegistry`; планировщик, таблица, граф, браузер каталога, dashboard, заметки, HUD, персистентность в сохранении — всё без сайдкара |
| Milestone 2 | AI-контур | Чат; Work Orders с ручными формами; инструменты v1.0, сгенерированные из реестра; белый список в адаптере; тест паритета |
| Milestone 3 | Hardening | Инертность в MP в ходе сессии, деградация, миграции, профилирование, установщик, документация |

Порядок: S2 и S3 первыми (они определяют срез v0.1), S1 параллельно, S4 и S5 — до Milestone 1 и Milestone 3 соответственно.

**Тестирование.** Ядро планировщика и валидатор тестируются UE Automation (Spec) без загрузки мира. Фикстуры — примеры из `contracts/` и снимок каталога, выгруженный из игры в JSON. Адаптер покрывается интеграционными тестами против зафиксированной версии Foreman. Примеры контрактов проверяются по JSON Schema в CI. **Тест паритета:** сборка падает, если операция выставлена модели без ручной точки входа (§7.5); для каждой операции один и тот же набор аргументов, поданный из UI и через инструмент, даёт одинаковый результат.

Критический путь v1.0 не содержит ни одного spike'а, способного опрокинуть архитектуру: S1 и S4 — штатные приёмы UE; S2 — исходящее соединение из мода и Node-процесс с официальным MCP SDK, без изменений Foreman; S3 опирается на работающий мод SBC того же стека; S5 — инженерная, а не исследовательская задача.

**Правило fallback.** Если spike опровергает выбранное решение, ADR о замене принимается до реализации зависящей функции. Для S2 fallback — upstream PR в Foreman: переменная `MCP_EXTRA_URLS`, подключающая уже готовый `McpAggregateGateway`, плюс поддержка заголовков. Для S3 — собственный расчёт на HiGHS поверх `CatalogProvider` (каталог) и сужение набора метрик до дешёвых (телеметрия). Для S5 — документированный docker-путь с явным предупреждением о сужении аудитории.

# 14. Acceptance criteria для v1.0

**AC-01.** Игрок размещает AI Terminal, нажимает E и открывает полноэкранную панель. Повторное открытие восстанавливает последнее состояние.

**AC-02.** Игрок создаёт AI Assistant, экипирует в обычном ручном слоте, ЛКМ открывает ту же панель в компактном пресете. При переключении предмета HUD скрывается и возвращается после повторной активации.

**AC-03.** Без сайдкара игрок открывает Planning, выбирает рецепт и альтернативу **из действительно разблокированных в этом сохранении** (включая рецепты установленных модов), задаёт расход/мин и получает таблицу машин/потоков/сырья, суммарную мощность и читаемое послойное представление плана с pan/zoom и выбором узла. Побочные продукты и циклы рецептов обозначены как ограничения (§8.3), а не дают молча неверный результат. Интерактивная правка на холсте в v1.0 не требуется.

**AC-04.** Фактические ресурсы/мин и мощность отображаются с меткой `live` и временем актуальности; плановые значения отмечены `planned`. Временные графики работают минимум на одном выбранном контуре. Частота перерисовки не превышает частоту поступления данных.

**AC-05.** Текстовый диалог с Foreman работает внутри игрового UI: потоковый ответ, отмена, история, видимые Work Orders. Инструменты v1.0 (`search_items`, `get_recipes`, `query_metric`, `compute_plan` и др.) вызываются моделью через адаптер и возвращают данные текущего сохранения; инструменты Foreman вне белого списка модели не видны.

**AC-06.** HUD отображает текстовую подсказку, ресурсную метрику, мини-представление плана и временной график мощности; игрок управляет видимостью назначаемыми клавишами.

**AC-07.** После перезапуска игры планы, экраны, HUD-профиль и заметки восстанавливаются вместе с сохранением, в том числе после переименования файла и ротации автосохранений. Открытие другого сохранения не подмешивает чужое состояние.

**AC-08.** Экран терминала показывает актуальное содержимое, обновляется по изменению, а не покадрово, и читается из кэша до подключения сайдкара. Терминал без содержимого показывает документированное пустое состояние.

**AC-09.** При остановленном сайдкаре работают все ручные вкладки и планировщик, AI-вкладки показывают состояние «не подключено», метки устаревших данных корректны, игра не падает и не фризит.

**AC-10.** Если сессия мультиплеерная или к одиночной игре подключается другой игрок, мод становится инертным: UI и HUD закрыты, связь с адаптером разорвана, игрок видит внятное сообщение, сессия стабильна. После ухода удалённых игроков мод возобновляет работу. Игрок без мода подключиться не может. Сохранение с размещённым терминалом открывается в любой сессии без повреждений.

**AC-11.** Профилирование подтверждает соблюдение бюджета GameThread (§11) при десятках размещённых терминалов и активном сборе телеметрии.

**AC-12.** Установка: от скачивания до первого ответа помощника без ручного редактирования конфигов и без Docker, кроме ввода ключа LLM-провайдера. Сайдкар запускается модом при старте игры.

**AC-13.** Паритет: для каждого инструмента v1.0 из §7.1 игрок выполняет то же действие вручную через UI без LLM-провайдера, а для операций мода — и без сайдкара. Результат совпадает с результатом вызова модели (тот же контракт), а объект, созданный моделью, игрок открывает и правит вручную. Тест паритета (§13) проходит в CI.

# 17. История изменений

## 17.1 2.1-draft относительно 2.0-draft

Сводка для ревью. Причины: проверка исходников Foreman (§3.4), поиск готовых планировщиков (§8.3) и разбор документа.

**Изменено:**

- **Связка с Foreman** (ADR-012). Вместо MCP-эндпойнта в игре — адаптер сайдкара: единственный MCP-сервер Foreman, белый список инструментов, авторизация, стабильный API для мода. Мод подключается к адаптеру исходящим соединением. Причина: Foreman подключается только к одному MCP-серверу, не шлёт заголовков, закрывает чат сессией Better Auth.
- **Планировщик** (ADR-013): адаптированное ядро Satisfactory Build Calculator вместо собственной разработки. Механизм «закрепить ставку» для циклов удалён: в v1.0 цикл даёт ошибку с объяснением, побочные продукты не сводятся в баланс; v1.x — LP на HiGHS.
- **Подтверждения игрока удалены** (ADR-009, §7). У модели нет инструментов, изменяющих мир; заметки, экраны и чертежи создаются после валидации. Правило §7.3 о подтверждении «по происхождению» удалено как нереализуемое.
- **Хранение** (ADR-014): компактное состояние — в сохранении, `saveId` вместо ключа по имени файла.
- **Мультиплеер** (ADR-016, §4.2): определение в ходе сессии, контент регистрируется всегда, `RequiredOnRemote`.
- **Каталог для модели** (ADR-017): поисковые инструменты вместо `get_catalog`.
- **Паритет ручного и AI-пути** (ADR-018, §7.5, FR-11): `OperationRegistry`, ручной путь для каждого инструмента (столбец в §7.1), браузер каталога в Planning, ручные формы Work Orders через REST Foreman, инструменты заметок, правило версий, тест паритета. Фильтр адаптера переведён с чёрного списка на белый.
- **Упаковка** (§4.1): конкретизирована — портативный Node, бандлы, SQLite, launcher; сайдкар запускает мод; `ff-client` не поставляется.
- **Spike'и и план** (§13): S2 и S3 переформулированы, добавлены вертикальный срез v0.1 и стратегия тестирования; новый fallback для S2 — upstream PR в Foreman.
- **Название:** «Satisfactory Build Project» исправлено на фактическое — Satisfactory Build Calculator (SBC).

**Добавлено:** §5.6 единицы; JSON Schema контрактов и проверка примеров в CI; коды предупреждений плана; риск R-17 (API Foreman); раздел закрытых решениями 2.1 рисков (R-13, часть R-02).

**Исправлено в примерах:** `plan.example.json` был внутренне противоречив (альтернатива в `selectedAlternates` не совпадала с рецептом группы, предупреждение о цикле без цикла, неполное сырьё, мощность не сходилась с группами). Новый пример посчитан по рецептам игры.

## 17.2 2.0-draft относительно 1.0-draft

Причина большинства изменений — решение §1.1 об отказе от мультиплеера.

**Удалено:**

- Game Bridge как компонент (ADR-004 отозван); его задачи распределены между модом и локальными файлами.
- FRM как обязательный серверный мод (ADR-003 заменён).
- Канал Bridge → серверное расширение SML — самая несспроектированная часть прежней редакции.
- Серверное расширение как отдельный деплой; осталось authority-слоем в процессе.
- ACL, роли, scope `shared`, pairing-токены, TLS, публикация портов.
- Прежние AC-01 (второй игрок), AC-10 (независимость игроков), AC-11 (late-join).
- Пайплайн изображений для экрана в мире; заменён render target'ом.
- Тип виджета `image`; поле `targetPlayer` в `BlueprintRequest`.
- ADR-010.

**Изменено:**

- Объём v1.0 сужен до ручного контура плюс текстовый чат; Blueprint, AI-экраны, голос и интерактивный граф разнесены по v1.1–v1.4 (§1.2).
- Представление графа: собственное read-only вместо извлечения кода SBC (ADR-007). AC-03 больше не требует интерактивности и не зависит от непройденного spike'а.
- Расчёт плана перенесён в мод (ADR-013), что закрыло R-04 и усилило FR-10.
- Хранение состояния — локальные файлы мода, а не БД внешнего сервиса (ADR-014). Это сознательный разворот относительно промежуточного варианта «всё в БД Foreman»: он противоречил бы FR-10.
- Foreman не форкается; наши инструменты — внешний MCP, который хостит сам мод (ADR-012).
- `ScreenDefinition`: `layout` стал перечислением пресетов с именованными слотами (прежние `layout:"grid"` и `area:"left"` были несовместимы), `source` стал структурированным, добавлены `theme` и клампинг `refreshSec`, `scope` сокращён.
- `BlueprintRequest`: приведён к одному каноническому набору полей (текст и пример прежней редакции расходились), добавлены `requestId` и `clockApplied`.
- `PreviewResult` специфицирован, добавлены машиночитаемые коды предупреждений, включая `MANIFOLD_RAMP_UP`.
- Частота обновления виджетов привязана к частоте данных.
- Spike'и сокращены с пяти до пяти других: исчезли транспорт и Blueprint-на-DS, появились MCP-эндпойнт и упаковка.

**Добавлено:**

- §4.1 упаковка и установка, §4.2 поведение в MP — обоих не было.
- §5.5 согласование версий мода и сайдкара.
- §7.3 инъекции через авторский текст игрока.
- §8.3 планировщик с честной оценкой побочных продуктов и циклов.
- §10.1 кэш отрендеренного экрана, без которого обещание деградации было невыполнимым.
- Риски R-10 (обновление игры), R-11 (упаковка), R-12 (лицензия FRM), R-13 (слушатель в процессе), R-14 (циклы рецептов), R-15 (загрузка в MP), R-16 (ёмкость команды).
- AC-09 (деградация), AC-10 (инертность в MP), AC-11 (бюджет GameThread), AC-12 (установка).
- §2.2 открытые лицензионные вопросы, включая неназванную лицензию собственного мода.

**Сохранено без изменений по существу:** граница доверия LLM и декларативная белая схема экранов (§7, ADR-005); разделение `plannedRate` и `actualRate` (§8.4); единый контракт для ручного и AI-пути (ADR-006); требование «известный рецепт ≠ разблокированный»; правило fallback-ADR при провале spike'а; запрет блокирующих вызовов в GameThread.

**Итог архитектуры.** Релиз состоит из одного мода и одного локального сайдкара: Foreman используется как есть, а тонкий адаптер связывает его с модом. Сложные части берутся из готовых проектов там, где извлечение объективно дешевле реализации: планировщик — из Satisfactory Build Calculator, генератор чертежей — из Factory Spawner, LLM-оркестрация — из Foreman. Собственная разработка сосредоточена на интеграции, адаптере, контрактах, границе доверия LLM и жизненном цикле состояния. Отказ от мультиплеера убрал с критического пути v1.0 все интеграционные неизвестные, способные опрокинуть архитектуру, и оставил один риск, которым проект не управляет вовсе, — совместимость с обновлениями самой игры.
