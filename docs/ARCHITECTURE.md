# Статус и краткое резюме

| Поле | Значение |
|---|---|
| Документ | FICSIT AI — Release Architecture |
| Версия | 3.0-draft · 04.11.2026 (заменяет 2.0-draft того же числа) |
| Статус | Проект архитектуры на согласование; не описание уже реализованного продукта |
| Целевой стек | Satisfactory 1.2, SML 3.12, UE 5.6, Windows game client |
| Топология | **Только одиночная игра.** Dedicated Server, listen server и мультиплеер вне v1.x |
| Лицензия | **Apache-2.0** (решение принято, §2.2) |
| База кода | **Форк Satisfactory Build Calculator** (MIT), а не greenfield-проект (§2, ADR-016) |
| Главный приоритет | Переиспользование готовых решений там, где задача объективно сложна |
| Реестр модулей | `MODULES.md` — декомпозиция на 34 модуля с результатами поиска готовых решений по каждому |

**Назначение.** FICSIT AI — мод к Satisfactory и локальный сервис-компаньон, превращающие FICSIT Foreman в доступного прямо в игре инженерного помощника. Игрок взаимодействует с ним текстом (позже голосом), через размещаемый терминал и экипируемое устройство. Помощник получает реальные игровые данные, планирует производство, показывает производственные графы, управляет декларативными экранами и формирует запросы на создание простых Blueprint.

**Ключевое изменение относительно 1.0-draft (сохраняется).** Проект отказывается от поддержки мультиплеера и Dedicated Server в пределах v1.x. Это решение принято не для экономии, а чтобы убрать с критического пути интеграционные неизвестные, каждая из которых могла опрокинуть архитектуру: сетевой канал между внешним сервисом и игровым сервером, доставка Blueprint клиенту в отсутствие локального игрока, репликация экранов и ACL.

**Ключевое изменение относительно 2.0-draft.** Выполнен систематический поиск готовых решений по каждому модулю (`MODULES.md`), и он изменил три решения редакции 2.0:

1. **Мод строится как форк Satisfactory Build Calculator** (MIT, C++, та же целевая сборка Satisfactory 1.2 / SML 3.12 / UE 5.6), а не как новый проект. Форк приносит внутриигровой калькулятор, **интерактивный** граф производственной цепочки с пан/зумом, чтение каталога с разблокировками и рецептами других модов, выверенную силовую модель с оверклоком и Somersloop, компактный HUD, настраиваемые хоткеи, локализацию и трекер строительства. Редакция 2.0 оценивала иное предложение — извлечь из этого мода отдельный виджет — и справедливо его отклонила (ADR-007). Форк как база проекта — другое решение с другой стоимостью (ADR-016).
2. **MCP-сервер уезжает из игрового процесса в компаньон.** Это снимает с критического пути входящий слушатель в игре вместе с риском R-13 и заменяет реализацию MCP на C++ официальным TypeScript SDK (ADR-017, отзывает ADR-012).
3. **Ficsit Remote Monitoring исключён как источник кода.** В его репозитории нет файла лицензии; README разрешает строить на API, но не заимствовать код. Это закрывает R-12 отрицательным ответом, однако заменять FRM почти нечем не пришлось: состав каталога даёт документированный API SML, разблокировки и числовые параметры — MIT-код форка (ADR-018, заменяет ADR-003).

Полный разбор изменений — в §17.

**Главное ограничение проекта.** Не разрабатывать собственные решения там, где готовый проект уже предоставляет функциональность или исходный код **и где задача объективно сложна**: сериализация Blueprint, маршрутизация лент и труб, LLM-оркестрация, STT/TTS, внутриигровой калькулятор и граф. Обратное тоже верно: не встраивать чужой код там, где собственная реализация проще его извлечения (§2). Отсутствие у стороннего мода публичного API не является основанием объявлять его runtime-зависимостью: такой компонент заимствуется/адаптируется при соблюдении лицензии. **Отсутствие лицензии, напротив, является безусловным основанием исключить компонент из источников кода** (§2.2).

**Принцип приоритета платформы.** Прежде чем писать модуль, проверяется, не предоставляет ли его SML. Редакция 2.0 планировала как собственную работу локальный конфиг, назначаемые клавиши, персистентность состояния и определение топологии сессии; всё это SML предоставляет готовым (§2.3).

**Архитектурный принцип.** Один `ProductionPlan` описывает производство; один `ScreenDefinition` описывает его отображение; один `BlueprintRequest` используется и ручным редактором, и LLM. AI предлагает действия, **authority-слой мода валидирует**, игрок подтверждает действия с игровыми последствиями. В одиночной игре этот слой перестаёт быть границей процессов, но остаётся обязательной границей кода — он изолирует LLM, а не других игроков (ADR-009).

## 1.2 Отложенные версии

Каждая версия ниже закрывает один риск и не блокирует предыдущую.

| Версия | Содержание | Главный риск версии |
|---|---|---|
| v1.1 | Экипируемый AI Assistant и HUD-профили (FR-02, FR-07); Blueprint Builder: ручная форма и общий валидатор | Поведение `FBuildPlanGenerator` под программным вводом |
| v1.2 | Рантайм `ScreenDefinition` и AI-компоновщик экранов: `create_screen`/`update_screen`/`assign_screen` | Качество вывода LLM в рамках белой схемы |
| v1.3 | Голосовой контур: PTT → STT → Foreman → TTS | Аудио в UE/Proton (бывший R-07) |
| v2.0 | Мультиплеер и Dedicated Server | Всё, что снято этим документом; потребует ADR-серии заново |

**Версия v1.4 упразднена.** Она существовала ради одного пункта — интерактивного редактора графа, — и этот пункт приходит в v1.0 вместе с форком (§6.4, ADR-016). Риск R-02 закрыт.

**Правило единого контракта.** Схемы `ScreenDefinition` и `BlueprintRequest` пишутся, валидируются и фиксируются **в v1.0** как файлы `contracts/*.schema.json`, хотя рантайм экранов появляется в v1.2, а Blueprint-путь в v1.1. Контракт должен быть один с самого начала, иначе ручной и AI-путь разъедутся. Но фиксация **схемы** не требует реализации **рантайма** в той же версии: в v1.0 `ScreenDefinition` существует как замороженная схема и один встроенный экран терминала, а не как генерический рендерер с библиотекой экранов (§5.3).

## 1.3 Что не входит

Мультиплеер, Dedicated Server, listen server; автоматическое строительство фабрики в мире; CAD/оптимизатор произвольной 3D-геометрии; свободный исполняемый код/HTML от LLM; автономный NPC; управление транспортом или оборудованием без подтверждения; замена интерфейса всего Satisfactory; поддержка сторонних машин с нестандартной геометрией в генераторе чертежей. **Это не ограничивает получение рецептов модовых машин из игры:** данные присутствуют, даже если генератор чертежей не умеет их размещать.

# 2. Стратегия готовых компонентов

Под «зависимостью» понимается мод/сервис, который конечный пользователь должен установить. «Переиспользовать код» означает включить или адаптировать функциональность в наш мод с соблюдением лицензии и атрибуции. Эти подходы не смешивать.

**Уточнение принципа относительно 1.0-draft (сохраняется).** Переиспользование оправдано, когда стоимость извлечения ниже стоимости реализации. Принцип «не писать заново» не должен превращаться в обязательство встраивать чужой код в простые места.

**Уточнение относительно 2.0-draft: три разных формы переиспользования, которые редакция 2.0 не различала.**

| Форма | Что означает | Когда применима |
|---|---|---|
| Runtime-зависимость | Пользователь обязан установить сторонний мод или сервис | Только SML и Foreman. Для стороннего мода с одним контрибьютором — никогда |
| Извлечение кода | Вынуть из чужого проекта отдельный компонент и встроить в свой | Когда компонент слабо связан с остальным проектом |
| **Форк как база** | Взять чужой проект целиком за основу своего, сознательно наследуя его модель данных | Когда покрытие велико, лицензия позволяет, целевой стек совпадает |

Редакция 2.0 рассмотрела для Satisfactory Build Calculator только вторую форму и справедливо её отклонила: извлечение интерактивного граф-виджета из UMG-дерева чужого мода означает унаследовать его модель данных и обработку ввода. **Третья форма меняет вывод, потому что в ней наследование модели данных — цель, а не издержка.** Покрытие форка измерено в `MODULES.md` и составляет около двух третей модулей ручного контура; лицензия MIT; целевая сборка совпадает буквально (Satisfactory 1.2, SML 3.12, UE 5.6). Решение — ADR-016.

**Почему это особенно важно для UI.** Документация SML прямо указывает, что работа с виджетами в C++ «agonizingly verbose», и рекомендует гибрид C++ и Blueprint. Satisfactory Build Calculator написан на 99.5% C++, включая все виджеты, то есть самый дорогой и наименее приятный участок работы в нём уже выполнен и протестирован на целевой сборке. Редакция 2.0 нормировала контракты до отдельных полей, но оценивала «свою отрисовку графа в UMG» и временные графики одной строкой, хотя именно это — крупнейший пул трудозатрат проекта и единственный с циклом итерации в минутах.

**Текущая подтверждённость.** По состоянию на 04.11.2026 SMR подтверждает совместимость SML 3.12. Для Factory Spawner проверены C++-точки `Generate`, `SpawnPipeAndConnect` и `WriteBlueprintToArchive`, и его версия 2.3.0 уже собрана под целевой стек; в одиночной игре `FirstPlayerController` — это и есть игрок, поэтому главное препятствие прежней редакции (R-01) снято. Для Satisfactory Build Calculator прочитаны `SBCProductionCalculator.h` и `SatisfactoryBuildCalculator.Build.cs`; подтверждено, что `FSBCProductionCalculator` — обычный C++-класс без зависимости от `UObject` и мира, а миру принадлежит единственный метод `SynchronizeRuntimeRecipes`. **Не подтверждена и вынесена в спайк цена адаптации `SBCCalculatorWidget` под DAG** — единственная непроверенная цена решения о форке. Наличие собранного мода не подтверждает наличие доступного API для сторонних модов.

**Риск, который берётся вместе с форком.** У Satisfactory Build Calculator один контрибьютор, 27 коммитов, статус release-candidate и нет опубликованных релизов. Поэтому он берётся **форком, а не зависимостью**: заброшенность апстрима тогда не влияет на проект, а стоимость — однократная. Это же исключает его из runtime-зависимостей по §1.1. Зафиксировано как R-17.

## 2.1 Решения «не писать заново» и «писать самим»

Не писать заново:

- Систему Work Orders, учётных записей, LLM tool calling и управление историей — всё остаётся в Foreman.
- **Реализацию протокола MCP** — официальный TypeScript SDK в компаньоне, а не JSON-RPC и слушатель на C++ (ADR-017).
- **Внутриигровой калькулятор, граф цепочки, силовую модель, HUD, хоткеи и локализацию** — форк Satisfactory Build Calculator (ADR-016).
- **Состав каталога, включая рецепты других модов** — `UModContentRegistry` из SML (§2.3, §8.1).
- **Конфигурацию, назначаемые клавиши, персистентность и определение стороны сессии** — средства SML (§2.3).
- Контроллер конвейеров/труб и сериализатор Blueprint — адаптировать Factory Spawner (v1.1).
- Решатель линейных систем — Eigen; LP — HiGHS, если понадобится (§8.3).
- Аудиодвижок, STT и TTS — sherpa-onnx (v1.3).

Писать самим:

- **Постановку задачи планировщика** — построение матрицы стехиометрии вместо обхода дерева (§8.3, ADR-019). Сам решатель готовый.
- **Телеметрию** — единственный модуль без лицензионно чистого референса (§8.2).
- **Authority-слой, валидатор и очередь подтверждений** — ядро продукта, заимствовать нечего и не нужно (§3.2, §7).
- **Обработчики инструментов в моде и транспорт до компаньона** (§3.3, §7.1).
- **Адаптацию граф-виджета форка под DAG** — основная работа по UI в v1.0 (§6.4).
- **Проекцию плана в контракты и персистентность по ключу сохранения** (§5, §10).

## 2.2 Лицензионные решения

1. **Лицензия проекта — Apache-2.0.** Решение принято. Совпадает с Foreman; MIT у форка, Factory Spawner, KantanCharts, HiGHS и whisper.cpp, Apache-2.0 у MCP SDK, sherpa-onnx и quicktype, MPL-2.0 у Eigen и BSD-3 у IXWebSocket — все совместимы. Полная сводка — в `MODULES.md`.
2. **Ficsit Remote Monitoring исключён как источник кода. Вопрос закрыт отрицательно.** Проверено 04.11.2026: в корне репозитория `porisius/FicsitRemoteMonitoring` файла `LICENSE` нет, в блоке Resources перечислены только Readme и Contributing. По умолчанию это отсутствие разрешения на копирование кода. Одновременно README содержит раздел «Permissions Granted: Feel free to create your own web UI or serial apps» — автор явно разрешает **строить на API**, но не лицензирует **заимствование исходного кода**. Следствия:
   - FRM удалён из §8.1 как референс при реализации чтения подсистем.
   - Замена нашлась почти полностью: состав каталога — документированный `UModContentRegistry` из SML, статус разблокировки и числовые параметры — MIT-код форка. Без референса остаётся только телеметрия (§8.2).
   - Использование **HTTP API** FRM остаётся лицензионно допустимым и сохраняется как резервный вариант, если телеметрия когда-либо станет внешней. В v1.0 не применяется: это противоречило бы принципу «потребитель данных в том же процессе».
   - Риск R-12 закрыт.
3. **Исключены по лицензии:** Graphviz (EPL-1.0) и `piper1-gpl` (GPL-3.0). Оба заменимы и не нужны: раскладка графа приходит с форком, STT и TTS закрывает sherpa-onnx под Apache-2.0. Отдельно отмечается, что прежний `rhasspy/piper` был под MIT — смена лицензии зафиксирована в имени нового репозитория, и ссылаться на старые оценки нельзя.
4. Заимствованный код — в каталоге `third_party/<project>/` с исходным файлом лицензии, `NOTICE` и перечнем внесённых патчей по файлам. Для форка это означает, что унаследованные файлы сохраняют MIT-заголовки, а `NOTICE` фиксирует происхождение.

## 2.3 Что предоставляет сама платформа

Раздела не было. Редакция 2.0 планировала как собственную работу четыре модуля, которые SML предоставляет готовыми. Проверка документации SML выполнена 04.11.2026.

| Задача | Средство SML | Что это отменяет |
|---|---|---|
| Конфигурация мода | Mod Configuration: описание структуры → автогенерация UI в меню Mods, JSON на диске, автозагрузка при старте, `CreateConfigurationWidget`, `FillConfigurationStruct` | Собственный «локальный конфиг» и его UI (§10) |
| Назначаемые клавиши | Mod Key Bind Registry: `RegisterModKeyBind`, `RegisterModAxisBind` | Собственную систему хоткеев (§6.5) |
| Персистентность состояния | `AModSubsystem` с сохранением в save-файл | Часть собственного слоя хранения (§10) |
| Определение стороны сессии | Replication Policy у `AModSubsystem` — декларативная таблица «Singleplayer / Host-and-play / Dedicated / MP Client» | Значительную часть кода детекта топологии (§4.2) |
| Состав каталога, включая модовый | `UModContentRegistry`: `GetRegisteredRecipes()`, `GetLoadedItemDescriptors()`, `GetObtainableItemDescriptors()`, `IsRecipeVanilla()`; события `OnRecipeRegistered`, `OnSchematicRegistered` | Референс FRM для половины §8.1; события дают инкрементальное обновление каталога бесплатно |

**Правило.** Перед реализацией любого модуля проверяется наличие средства SML. Это правило внесено в `MODULES.md` как область A и является причиной, по которой область A почти не содержит собственной работы.

# 3. Логическая архитектура

![Компонентная схема FICSIT AI](assets/components.png){ width=6.0in }

Архитектура состоит из **двух рантаймов**: игровой процесс и локальный сервис-компаньон. В 1.0-draft их было пять (клиент, серверное расширение SML, Game Bridge, Foreman, FRM).

## 3.1 Игровой процесс: презентационный слой

`AI Terminal` (строительный объект), `AI Assistant` (экипируемый предмет), **единственный** `UI Controller`, виджеты UMG, представление производственного плана, HUD, отрисовка экрана в мире, локальные настройки клавиш. Терминал и предмет открывают один и тот же контроллер с разными layout-пресетами: у терминала полная сетка, у экипировки компактная раскладка (ADR-001, §6.2).

## 3.2 Игровой процесс: authority-слой

Единственный путь от любого предложенного действия к мутации мира. Содержит: `CatalogProvider`, `TelemetrySampler`, `Validator`, очередь подтверждений и — с v1.1 — адаптированное ядро Factory Spawner.

**Инвариант.** Ни один обработчик входящего сообщения от компаньона или ответа LLM не имеет прямого пути к мутации игрового мира. Все такие действия проходят через `Validator` и явное подтверждение игрока. Он сохраняется ровно в таком виде, чтобы будущий мультиплеер стал портированием, а не переписыванием (ADR-011).

**Инвариант проверяется скриптом в CI, а не ревью.** Редакция 2.0 полагалась на «ревью и тест». Ревью не масштабируется и не воспроизводится, поэтому правило формулируется как проверяемое: вызовы мутирующего игрового API не должны встречаться в единицах трансляции обработки внешних сообщений. Нарушение роняет сборку.

## 3.2.1 Разделение на ядро и фасад

Раздела не было, и в редакции 2.0 отсутствовал ответ на вопрос, как разрабатывать и тестировать логику мода. Вводится три слоя:

| Слой | Содержание | Зависимость от Unreal |
|---|---|---|
| `core/` | Решатель плана, диагностика, раскладка DAG, работа со схемами, диффы планов, клампинг `refreshSec` | **Нет.** Обычная C++-библиотека, юнит-тесты на хостовом тулчейне |
| `GameFacade/` | Каталог, статус разблокировки, дескрипторы машин, снятие телеметрии, запись чертежа | **Единственное место**, где встречаются типы `AFG*` и `UFG*` |
| Остальной мод | Виджеты, акторы, подсистемы, транспорт | Полная |

Два следствия, каждое из которых решает отдельную задачу:

1. **Скорость разработки.** Планировщик с байпродуктами и циклами невозможно отлаживать запусками Satisfactory. Цикл итерации для логики падает с минут до секунд. Это внесено в нефункциональные цели §1.1.
2. **Единственная конкретная митигация R-10.** Риск «обновление игры ломает мод» назван в §15.2 самым вероятным убийцей проекта, а митигирован был формулировкой «минимум связи с внутренними структурами игры». С фасадом это становится проверяемым правилом: `AFG*`/`UFG*` вне `GameFacade/` роняет сборку, и обновление игры превращается в починку одного каталога.

Форк уже наполовину соответствует этой схеме: `FSBCProductionCalculator` — обычный C++-класс без `UObject`, чистая функция над POD-структурами, а мира касается единственный метод `SynchronizeRuntimeRecipes(UObject* WorldContext, …)`. Цена приведения — std-типы в `core/` вместо `FString`/`TArray` и конверсия на границе фасада.

## 3.3 Игровой процесс: транспорт до компаньона

**Решение изменено относительно 2.0-draft (ADR-017, отзывает ADR-012).** Редакция 2.0 поднимала в игровом процессе входящий MCP-слушатель на `127.0.0.1`. Теперь MCP-сервер живёт в компаньоне, а мод держит **одно исходящее соединение** к компаньону.

Причина — стоимость и риск, а не вкус. Входящий слушатель в игре означал написать на UE C++ HTTP/SSE-сервер, JSON-RPC, сессии и capability negotiation MCP, accept-loop вне GameThread и корректное закрытие при смене сохранения и выходе. Слушающий сокет в игровом процессе — ещё и самый вероятный источник зависаний на shutdown. Контрольный факт: FRM, который делает именно это, вендорит для своего сервера `ThirdParty/uWebSockets`, то есть серверная сторона в игровом процессе требует вендоринга стороннего сетевого стека.

Что даёт перенос:

- **Spike S2 и риск R-13 уходят с критического пути.** Редакция 2.0 сама называла это решение резервным планом для S2 (§13); теперь оно основное, и проверять нечего.
- Реализация MCP заменяется официальным TypeScript SDK (Apache-2.0).
- Валидация аргументов по JSON Schema выполняется в компаньоне дешёвыми средствами, а `Validator` мода валидирует повторно по живому каталогу. Защита в глубину не ослабевает: инвариант §3.2 описывает путь к мутации, а не расположение сокета.
- Исчезает требование токена и привязки к loopback для входящего порта (прежний §12.1): входящего порта нет.
- **Вместо двух протоколов в двух направлениях остаётся один транспорт.** Прежде мод был HTTP-клиентом для SSE Foreman и HTTP-сервером для MCP. Теперь это один канал: один reconnect с backoff, один handshake `apiVersion`, одно состояние «компаньон не поднят». Потоковый ответ чата идёт тем же каналом, и отдельный SSE-клиент на C++ не нужен.

Требования к транспорту: работа вне GameThread; любое обращение к игровому состоянию — через передачу задания в GameThread и снапшот-ответ; запрет блокирующих вызовов в GameThread сохраняется полностью (§12).

**Новая непроверенная позиция.** Доступность движковых модулей `HTTP` и `WebSockets` моду Satisfactory в шиповой сборке не подтверждена. Это **Spike S2 в новой формулировке** и он на критическом пути v1.0. Fallback — вендорить клиентскую библиотеку (IXWebSocket, BSD-3-Clause), что существенно дешевле серверной стороны, но добавляет зависимость, у которой мейнтейнер публично ищет себе замену. Риск R-18.

## 3.4 Компаньон (локально)

**Решение изменено относительно 2.0-draft (ADR-020, уточняет ADR-004).** Редакция 2.0 утверждала, что сайдкар появляется только в v1.3 для STT/TTS. Одновременно §4 требовала установить Foreman с его БД на машину игрока уже в v1.0, а §4.1 и ADR-015 делали установщик, который его поднимает, блокирующим требованием релиза. То есть локальный неигровой процесс в v1.0 существовал, и мы владели его упаковкой, запуском, супервизией и версионированием, но называли его чужим компонентом. Эта фикция стоила ясности проектирования: пока компонента «нет», в него нельзя положить ничего полезного — в частности MCP-сервер.

Компонент называется прямо: **компаньон — наш процесс, внутри которого запускается vanilla Foreman.** Состав в v1.0:

| Часть | Роль | Готовое решение |
|---|---|---|
| MCP-сервер | Предоставляет Foreman инструменты (§7.1) и проксирует их в игру | MCP TypeScript SDK, Apache-2.0 |
| Терминатор транспорта | Единственный канал к моду; оба направления завершаются здесь | §3.3 |
| Валидация по схемам | Проверка аргументов инструментов до передачи в мод | `contracts/*.schema.json` |
| Супервизия Foreman | Запуск, health, агрегация логов, проверка `apiVersion` | Node `child_process` |
| Режим fake-LLM | Проигрывание сценарных последовательностей tool-вызовов | своя работа (§13.1) |
| STT/TTS | v1.3 | sherpa-onnx, Apache-2.0 |

Foreman остаётся как есть: `ff-server`, собственная БД, chat-цикл, Work Orders, история. Не форкается. `sf-game-data-graph` **не используется для расчётов** — планирование выполняется в моде (§8.3); встроенные данные Foreman остаются только для справочных ответов вне подключённой игры.

Интерфейс: компаньон обращается к существующему `POST /api/playthroughs/:id/chat` и читает SSE-события `text`, `tool_use`, `work_order`, `done`, `error`, передавая их моду по транспорту §3.3. Foreman обращается к компаньону как к MCP-серверу. Всё на localhost.

## 4.1 Упаковка и установка

**Это главный UX-риск проекта, и в 1.0-draft его не было.** В одиночной игре игрок сам себе администратор. Требование «установите Docker и поднимите несколько контейнеров» ограничивает аудиторию мода сотнями человек вместо десятков тысяч.

Решение для v1.0: **один установщик**, поднимающий компаньон как упакованный исполняемый файл с собственным встроенным хранилищем, плюс обычная установка мода через SMM. Docker-compose допустим как альтернативный путь для тех, кто его предпочитает, но не как основной. Мод должен сам обнаруживать неподнятый компаньон и показывать внятное состояние, а не ошибку соединения.

**Уточнение инструментария относительно 2.0-draft, и оно ухудшает оценку.** Редакция 2.0 писала «packaged Node», подразумевая существующий общепринятый инструмент. Проверено 04.11.2026: **`vercel/pkg` заархивирован 13.01.2024 и использоваться не может.** Актуальные варианты:

| Вариант | Состояние | Замечание |
|---|---|---|
| **Node SEA** (`node --build-sea`) | Официальная функция Node, VFS для ассетов, ESM-точки входа, code cache | **Stability 1.1 — Active development.** Выбран основным, но статус означает возможные изменения API |
| `bun build --compile` | Рабочая альтернатива | Меняет рантайм, под которым работает Foreman |
| Документированный docker-путь | Всегда доступен | Явное предупреждение о сужении аудитории |

Следствие: **риск R-11 острее, чем записан в редакции 2.0**, потому что у выбранного инструмента статус «активная разработка», а не «стабильно». Spike S5 сохраняется как блокирующее требование релиза и получает явные fallback-варианты из таблицы выше.

Критерий приёмки упаковки: от скачивания до первого ответа помощника — без ручного редактирования конфигов, кроме ввода ключа LLM-провайдера.

## 4.2 Поведение в мультиплеерной сессии

Мод регистрирует новые классы акторов (терминал, предмет), поэтому в мультиплеере он принципиально требует установки у всех участников и на сервере — «client-only мод с размещаемым объектом» в MP невозможен. Промежуточного варианта нет, и это подтверждает решение §1.1.

Но в MP-сессии клиентский мод всё равно загрузится и начнёт считать себя авторитетным, давая десинк и краши. Поэтому в v1.0 обязательно:

1. Определение контекста при инициализации: если сессия не одиночная, мод не регистрирует строительный объект и не поднимает транспорт до компаньона.
2. Явное сообщение игроку с указанием причины, а не молчаливое бездействие.
3. Уже размещённые в одиночном сохранении терминалы не должны ломать загрузку, если сохранение впоследствии открыто в MP.

**Упрощение относительно 2.0-draft.** Пункт 1 почти целиком обеспечивается средствами платформы: Replication Policy у `AModSubsystem` — декларативная таблица сторон «Singleplayer / Host-and-play hosts / Dedicated Servers / MP Clients», и нужная сторонность выбирается настройкой, а не кодом (§2.3). Собственной работой остаются пункты 2 и 3.

**Наследство форка, требующее решения.** Satisfactory Build Calculator содержит `SBCRemoteCallObject` и заявляет поддержку listen-server. Его поведение в MP нужно либо осознанно использовать, либо осознанно отключить — молчаливое наследование чужой MP-логики при заявленной топологии «только одиночная игра» недопустимо. Это пункт приёмки форка, см. §13.

Это задача v1.0 и отдельный критерий приёмки (AC-10), а не «потом».

# 5. Модель данных: четыре базовых контракта

## 5.0 Схема — источник истины, проза — ссылка на неё

Раздела не было, и его отсутствие уже стоило проекту трёх дефектов. Редакция 2.0 сама зафиксировала, что в 1.0-draft текст §5.3 и пример расходились дважды (`layout` против `area`; поля темы и прав были в тексте и отсутствовали в примере), а текст §5.4 и пример §11.2 перечисляли разные наборы полей (`belts`/`pipes`/`power` плоско против вложенного `connections`, `naming` против `outputName`). **Три расхождения в одной ревизии, все найдены вручную.** Это единственный класс дефектов, наблюдавшийся в проекте эмпирически, и он структурный: пока нормативом является проза, а примеры пишутся руками, расхождение неизбежно.

Решение:

1. **Нормативный артефакт — `contracts/*.schema.json`.** Проза §5 описывает смысл и ссылается на схему, но не дублирует перечень полей.
2. **Примеры валидируются в CI** против схем (`ajv-cli`). Расхождение роняет сборку.
3. **Типы генерируются, а не пишутся:** TypeScript для компаньона — quicktype (Apache-2.0); для C++ либо кодоген, либо тест на паритет полей со схемой.
4. Схемы поставляются с модом через `RuntimeDependencies` с `StagedFileType.NonUFS` — приём, уже применённый в форке для его файлов данных.

Даже один пункт 2 закрывает весь класс дефектов целиком.

**Состав нормативных файлов** (`docs/contracts/`):

| Схема | Контракт | Пример |
|---|---|---|
| `catalog.schema.json` | `GameCatalog` (§5.1) | `catalog.example.json` |
| `plan.schema.json` | `ProductionPlan` (§5.2) | `plan.example.json` |
| `screen.schema.json` | `ScreenDefinition` (§5.3) | `screen.example.json` |
| `blueprint.schema.json` | `BlueprintRequest` (§5.4) | `blueprint.example.json` |
| `blueprint-preview.schema.json` | `PreviewResult` (§5.4) | `blueprint-preview.example.json` |

Схемы написаны в Draft 2020-12 и закрыты `additionalProperties: false` на каждом уровне: незнакомое поле от LLM — ошибка валидации, а не проигнорированный ключ. `CreateResult` схемы пока не имеет: его форма зависит от программного API Factory Spawner и фиксируется в v1.1 вместе со Spike S4.

## 5.1 `GameCatalog` (read-only)

Нормализованные сущности `Item`, `Recipe`, `Machine`, `Schematic`, `UnlockState`. Ключ — устойчивое игровое `className`; отображаемое имя и локализованная подпись хранятся отдельно. У рецепта: список ингредиентов/продуктов, длительность, производство в минуту, `producedIn`, `isAlternate`, `unlocked`. У машины: класс, семейство, энергопотребление, доступность для строительства, порты.

Источник истинности — **только текущий игровой процесс**. Прежнее разделение «FRM даёт перечень, SML даёт статус разблокировки» устранено. Инвариант «известный рецепт ≠ разблокированный в этом сохранении» поддерживается одним кодом, а не сверкой двух источников, и реализуется через `UModContentRegistry` плюс чтение статуса разблокировки (§8.1).

**Обновление:** полная сборка при загрузке сохранения и после изменения состава модов; инкрементальное обновление разблокировок по игровым событиям; версия каталога (`catalogRevision`) для инвалидации кэшей UI.

Нормативное перечисление полей — `contracts/catalog.schema.json` (§5.0). Признак `isVanilla` из `UModContentRegistry::IsRecipeVanilla` сохраняется в каталоге: он нужен, чтобы отличать модовый контент от игрового при генерации чертежей (§9.3).

## 5.2 `ProductionPlan`

Идентификатор, владелец (сохранение), версия, `catalogRevision`, целевой ресурс и расход/мин; список производственных групп (машина, рецепт, количество, частота), соединений (item, source group, target group, quantity/min, единицы), выбранных альтернативных рецептов, источников сырья, сводные показатели энергии и материалов, перечень предупреждений планировщика.

План — **вычисляемая модель**, а не рисунок. Таблица, граф и Foreman работают с одним объектом; отрисовка — только представление. План хранит `catalogRevision`, при котором был посчитан: при расхождении с текущим UI помечает план как требующий пересчёта, а не молча показывает устаревшие числа.

Нормативное перечисление полей — `contracts/plan.schema.json` (§5.0). Структура `groups[]` плюс `connections[]` — это DAG, а не дерево: именно она позволяет побочным продуктам и циклам выражаться без спецслучаев (§6.4, §8.3). Прогресс трекера строительства живёт в том же объекте, в `groups[].builtCount` (§6.7).

## 5.3 `ScreenDefinition`

Исправления относительно 1.0-draft: `layout` и `area` были несовместимы (`grid` с именованными значениями `left`/`right`/`bottom`), поля темы и прав присутствовали в тексте и отсутствовали в примере, `source` был неструктурированной строкой.

**Разделение схемы и рантайма относительно 2.0-draft.** Схема фиксируется в v1.0, рантайм переносится в v1.2. Причина: в v1.0 экраны **некому создавать**. Вкладка Screens по §6.3 сама относится к v1.2, AI-путь (`create_screen`, `assign_screen`) тоже. Редакция 2.0 требовала в v1.0 генерический рендерер по белому списку, библиотеку экранов, привязку `terminalId → screenId` и персистентный кэш `screenId + renderRevision` — то есть полный рантайм для отображения конфигураций, которые в этой версии невозможно составить.

| Что | v1.0 | v1.2 |
|---|---|---|
| Схема `contracts/screen.schema.json` | **Пишется, валидируется, замораживается** | не меняется |
| Экран терминала | **Один встроенный экран**, не составляемый игроком | генерический рендерер по белому списку |
| Библиотека экранов, привязка, `assign_screen` | нет | да |
| Кэш `screenId + renderRevision` (§10.1) | нет | да |

Правило единого контракта из §1.2 соблюдено: схема одна с самого начала, ручной и AI-путь не разъедутся. Отложен только рантайм.

Поля: `schemaVersion`, `id`, `scope`, `title`, `layout`, `theme`, `widgets[]`. Каждый виджет: `id`, `type`, `slot`, `source`, необязательные `options` и `refreshSec`. Нормативное перечисление — в `contracts/screen.schema.json` (§5.0).

- `scope` — `personal` | `terminal`. Значение `shared` удалено вместе с мультиплеером.
- `layout` — **перечисление пресетов** (`slots-1`, `slots-2`, `slots-3`, `hud-compact`), а не свободная сетка. Слоты именованные: `main`, `side`, `foot`. Перечисление вместо произвольной геометрии резко сокращает число невалидных состояний, которые может породить LLM. Свободная сетка — кандидат на v1.2 после накопления реальных экранов.
- `source` — структурированный объект `{"kind": "...", "id": "..."}`, где `kind` — перечисление (`plan`, `metric`, `work_orders`, `notes`, `static`). Валидируется не только синтаксически: `id` сверяется с живым каталогом метрик и существующими планами, иначе виджет отклоняется с указанием причины.
- `refreshSec` — необязательное; клиент **зажимает** значение в допустимый диапазон, а не отклоняет определение, и у тяжёлых источников есть нижний порог (§8.2).

Типы виджетов v1.0: `text`, `metric`, `table`, `timeseries`, `production_graph`, `notes`, `work_orders`. Тип `image` удалён — пайплайна изображений в v1.0 нет; вернётся вместе с пайплайном изображений в компаньоне, не ранее v1.2.

Клиент создаёт виджеты только из белого списка и отвергает незнакомые поля и типы. В JSON нет HTML, JS, Unreal class paths или сетевых URL.

**Правило, отложенное вместе с мультиплеером.** В 1.0-draft `notes` мог попасть на общий терминал, что было утечкой (бывший R-06). В одиночной игре ограничение не нужно, но его надо восстановить как жёсткое правило белого списка (`notes` недопустим при `scope=terminal`) одновременно с появлением MP. Зафиксировано в §15, ADR-005.

## 5.4 `BlueprintRequest`

Исправление относительно 1.0-draft: там текст §5.4 и пример §11.2 перечисляли разные поля (`belts`/`pipes`/`power` плоско против вложенного `connections`; `naming` против `outputName`). Нормативный набор — `contracts/blueprint.schema.json` (§5.0).

Поля: `schemaVersion`, `requestId`, `machineClass`, `recipeClass`, `count`, `layout`, `connections{belts,pipes,power}`, `outputName`. Поле `targetPlayer` удалено — адресат один.

- `requestId` обеспечивает идемпотентность повторного подтверждения.
- **Поля `clockPercent` и `clockApplied` удалены относительно 2.0-draft.** Редакция 2.0 вводила их парой, где `clockApplied=false` честно означало «значение учтено в расчёте, но в чертеже такт не выставлен», и помечала вопрос как уточняемый спайком v1.1. Контракт, который переносит нерешённый вопрос, тащит его дальше: в UI, в текст preview и в ожидания игрока. Решение: такт — понятие планировщика и живёт в `ProductionPlan.groups[].clockPercent` для расчёта `plannedRate`, а в `BlueprintRequest` его нет. Blueprint Builder прямо сообщает, что такт выставляется игроком после размещения чертежа. Если спайк v1.1 покажет, что генератор умеет выставлять такт, поле добавляется как необязательное — политика `schemaVersion` из §5.5 это допускает как аддитивное изменение. Вместе с полями удаляется код предупреждения `CLOCK_NOT_APPLIED`.

Отдельные `PreviewResult` и `CreateResult`. `PreviewResult` содержит `valid`, массивы `errors` и `warnings` с машиночитаемыми кодами, оценки входов/выходов, мощности и габаритов, предложение разбиения на модули. Код предупреждения `MANIFOLD_RAMP_UP` обязателен: у манифолда известен эффект разгона и голодающей последней машины, и preview должен об этом сообщать, а не только считать суммарный поток.

Порядок: dry-run и валидация → отдельное подтверждение игрока → исполнение через authority-слой.

## 5.5 Версионирование и совместимость

В 1.0-draft `schemaVersion` был у сущностей, но согласования версий компонентов не было. Теперь:

- У мода и компаньона единый `apiVersion`. Мод присылает свой при handshake транспорта (§3.3); при несовпадении мажорной версии AI-функции отключаются с **видимым игроку сообщением**, ручные продолжают работать.
- Мод и компаньон поставляются одним установщиком с согласованными версиями, чтобы пользователь не смешивал сборки.
- У сущностей сохраняется `schemaVersion` и миграции при загрузке локальных файлов.
- **Границы механизма.** Поскольку мод и компаньон поставляются одной сборкой, проверка `apiVersion` срабатывает только на неподдерживаемых смешениях. Проверка остаётся — она дешёвая и даёт внятное сообщение вместо непонятного сбоя, — но **миграционная машинерия под `apiVersion` не строится**. Миграции нужны только для `schemaVersion` локальных файлов, где расхождение версий ожидаемо и нормально.
- **Аддитивные изменения** (новое необязательное поле) не повышают мажорную версию. Именно это позволяет вернуть `clockPercent` в `BlueprintRequest`, если спайк v1.1 покажет применимость такта (§5.4).

# 6. Интерфейсы игрока и UX

## 6.1 AI Terminal

Открывается по E; показывает тот же UI-контроллер, что и переносное устройство, с пресетом полной сетки. У физического экрана два режима: лёгкий world-display (render target, обновляется по изменению) и полный интерактивный UMG при открытии. Настройка терминала хранится как ссылка `terminalId → screenId`, не как копия разметки.

Открытый вопрос, перенесённый из 1.0-draft: требует ли терминал питания или декоративен. Решение влияет на игровой баланс, не на архитектуру.

## 6.2 AI Assistant (v1.1)

**Перенесено из v1.0 относительно 2.0-draft.** Терминал даёт всю ценность продукта в v1.0, а экипируемый предмет добавляет отдельную поверхность: actor ручного слота, рецепт крафта, машину состояний «выбран в руке», компактный пресет и привязку видимости HUD к активному слоту. Поскольку критерий активности HUD по §6.5 привязан именно к этому предмету, FR-02 и FR-07 переносятся вместе. Контроллер и пресеты при этом проектируются в v1.0 так, чтобы вторая поверхность подключалась без переделки (ADR-001).

Крафтится обычным игровым способом и занимает стандартный ручной слот. ЛКМ открывает интерфейс, горячая клавиша переключает HUD. Критерий активности — «в активном слоте/выбран в руке», а не наличие в инвентаре: это даёт однозначное включение и скрытие HUD при переключении оборудования. Не зависеть от PowerSuit или сторонних расширений слотов.

**Layout-пресеты по поверхности.** У терминала (большой экран, мышь, игрок стоит) и у экипировки (быстрый доступ, возможно на ходу) разная эргономика, и буквально один и тот же экран плохо подходит обоим. Контроллер и набор виджетов общие, раскладка выбирается пресетом: `slots-3` для терминала, `hud-compact` или `slots-1` для экипировки. Поле `layout` в `ScreenDefinition` это и обеспечивает.

## 6.4 Представление производственного плана

**Решение изменено относительно 2.0-draft (ADR-016, заменяет ADR-007).** Редакция 2.0 отложила интерактивный граф в v1.4 и приняла собственное read-only представление базовым путём. Основанием была оценка одного конкретного предложения — извлечь граф-виджет из UMG-дерева Satisfactory Build Calculator. Форк того же мода как базы проекта меняет вывод: **интерактивный граф приходит в v1.0, а не в v1.4,** версия v1.4 упразднена, риск R-02 закрыт.

В v1.0 два уровня:

1. **Таблица** — авторитетное представление: группы машин, количество, такт, входы/выходы в единицах в минуту, сырьё, суммарная мощность, предупреждения. Вся ценность AC-03 («какие машины, сколько, сколько энергии») достигается здесь. Реализуется штатными `UListView`/`UTileView`.
2. **Граф, интерактивный** — приходит с форком: связный граф карточек с цветовыми акцентами по типу машины, пан перетаскиванием левой кнопкой, зум колесом вокруг курсора, reset-view, фокус на выбранной карточке, детальный и компактный вид карточек, разворачивание и сворачивание.

**Что остаётся собственной работой, и это главная UI-задача v1.0.** Виджет форка отрисовывает **дерево**: `FSBCProductionNode` содержит `TArray<TSharedPtr<FSBCProductionNode>> Children`, а рекурсия обрывается множеством `Ancestry`. Наша модель `ProductionPlan` — честный **DAG** с `groups[]` и `connections[]`, где общие промежуточные продукты слиты в одну группу, а не продублированы по ветвям.

| Путь | Стоимость | Последствие |
|---|---|---|
| Проекция DAG в дерево для отрисовки | низкая | Теряется слияние узлов, то есть теряется смысл перехода к DAG |
| Адаптация виджета под DAG | основная работа | Правильный путь; принят |

Цена второго пути **не подтверждена** и выносится в спайк: требуется прочитать `SBCCalculatorWidget.cpp` целиком до окончательного решения о форке. Это единственная непроверенная цена ADR-016 (§13).

Производственная цепочка — DAG из нескольких десятков узлов с естественными уровнями (сырьё → промежуточные → целевой), поэтому раскладка предсказуема и не требует внешнего движка. Graphviz не нужен ни в одной версии.

## 6.5 HUD (v1.1)

**Перенесено из v1.0 вместе с FR-02.** Критерий активности HUD — «устройство в активном слоте», поэтому HUD без экипируемого предмета не имеет условия включения.

Набор маленьких прозрачных `ScreenWidget`, а не второй независимый UI: текстовые подсказки, задачи, показатели мощности, мини-представление плана, временные графики, уведомления. Готовые профили `minimal`, `production`, `power`, `work-order`; виджеты включаются, скрываются и переставляются. Управление — назначаемыми клавишами через SML Mod Key Bind Registry (§2.3), а с v1.2 ещё и теми же Screen-инструментами. HUD локален игроку.

**Что уже есть в v1.0.** Форк приносит работающий компактный HUD с переключением по клавише и перепривязкой клавиш из конфигурационной страницы мода. То есть в v1.0 код HUD существует и работает; в v1.1 добавляются профили и привязка к активному слоту. Это снижает стоимость переноса почти до нуля и было причиной согласиться на перенос.

## 6.6 Экран в мире

Решение упрощено относительно 1.0-draft. Прежняя схема (внешний рендер PNG, доставка клиенту по подписанному адресу, запрет на создание текстур на DS) существовала из-за headless-сервера. В одиночной игре композиция рендерится в **render target** в том же процессе и применяется к материалу меша терминала — штатный приём UE, без внешнего сервиса и без пайплайна изображений.

Обновление — по изменению содержимого (`renderRevision`), не покадрово. Никаких высокочастотных стримов. Подход Image Screens остаётся референсом на случай нетривиальностей с материалом, но зависимостью не является.

В v1.0 на экран выводится один встроенный экран, а не составляемая игроком композиция (§5.3). Персистентный кэш `screenId + renderRevision` переносится в v1.2 вместе с рантаймом экранов (§10.1).

## 6.7 Трекер строительства (FR-11)

Раздела не было: функция приходит с форком и в архитектуре v2.0 отсутствовала. Трекер связывает узлы `ProductionPlan` с фактически построенными в мире машинами:

- Совпадение считается по классу машины, рецепту, числу Power Shards и числу Somersloops одновременно.
- Демонтаж связанной машины уменьшает прогресс.
- Смена рецепта или модификаторов приводит к переназначению.
- Существующие постройки игнорируются до явного линкования игроком — это снимает неоднозначность, когда под критерий подходит несколько машин.
- При неоднозначном автоматическом совпадении система ждёт решения игрока, а не выбирает произвольно.

**Что нужно доработать.** В форке цели живут в volatile session memory и в сохранение не пишутся. Персистентность по ключу сохранения добавляется нами (§10) — иначе трекер противоречит AC-07.

Функция хорошо ложится в продукт: она соединяет расчёт с фактическим состоянием фабрики и даёт `actualRate` естественную точку привязки к плану (§8.4).

# 7. Граница доверия LLM

Эта граница — главная причина, по которой authority-слой сохраняется в одиночной игре. Отказ от мультиплеера снял угрозы со стороны других игроков, но не изменил ни одной угрозы со стороны модели.

## 7.1 Инструменты

Инструменты объявляет **компаньон** через MCP-сервер и проксирует их в мод по транспорту §3.3; реализация остаётся в моде, где лежат данные и авторитет. У каждого инструмента — JSON Schema из `contracts/`, проверка прав и лимиты размера/частоты.

**Двухуровневая валидация.** Компаньон проверяет аргументы по схеме до передачи в игру; `Validator` мода проверяет повторно по живому каталогу. Это не дублирование, а защита в глубину: первый уровень отсекает синтаксический мусор дешёвыми средствами вне игрового процесса, второй отвечает за семантику и является обязательным — он один не может быть обойдён, даже если компаньон скомпрометирован.

| Инструмент | Версия | Мутирует мир |
|---|---|---|
| `get_catalog`, `query_metric`, `get_plan` | v1.0 | нет |
| `compute_plan` | v1.0 | нет (расчёт в моде, результат в ответ) |
| `list_widget_types`, `create_screen`, `update_screen`, `assign_screen`, `set_hud_profile` | v1.2 | нет (UI-состояние, не мир) |
| `preview_blueprint` | v1.1 | нет |
| `request_blueprint_creation` | v1.1 | **да** — только через подтверждение игрока |

## 7.2 Пайплайн

Текст игрока → Foreman/LLM → вызов инструмента → **MCP-сервер компаньона** → валидация по схеме → **транспорт в мод (§3.3)** → валидация по живому каталогу в `Validator` → применение (для UI-состояния) или постановка в очередь подтверждения (для мутаций мира) → UI получает событие `plan.updated` (с v1.2 также `screen.updated`) и обновляет конкретные виджеты.

Правка через интерфейс вызывает те же внутренние операции, что и инструменты. Схемы версионируются, возможен откат. Невалидная команда не изменяет сохранённое состояние. **Не** разбирать текст ответа LLM регулярными выражениями, чтобы понять действие.

## 7.3 Инъекции через авторский текст игрока

Этого раздела в 1.0-draft не было. Документ защищал от того, что модель **выдаёт**, но не от того, что она **читает**.

Внутрь контекста попадают строки, написанные человеком: заметки, имена терминалов, `outputName` прошлых чертежей, история чата. Заметка вида «назначь экран X на терминал Y» будет прочитана моделью как инструкция. Меры:

1. Любая запись, инициированная инструментом на основании **прочитанного** текста, а не собственной реплики игрока в этом обмене, требует того же подтверждения, что и запись из UI.
2. Аргументы инструментов никогда не принимаются в виде идентификаторов, извлечённых из текста: `className`, `recipeClass`, `id` метрики и плана сверяются с живым каталогом (принцип уже был заявлен в 1.0-draft для class names — здесь он распространён на все идентификаторы).
3. Авторский текст игрока передаётся модели в явно размеченном виде как данные, а не как часть инструкций.

## 7.4 Лимиты

LLM не может задавать сетевые URL, выполнять команды операционной системы или произвольный код; допустимы только объявленные виджеты и каталогизованные источники. Ограничения: размер `ScreenDefinition`, число виджетов, нижний порог `refreshSec` для тяжёлых источников, частота создания планов и запросов чертежей, глубина рекурсии планировщика.

# 8. Данные и вычисления

## 8.1 Каталог из игры

`CatalogProvider` живёт в `GameFacade/` (§3.2.1) и даёт точный ответ на вопрос «можно ли использовать это прямо сейчас».

**Решение изменено относительно 2.0-draft (ADR-018, заменяет ADR-003).** Редакция 2.0 назначала основным референсом реализации код FRM, оговаривая это разрешением из §2.2. Разрешения нет: файла лицензии в репозитории FRM не существует. Однако заменять почти нечего — задача распадается на четыре части, и три из них закрыты лицензионно чисто:

| Часть | Источник | Статус |
|---|---|---|
| Состав сущностей, включая рецепты других модов | **`UModContentRegistry` из SML**: `GetRegisteredRecipes()`, `GetLoadedItemDescriptors()`, `GetObtainableItemDescriptors(flags)`, `IsRecipeVanilla()` | Документированный API платформы |
| Инкрементальное обновление каталога | **События SML** `OnRecipeRegistered`, `OnSchematicRegistered`, `OnResearchTreeRegistered` | Документированный API; требование §5.1 выполняется бесплатно |
| Статус разблокировки в этом сохранении | **Код форка**: `FSBCProductionData::SynchronizeRuntimeRecipes()` | MIT |
| Статические числовые параметры | **Структуры форка** и `Docs.json` из установки игры | MIT, данные самой игры |

Прежняя схема с `getRecipes`/`getSchematics` из FRM устранена, и вместе с ней — необходимость сверять два источника. Бывший R-03 (`getRecipes` возвращает и закрытые рецепты) закрыт исчезновением второго источника.

**Что приходит с форком помимо самого чтения.** Выверенные доменные константы, которых в редакции 2.0 не было вовсе: кривая оверклока (`PowerExponent = 1.321929`), экспонента Somersloop (`BoostPowerExponent = 2.0`), число слотов сломов, диапазоны переменного потребления, генераторы с диапазоном выработки, доля grid boost от alien power augmenter, лимиты по числу точек добычи, байпродукты в составе рецепта. Это недели выверки, и они невидимы в архитектурном документе, пока не начнёшь сверять числа с игрой.

**Что остаётся непокрытым.** Телеметрия (§8.2). Это единственный модуль без лицензионно чистого референса, и риск R-12 закрыт именно потому, что он сузился до него одного.

## 8.2 Телеметрия

`TelemetrySampler` собирает фактические значения из игровых подсистем: производство ресурса/мин, потребление и генерацию электричества, активность машин, суммарные входы/выходы по выбранной группе. Значения несут `source=live` либо `source=planned`, временную метку, единицу, точность и scope.

**Это единственный модуль проекта, который пишется полностью с нуля без референса.** Поиск готовых решений (`MODULES.md`, B4) дал отрицательный результат: FRM решает задачу технически, но исключён лицензионно (§2.2), а пригодного аналога под MIT или Apache-2.0 не найдено. Следствия для планирования: модуль получает отдельную оценку трудозатрат, его объём сознательно сужается до дешёвых метрик, и именно он является содержанием спайка по бюджету GameThread. Правило fallback из §13 — сузить набор метрик, а не отложить модуль: без телеметрии не выполняются FR-04 и AC-04.

**Нагрузка на GameThread остаётся риском и меняет только форму.** HTTP-раунд-трипа больше нет, но тяжёлая агрегация по подсистемам в игровом потоке каждый тик просадит FPS так же надёжно, как частый опрос FRM. Правила:

- Сбор по расписанию, не по запросу UI; UI читает последний снапшот.
- В GameThread выполняется только снятие значений; агрегация, расчёт производных и сглаживание — на воркере.
- Предлагаемые интервалы до измерения: мощность 2–5 с, агрегаты фабрик 5–15 с, каталог только по событию изменения.
- Кольцевой буфер временных рядов в памяти мода, персистится вместе с состоянием.
- **Частота обновления виджета не выше частоты данных.** В 1.0-draft HUD обновлялся «1–2 раза/с» при данных раз в 2–5 с, то есть перерисовывал интерполяции устаревших чисел. Виджет показывает значение с метаданными свежести и перерисовывается при поступлении нового снапшота.

## 8.3 Планировщик в моде

Вход: целевой предмет, расход/мин, выбранные альтернативные рецепты, границы сырья. Выход: `ProductionPlan` (§5.2). Модуль живёт в `core/` и не зависит от Unreal (§3.2.1).

**Решение изменено относительно 2.0-draft (ADR-019).** Редакция 2.0 предлагала три пути в коде: точный обход деревьев, отдельная обработка побочных продуктов с явным стоком и отдельный путь для циклов, где игрок обязан закрепить одну из ставок, после чего система разрешается как малая линейная система. Это три ветки плюс отдельный UI-флоу, а риск R-14 оставался действующим.

**Общая постановка — один путь.** Неизвестные — интенсивности выбранных рецептов; для каждого предмета записывается балансовое уравнение; решается система `A·x = d` при `x ≥ 0`, где `A` — матрица стехиометрии. Деревья, побочные продукты и циклы (переработанные пластик и резина) выпадают из одного и того же решения, потому что цикл в матрице — это просто записи в обе стороны. «Нет решения» и «недоопределено» становятся диагностируемыми состояниями, а не специальными случаями в коде.

Это работает именно потому, что **альтернативные рецепты выбирает игрок** (`selectedAlternates`, §5.2): при фиксированном наборе рецептов задача линейна. Автоматический подбор альтернатив и минимизация сырья — это уже LP или MILP, и они справедливо вне объёма v1.x; если когда-нибудь понадобятся, постановка не меняется, меняется только решатель (HiGHS, MIT).

**Оговорка, заложенная сразу.** Решение линейной системы может дать отрицательные интенсивности, то есть «запустить рецепт назад», что физически бессмысленно. Поэтому требуется либо неотрицательный метод наименьших квадратов, либо явный детект отрицательных значений с честным диагнозом «система неразрешима при заданных ограничениях». Второе дешевле и для v1.0 достаточно: предупреждение в `warnings` плана с кодом `SYSTEM_INFEASIBLE` и перечнем рецептов, получивших отрицательную интенсивность, в `scope`. Прежний код `RECIPE_LOOP_NEEDS_PIN` отозван вместе с UI закрепления ставки: циклы больше не требуют вмешательства игрока.

**Инструментарий.** Eigen (MPL-2.0). Его доступность в modding SDK не подтверждена; fallback — гаусс с частичным выбором ведущего элемента, около восьмидесяти строк для систем в несколько сотен неизвестных, что всё равно меньше, чем три специальных случая и UI закрепления ставки.

Последствие для рисков: **R-14 закрывается, а не откладывается.**

**Что приходит с форком и что заменяется.** `FSBCProductionCalculator::Calculate()` уже считает число машин, сырьё, мощность и выработку с учётом сломов и Somersloop — эта арифметика и её константы сохраняются. Заменяется способ обхода: рекурсия `BuildNode` с обрывом по множеству `Ancestry` уступает место построению матрицы. Структуры каталога (`FSBCProductionData`) остаются.

Движок `sf-game-data-graph` Foreman для расчётов не используется. Это закрывает бывший R-04 (расхождение live-данных и статического графа) и обеспечивает FR-10: планирование работает при остановленном компаньоне.

## 8.4 `plannedRate` против `actualRate`

Две независимые величины: `plannedRate` = рецепт × число машин × такт; `actualRate` = наблюдаемое в игре. В таблице, графе и HUD не смешивать без подписи. Дефициты и нарушения пропускной способности вычисляет планировщик; LLM только объясняет результат.

# 9. Создание Blueprint (v1.1)

## 9.1 Ядро

Используется проверенное ядро Factory Spawner: `FBuildPlanGenerator::Generate(TArray<FFactoryCommandToken>)`. Чатовый ввод заменяется программным API, компоновка `single_row` ограничивается известными типами машин. Существующая реализация создаёт splitter/merger, pipe cross, belt/lift, power wire и пишет Blueprint через игровой subsystem.

**Главное упрощение относительно 1.0-draft.** Бывший R-01 состоял в том, что генератор опирается на `FirstPlayerController` и пишет чертёж в текущий subsystem, а на Dedicated Server локального игрока нет. В одиночной игре `FirstPlayerController` — это и есть игрок, и Factory Spawner именно так и работает сегодня. Spike D прежней редакции из «может опрокинуть архитектуру» превращается в обычную задачу интеграции.

## 9.2 Изменения в адаптированном ядре

Экспорт/обёртка программного API; генерация уникального имени, не перезаписывающего чертежи `FactorySpawner`; валидация количества, класса, рецепта и разблокировки; проверка габаритов; расчёт нагрузки по лентам и трубам с предупреждением `MANIFOLD_RAMP_UP`; корректная обработка ошибок без частично связанных объектов; выяснение, применим ли `clockPercent` в самом чертеже (§5.4).

## 9.3 Ограничения v1.1

Только шаблонные ряды; ввод и вывод в отдельных коллекторах; раздельные входы для нескольких ингредиентов; питание; предлагаемое разбиение превышающего размер ряда на модули. Распределение напора в трубах и идеальный баланс сложных заводов не гарантируются: игрок видит ограничения и решает вручную.

# 10. Хранение и жизненный цикл

Решение изменено относительно 1.0-draft. Прежде `ProductionPlan` и `ScreenDefinition` лежали в БД Game Bridge. Поскольку Bridge удалён, а FR-10 требует работы без компаньона, состояние мода хранится **локально у мода**: хранение в БД компаньона означало бы, что сохранённые планы недоступны при остановленном Foreman (ADR-014).

**Уточнение относительно 2.0-draft.** Часть механизма предоставляет платформа: `AModSubsystem` из SML умеет сохраняться в save-файл (§2.3). Поэтому разделение «что в save, а что в локальные файлы мода» становится выбором, а не самостоятельной реализацией: в save уходит то, что логически принадлежит миру, в локальные файлы — то, что к миру не привязано либо слишком объёмно для save.

| Где | Что хранится | Не хранить |
|---|---|---|
| Локальные файлы мода (ключ — сохранение) | `ProductionPlan`, заметки, кольцевые буферы телеметрии; с v1.1 HUD-профили; с v1.2 `ScreenDefinition`, привязки терминалов и кэш отрендеренных экранов | ключи LLM-провайдера в открытом виде |
| `AModSubsystem` в save | состояние трекера строительства (§6.7), связи узлов плана с построенными машинами | длинные JSON-схемы, переписка |
| Foreman DB | аккаунт, playthrough, переписка, Work Orders | игровые значения каждого тика, копии каталога |
| Satisfactory save | установленный терминал, его идентификатор и игровые параметры объекта; с v1.2 `screenId` | длинные JSON-схемы, токены, переписка |
| Конфиг через SML Mod Configuration | hotkeys, аудио, адрес компаньона | — |

Порядок восстановления: загрузка сохранения → сборка каталога → чтение локального состояния по ключу сохранения → восстановление трекера → подключение к компаньону, если он поднят → доступность AI-функций. С v1.2 между восстановлением состояния и подключением добавляется отрисовка экранов из кэша.

Безопасное удаление: терминал пропадает из save, но его `ScreenDefinition` не удаляется автоматически до истечения срока хранения, чтобы не терять дизайн. Удаление мода не должно повреждать сохранение.

## 10.1 Кэш отрендеренного экрана (v1.2)

§14 редакции 1.0-draft обещала «физический экран показывает последнюю PNG», но клиентское хранение этого изображения нигде не описывалось, то есть обещание деградации было невыполнимым. Механизм: кэш по ключу `screenId + renderRevision`, персистентный, читается до подключения компаньона.

**Перенесено в v1.2 вместе с рантаймом экранов (§5.3).** В v1.0 терминал выводит один встроенный экран, который рендерится из локального состояния мода и не требует отдельного кэша: данные для него и так доступны без компаньона, поэтому кэш решал бы несуществующую проблему. Терминал, у которого содержимого ещё не было, показывает документированное пустое состояние, а не ошибку — это требование сохраняется в v1.0.

# 11. Сбои, ограничения производительности и деградация

| Сбой | Ожидаемое поведение |
|---|---|
| Компаньон/Foreman не поднят | Работают все ручные вкладки, планировщик, метрики, трекер строительства; AI-вкладки показывают состояние «не подключено» с подсказкой |
| Транспорт оборвался в середине ответа | Reconnect с backoff; частичный ответ помечается прерванным, состояние не меняется (§3.3) |
| Несовпадение `apiVersion` | AI-функции отключены с видимым сообщением; ручные работают |
| LLM-провайдер недоступен | Foreman отвечает ошибкой, чат показывает причину, остальное работает |
| STT/TTS недоступен (v1.3) | Текстовый чат и управление клавишами сохраняются |
| Ошибка Blueprint (v1.1) | Не создавать частично связанные объекты; показывать причину; сохранять запрос для исправления |
| Цикл рецептов в плане | Решается наравне с деревом: цикл в матрице — записи в обе стороны, вмешательство игрока не требуется (§8.3, ADR-019) |
| Система неразрешима при заданных ограничениях | Предупреждение `SYSTEM_INFEASIBLE` с перечнем рецептов, получивших отрицательную интенсивность, а не молчаливый неверный результат |
| Мультиплеерная сессия | Мод инертен, сообщение игроку, сессия стабильна (§4.2) |
| Обновление игры сломало SML | Мод не загружается средствами SML, сохранение не повреждается |

**Начальные, проверяемые нагрузочные цели** (не гарантии до измерений): открытие кэшированного UI без обращения к компаньону; перерисовка виджета по поступлению снапшота, не по таймеру; снятие телеметрии в GameThread в пределах бюджета доли миллисекунды на выборку, агрегация вне GameThread; экран в мире обновляется по `renderRevision`; десятки размещённых терминалов не создают линейного роста затрат в кадре (неактивные терминалы не рендерят). Перед релизом профилировать GameThread и GPU.

# 12. Доступы и безопасность

Мультиплеерные пункты 1.0-draft (pairing-токены с привязкой к `worldId`/`playerId`, ACL терминалов, роли owner/editor/viewer, запрет публикации портов) удалены вместе с топологией. Пункты, относящиеся к изоляции LLM, сохранены полностью — они не зависели от мультиплеера.

1. **У мода нет входящего порта.** Пункт редакции 2.0 о привязке MCP-эндпойнта к loopback и токене из локального конфига снят вместе с самим эндпойнтом (§3.3, ADR-017): слушателя нет, поэтому произвольный локальный процесс не может обратиться к игре. Входящий порт есть у компаньона, он привязан к loopback, и MCP-сервер принимает соединения только от локального Foreman.
2. Ключ LLM-провайдера хранится у компаньона, не в игровых файлах и не в сохранении.
3. Все внешние ответы валидируются JSON Schema; действуют лимиты размера и частоты (§7.4).
4. Операции, изменяющие мир, проходят через authority-слой и требуют явного подтверждения. Идемпотентность через `requestId`.
5. Идентификаторы в аргументах инструментов сверяются с живым каталогом, а не принимаются из текста (§7.3).
6. Запрещены блокирующие сетевые вызовы в GameThread и зависимость игрового тика от внешнего сервиса.
7. Состояние привязано к ключу сохранения: план из другого сохранения не применяется молча.

## 13.1 Среда разработки

Раздела не было, и это пробел: «упрощение разработки» живёт в основном здесь. Редакция 2.0 не отвечала на вопросы, как запустить планировщик без игры, как протестировать инструменты без LLM, как проверить деградацию и сколько длится цикл «правка → результат».

| Средство | Назначение |
|---|---|
| `core/` с хостовыми юнит-тестами | Решатель, диагностика, раскладка и работа со схемами тестируются за секунды без запуска игры (§3.2.1) |
| `ficsitai-cli` | Вызывает те же tool-операции против фикстурного каталога. Инструменты тестируются без игры и без LLM |
| Фикстурный каталог | Снимок `GameCatalog` в файле; делает тесты планировщика детерминированными |
| Тестовое сохранение в репозитории | Известное состояние фабрики; без него телеметрию (§8.2) нечем проверять |
| **Режим fake-LLM в компаньоне** | Проигрывает сценарные последовательности tool-вызовов. Делает работу над AI-контуром детерминированной, не требующей ни модели, ни токенов, ни ожидания ответа |
| CI-инварианты | Валидация примеров против схем (`ajv-cli`); правило «`AFG*`/`UFG*` только в `GameFacade/`»; правило инварианта §3.2 |

**Заявленная цель.** Цикл итерации для логики вне Unreal — секунды (внесено в нефункциональные цели §1.1). Для кода, требующего запуска игры, цикл измеряется минутами, и это причина выносить в `core/` всё, что можно вынести.

# 14. Acceptance criteria для v1.0

**AC-01.** Игрок размещает AI Terminal, нажимает E и открывает полноэкранную панель. Повторное открытие восстанавливает последнее состояние.

**AC-02 перенесён в v1.1** вместе с FR-02 и FR-07: экипируемый предмет, компактный пресет и привязка видимости HUD к активному слоту.

**AC-03.** Без компаньона игрок открывает Planning, выбирает рецепт и альтернативу **из действительно разблокированных в этом сохранении**, задаёт расход/мин и получает таблицу машин/потоков/сырья, суммарную мощность и представление плана с паном, зумом и выбором узла. Общие промежуточные продукты показаны **одной группой**, а не продублированы по ветвям. Цепочка с циклом рецептов (переработанный пластик и резина) считается без требования закрепить ставку; неразрешимая система даёт предупреждение с машиночитаемым кодом, а не молчаливо неверный результат.

**AC-04.** Фактические ресурсы/мин и мощность отображаются с меткой `live` и временем актуальности; плановые значения отмечены `planned`. Временные графики работают минимум на одном выбранном контуре. Частота перерисовки не превышает частоту поступления данных.

**AC-05.** Текстовый диалог с Foreman работает внутри игрового UI: потоковый ответ, отмена, история, видимые Work Orders. Инструменты чтения (`get_catalog`, `query_metric`, `compute_plan`) вызываются моделью и возвращают данные текущего сохранения.

**AC-06 перенесён в v1.1** вместе с HUD-профилями.

**AC-07.** После перезапуска игры планы, заметки и состояние трекера строительства восстанавливаются по ключу сохранения. Открытие другого сохранения не подмешивает чужое состояние.

**AC-08.** Экран терминала показывает актуальное содержимое и обновляется по изменению, а не покадрово. Терминал без содержимого показывает документированное пустое состояние. Требование чтения из персистентного кэша перенесено в v1.2 вместе с рантаймом экранов (§10.1).

**AC-09.** При остановленном компаньоне работают все ручные вкладки, планировщик и трекер, AI-вкладки показывают состояние «не подключено», метки устаревших данных корректны, игра не падает и не фризит.

**AC-10.** При открытии мультиплеерной сессии мод инертен: объект не регистрируется, транспорт до компаньона не поднимается, унаследованный от форка путь удалённых вызовов не активируется, игрок видит внятное сообщение, сессия стабильна. Сохранение с размещённым терминалом открывается в MP без повреждений.

**AC-11.** Профилирование подтверждает соблюдение бюджета GameThread (§11) при десятках размещённых терминалов и активном сборе телеметрии.

**AC-12.** Установка: от скачивания до первого ответа помощника без ручного редактирования конфигов, кроме ввода ключа LLM-провайдера.

**AC-13.** Трекер строительства: игрок строит машину, соответствующую узлу плана по классу, рецепту и модификаторам, и прогресс узла увеличивается; демонтаж уменьшает его; состояние переживает перезапуск игры (FR-11, §6.7).

**AC-14.** CI-инварианты выполняются: примеры контрактов валидны против схем, типы `AFG*`/`UFG*` не встречаются вне `GameFacade/`, вызовы мутирующего игрового API не встречаются в обработчиках внешних сообщений (§3.2, §13.1).

# 17. Что изменилось

## 17.1 Относительно 2.0-draft

Сводка для ревью. Причина большинства изменений — три находки: у Satisfactory Build Calculator есть лицензия MIT и готовый интерактивный граф, у Ficsit Remote Monitoring лицензии нет вовсе, а SML предоставляет больше, чем предполагала прежняя редакция.

**Развороты — решения, прямо противоположные принятым в 2.0-draft:**

- **Мод строится форком Satisfactory Build Calculator, а не с нуля** (ADR-016 заменяет ADR-007). Прежняя редакция оценивала не ту постановку: «извлечь из чужого проекта виджет графа» действительно дороже, чем написать своё, и ADR-007 был верным ответом на этот вопрос. Форк целиком — другой вопрос: наследование модели данных перестаёт быть издержкой и становится целью. Вместе с графом приходят калькулятор, чтение каталога, силовая модель, HUD, хоткеи и локализация.
- **Версия v1.4 упразднена.** Интерактивный граф — то единственное, что в ней было, — приходит в v1.0 вместе с форком. R-02 закрыт.
- **MCP-сервер переехал из игрового процесса в компаньон** (ADR-017 отзывает ADR-012). Мод держит один исходящий канал и не слушает ни одного порта. Fallback редакции 2.0 стал основным решением, R-13 закрыт до реализации, а не после spike'а.
- **FRM исключён из источников кода** (ADR-018 заменяет ADR-003). Проверка репозитория 04.11.2026: файла лицензии нет; раздел README «Permissions Granted» разрешает обращаться к API, но не брать код. R-12 закрыт отрицательно, замены найдены: состав каталога — `UModContentRegistry` из SML, разблокировки и числовые параметры — MIT-код форка.
- **Планировщик решает линейную систему, а не обходит дерево** (ADR-019). Байпродукты, циклы и несколько конечных продуктов перестали быть тремя специальными случаями; R-14 закрыт постановкой задачи, а не UI закрепления ставки.
- **Компаньон — наш компонент v1.0** (ADR-020 уточняет ADR-004), а не «внешний сервис, который игрок как-нибудь поднимет». Мы владеем его упаковкой, запуском и супервизией; vanilla Foreman работает внутри.

**Добавлено:**

- **§2.3 «Что предоставляет сама платформа»** и правило ADR-023. Четыре модуля, которые прежняя редакция планировала писать самим, SML уже закрывает: конфигурация с генерируемым UI, реестр хоткеев, персистентность через `AModSubsystem`, сторонность сессии через Replication Policy.
- **§3.2.1 разделение на `core/` и `GameFacade/`** (ADR-021) — первая конкретная митигация R-10 и единственный способ держать модульные тесты на хосте, без запуска игры.
- **§5.0 схема как источник истины** (ADR-022). Прежняя редакция трижды расходилась с собственными примерами; теперь норматив — `contracts/*.schema.json`, проза ссылается, примеры валидируются в CI, типы генерируются.
- **§6.7 трекер строительства (FR-11)** — сопоставление построенных машин с узлами плана по классу, рецепту, Power Shards и Somersloops, с декрементом при демонтаже.
- **§13.1 среда разработки** — тесты ядра на хосте, `ficsitai-cli`, фикстурный каталог, тестовое сохранение, режим воспроизведения записанных ответов LLM, инварианты CI. Прежняя редакция строго специфицировала дешёвое (контракты) и не описывала дорогое (итерацию по UMG и латентность разработки).
- **[MODULES.md](MODULES.md)** — реестр из 34 модулей, по каждому: готовое решение, лицензия, статус проверки и остаток собственной работы.
- Риски R-17 (у форка один контрибьютор) и R-18 (доступность движковых `HTTP`/`WebSockets` моду не подтверждена). Критерии AC-13 (трекер) и AC-14 (инварианты CI). Набор spike'ов пересобран: S0 — чтение `SBCCalculatorWidget.cpp` до подтверждения форка.

**Изменено:**

- FR-06 стал интерактивным (следствие форка), FR-02 и FR-07 перенесены в v1.1, добавлен FR-11.
- `clockPercent` и `clockApplied` удалены из `BlueprintRequest`, код предупреждения `CLOCK_NOT_APPLIED` отозван (§5.4): поля описывали то, чего генератор не делает.
- Рантайм `ScreenDefinition` — генерируемый рендерер, библиотека экранов, `assign_screen`, кэш — перенесён в v1.2; в v1.0 замораживается только схема (§5.3).
- Упаковка: `vercel/pkg` заархивирован 13.01.2024, выбран Node SEA со статусом Active Development. R-11 **повышен**, а не снижен (§4.1).
- Лицензия проекта — **Apache-2.0**, как у Foreman. Из этого следует несовместимость с EPL-1.0 (Graphviz) и GPL-3.0 (piper1-gpl), зафиксированная в §2.2.
- R-10 снижен (но не закрыт), R-05 усугублён отсутствием референса телеметрии.

**Сохранено без изменений по существу:** граница доверия LLM и декларативная белая схема экранов (§7, ADR-005); разделение `plannedRate` и `actualRate` (§8.4); единый контракт для ручного и AI-пути (ADR-006); authority-слой и обязательное подтверждение игрока (ADR-009); только одиночная игра в v1.x (ADR-011); ядро Factory Spawner для чертежей (ADR-008); установщик как блокирующее требование релиза (ADR-015).

## 17.2 Относительно 1.0-draft (архив)

Раздел описывает переход к редакции 2.0-draft и сохранён как история решений. Часть пунктов ниже уже пересмотрена в §17.1 — прежде всего ADR-003, ADR-007 и ADR-012. Причина большинства изменений — решение §1.1 об отказе от мультиплеера.

**Удалено:**

- Game Bridge как компонент (ADR-004 отозван); его задачи распределены между модом и локальными файлами.
- FRM как обязательный серверный мод (ADR-003 заменён).
- Канал Bridge → серверное расширение SML — самая несспроектированная часть прежней редакции.
- Серверное расширение как отдельный деплой; осталось authority-слоем в процессе.
- ACL, роли, scope `shared`, pairing-токены, TLS, публикация портов.
- Прежние AC-01 (второй игрок), AC-10 (независимость игроков), AC-11 (late-join).
- Пайплайн изображений для экрана в мире; заменён render target'ом.
- Тип виджета `image`; поле `targetPlayer` в `BlueprintRequest`.
- ADR-010.

**Изменено:**

- Объём v1.0 сужен до ручного контура плюс текстовый чат; Blueprint, AI-экраны, голос и интерактивный граф разнесены по v1.1–v1.4 (§1.2).
- Представление графа: собственное read-only вместо извлечения кода SBP (ADR-007). AC-03 больше не требует интерактивности и не зависит от непройденного spike'а.
- Расчёт плана перенесён в мод (ADR-013), что закрыло R-04 и усилило FR-10.
- Хранение состояния — локальные файлы мода, а не БД внешнего сервиса (ADR-014). Это сознательный разворот относительно промежуточного варианта «всё в БД Foreman»: он противоречил бы FR-10.
- Foreman не форкается; наши инструменты — внешний MCP, который хостит сам мод (ADR-012).
- `ScreenDefinition`: `layout` стал перечислением пресетов с именованными слотами (прежние `layout:"grid"` и `area:"left"` были несовместимы), `source` стал структурированным, добавлены `theme` и клампинг `refreshSec`, `scope` сокращён.
- `BlueprintRequest`: приведён к одному каноническому набору полей (текст и пример прежней редакции расходились), добавлены `requestId` и `clockApplied`.
- `PreviewResult` специфицирован, добавлены машиночитаемые коды предупреждений, включая `MANIFOLD_RAMP_UP`.
- Частота обновления виджетов привязана к частоте данных.
- Spike'и сокращены с пяти до пяти других: исчезли транспорт и Blueprint-на-DS, появились MCP-эндпойнт и упаковка.

**Добавлено:**

- §4.1 упаковка и установка, §4.2 поведение в MP — обоих не было.
- §5.5 согласование версий мода и сайдкара.
- §7.3 инъекции через авторский текст игрока.
- §8.3 планировщик с честной оценкой побочных продуктов и циклов.
- §10.1 кэш отрендеренного экрана, без которого обещание деградации было невыполнимым.
- Риски R-10 (обновление игры), R-11 (упаковка), R-12 (лицензия FRM), R-13 (слушатель в процессе), R-14 (циклы рецептов), R-15 (загрузка в MP), R-16 (ёмкость команды).
- AC-09 (деградация), AC-10 (инертность в MP), AC-11 (бюджет GameThread), AC-12 (установка).
- §2.2 открытые лицензионные вопросы, включая неназванную лицензию собственного мода.

**Сохранено без изменений по существу:** граница доверия LLM и декларативная белая схема экранов (§7, ADR-005); разделение `plannedRate` и `actualRate` (§8.4); единый контракт для ручного и AI-пути (ADR-006); требование «известный рецепт ≠ разблокированный»; правило fallback-ADR при провале spike'а; запрет блокирующих вызовов в GameThread.

**Итог архитектуры.** Релиз состоит из одного мода и одного локального компаньона. Мод — форк Satisfactory Build Calculator: интерактивный граф, калькулятор, чтение каталога и силовая модель приходят вместе с базой кода, а не пишутся заново. Компаньон — наш компонент, внутри которого vanilla Foreman работает как есть и живёт MCP-сервер, так что мод не слушает ни одного порта. Там, где средство уже есть у платформы — конфигурация, хоткеи, персистентность, сторонность сессии, реестр контента, — берётся средство SML.

Собственная разработка после этого сосредоточена на одиннадцати модулях (§2, MODULES.md): интеграция форка с контрактами, планировщик как линейная система, граница доверия LLM, трекер строительства, телеметрия, жизненный цикл состояния и упаковка. Нормативом интерфейсов служат JSON-схемы, а не проза; инварианты разделения `core/` и `GameFacade/` и неприкосновенности authority-слоя проверяются скриптами CI, а не ревью.

Отказ от мультиплеера убрал с критического пути v1.0 все интеграционные неизвестные, способные опрокинуть архитектуру. Из оставшихся рисков два проект не контролирует — совместимость с обновлениями самой игры (R-10, снижен до починки одного каталога) и ёмкость команды (R-16, не закрыт), — а три требуют спайков до начала работы: качество кода форка (S0), доступность движкового транспорта (S2) и упаковка компаньона (S5).
