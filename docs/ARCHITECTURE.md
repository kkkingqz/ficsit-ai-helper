| Поле | Значение |

| Документ | FICSIT AI — Release Architecture |

| Лицензия | **GPL-3.0-or-later** (`LICENSE`, §2.2) |
| Реестр модулей | [MODULES.md](MODULES.md) — готовые решения и остаток собственной работы по каждому модулю |
| Статус | Проект архитектуры на согласование; не описание уже реализованного продукта |
| Целевая платформа | Satisfactory 1.2, SML 3.12, **Windows game client** — нативного Linux-клиента у игры нет |
| Платформа разработки | **Linux, игра под Proton** (ADR-033). Мод под Win64 собирается MSVC под wine; Windows-машины в команде нет |
| Топология | **Только одиночная игра.** Dedicated Server, listen server и мультиплеер вне v1.x |
| Главный приоритет | Переиспользование готовых решений там, где задача объективно сложна |

**Назначение.** FICSIT AI — мод к Satisfactory и локальный сервис-компаньон, превращающие FICSIT Foreman в доступного прямо в игре инженерного помощника. Игрок взаимодействует с ним текстом (позже голосом) через размещаемый терминал; экипируемое устройство и HUD появятся в v1.4. Помощник получает реальные игровые данные, показывает метрики и графики, ведёт заметки и Work Orders, управляет декларативными экранами, формирует запросы на создание простых Blueprint, а через подключаемый планировщик — планирует производство.

**Ключевое изменение 2.0-draft.** Проект отказывается от поддержки мультиплеера и Dedicated Server в пределах v1.x. Это решение принято не для экономии, а чтобы убрать с критического пути интеграционные неизвестные, каждая из которых могла опрокинуть архитектуру: сетевой канал между внешним сервисом и игровым сервером, доставка Blueprint клиенту в отсутствие локального игрока, репликация экранов и ACL. Полный разбор последствий — в §17.2.

**Ключевые изменения 2.1-draft** (по результатам проверки исходников Foreman и поиска готовых планировщиков, §17.1):

- Между модом и Foreman появляется тонкий **адаптер сайдкара**. Для Foreman он единственный MCP-сервер, мод подключается к нему исходящим соединением. Входящего слушателя в игровом процессе нет, Foreman не патчится (ADR-012).
- **Планировщик и представление плана — стандартизированная обёртка** с заглушкой в v1.0; внешний планировщик и UI подключаются к ней позже. Кандидаты провайдера — ядро Satisfactory Build Calculator (MIT, C++, SML 3.12) и линейная система; порядок их подключения выбирается по итогам Spike S3 (ADR-013, ADR-028).
- **UI — набор переиспользуемых экранных модулей** (Dashboard, Chat, Notes, Work Orders, Screens). В v1.0 их хост — AI Terminal, позже те же модули использует AI Assistant (ADR-001).
- **Объём v1.0 пересмотрен:** терминал с питанием 10 MW, экранные модули и редактор экранов вместе с инструментами модели для экранов; дорожная карта после v1.0: v1.1 — чертежи, v1.2 — голос, v1.3 — планировщик, v1.4 — AI Assistant и HUD (§1.2).
- **Подтверждений игрока нет.** Пишущие инструменты модели создают только объекты мода: заметки, экраны, чертежи в библиотеке. Ни один не изменяет мир, все применяются после валидации (ADR-009).
- Состояние мода хранится **в сохранении** с идентификатором `saveId`; снаружи — только телеметрия и кэш рендера (ADR-014).
- Мод определяет мультиплеер **в ходе сессии**, а не только при загрузке; контент регистрируется всегда, отключается поведение (ADR-016).
- Модель получает каталог через **поисковые инструменты**, а не одним ответом (ADR-017).
- **Паритет ручного и AI-пути:** каждое действие, доступное модели, игрок может выполнить вручную через UI без LLM. UI и модель вызывают одни и те же операции из общего реестра (§7.5, ADR-018).
- Первый результат работ — **вертикальный срез v0.1** (§13).

**Ключевые изменения 2.2-draft.** Редакция сводит в один документ две независимо развивавшиеся линии. Ведущей выбрана линия 2.1-draft: она опирается на чтение исходников Foreman, SBC и FicsIt-Networks, и её `OperationRegistry` с паритетом ручного пути (ADR-018) и обёртка планировщика (ADR-013) сильнее того, что предлагала параллельная линия 3.0-draft. Из закрытой линии перенесены семь находок; последний пункт списка — решение, которое из них следует:

- **Лицензии у Ficsit Remote Monitoring нет вовсе.** Проверено: файл лицензии в репозитории отсутствует. R-12 закрыт отрицательно, Spike S3 разблокирован, телеметрия становится полностью собственной разработкой (§2.2, §8.2).
- **Три модуля уже даёт платформа:** конфигурация с генерируемым UI и персистентность — средства SML, переназначаемые клавиши — Enhanced Input игры, а не наш код (§2.3, ADR-027). Определение сторонности сессии в их число не входит. Это единственная вставка, уменьшающая объём v1.0, и она направлена прямо в R-16.
- **Состав каталога — `UModContentRegistry`**, документированный путь к рецептам, включая модовые (§5.1, §8.1).
- **R-14 закрывается дешевле:** при выбранных игроком альтернативах задача планирования линейна, и LP-решатель для неё не нужен (§8.3, ADR-028).
- **`GameFacade/` с инвариантом CI** — первая конкретная митигация R-10, обобщение приёма ADR-026 на слой контакта с игрой (§3.2, ADR-029).
- **`vercel/pkg` заархивирован**, Node SEA имеет статус Active Development: R-11 повышается, S5 перестаёт быть «инженерной задачей» (§4.1).
- **Схема страницы результата поиска по каталогу** — он пересекает границу доверия и нуждается в контракте (§5.1).
- **Телеметрия v1.0 сокращена до текущей сессии**, история 24 ч перенесена в v1.1 (решение принято, §8.2).

Другие решения этой редакции: **правило «модель не изменяет игровой мир» принято как постоянный инвариант**, а не объём версии (§7, ADR-009); **модель управляет экранами и библиотекой чертежей, включая удаление чертежей** (§7.5). Ассет командного центра входит в объём v1.0 (§6.6, ADR-030).

**Главное ограничение проекта.** Не разрабатывать собственные решения там, где готовый проект уже предоставляет функциональность или исходный код **и где задача объективно сложна**: сериализация Blueprint, маршрутизация лент и труб, LLM-оркестрация, STT/TTS. Обратное тоже верно и теперь записано явно: не встраивать чужой код там, где собственная реализация проще его извлечения (§2). Отсутствие у стороннего мода публичного API не является основанием объявлять его runtime-зависимостью: такой компонент заимствуется/адаптируется при соблюдении лицензии.

**Архитектурный принцип.** Один `ProductionPlan` описывает производство; один `ScreenDefinition` описывает его отображение; один `BlueprintRequest` используется и ручным редактором, и LLM. **Модель не может ничего, чего не может игрок вручную:** каждый её инструмент — это операция мода с ручной точкой входа в UI, работающая без LLM (ADR-018). AI вызывает закрытый набор таких операций, **authority-слой мода валидирует** каждый вызов по схеме и живому каталогу. Инструментов, изменяющих игровой мир, у модели нет. В одиночной игре этот слой перестаёт быть границей процессов, но остаётся обязательной границей кода — он изолирует LLM, а не других игроков (ADR-009).

Редактор экранов и экранные инструменты выходят вместе в v1.0, ручная форма Blueprint Builder и инструменты чертежей — вместе в v1.1, инструменты планирования — вместе с подключённым планировщиком и его UI в v1.3, `set_hud_profile` — вместе с HUD в v1.4.

## 1.3 Что не входит

Мультиплеер, Dedicated Server, listen server; автоматическое строительство фабрики в мире; CAD/оптимизатор произвольной 3D-геометрии; свободный исполняемый код/HTML от LLM; автономный NPC; управление транспортом или оборудованием без подтверждения; замена интерфейса всего Satisfactory; поддержка сторонних машин с нестандартной геометрией в генераторе чертежей. **Это не ограничивает получение рецептов модовых машин из игры:** данные присутствуют, даже если генератор чертежей не умеет их размещать.

# 2. Стратегия готовых компонентов

Под «зависимостью» понимается мод/сервис, который конечный пользователь должен установить. «Переиспользовать код» означает включить или адаптировать функциональность в наш мод с соблюдением лицензии и атрибуции. Эти подходы не смешивать.

**Уточнение принципа относительно 1.0-draft.** Переиспользование оправдано, когда стоимость извлечения ниже стоимости реализации. Для сериализатора Blueprint, контроллера лент/труб и планировщика производства это верно с большим запасом. Принцип «не писать заново» не должен превращаться в обязательство встраивать чужой код в простые места: решение принимается по каждому компоненту отдельно, после чтения его исходников.

| Компонент | Решение | Обоснование и статус |
|---|---|---|
| SML 3.12 | **Обязательная runtime-зависимость**, GPL-3.0 | Регистрация машины/предмета, Widget Hooks, модовая упаковка; подтверждено документацией. Кроме этого даёт готовыми модули, которые 2.1-draft планировал писать сам: Mod Configuration и `AModSubsystem` с персистентностью, а также `UModContentRegistry` для состава каталога; клавиши берутся у Enhanced Input игры (§2.3, ADR-027) |
| FICSIT Foreman | **Внешний сервис, vanilla** | Chat REST/SSE, MCP-клиент, Work Orders, история. Не форкается и не патчится: подключается через адаптер сайдкара (§3.4, ADR-012). Apache-2.0 |
| Адаптер сайдкара | **Пишем сами**, Node/TS | Тонкий процесс без игрового состояния: MCP-сервер для Foreman, канал к моду, авторизация в Foreman (§3.3). Официальный TS SDK MCP |
| Satisfactory Build Calculator (SBC) | **Кандидат провайдера планировщика** (v1.3); порядок их подключения выбирается по итогам Spike S3 (§8.3, ADR-028) | `FSBCProductionData` + `FSBCProductionCalculator`: live-разблокировки, модовые рецепты, альтернативы, Power Shards, Somersloops, мощность. Для SBC 05.11.2026 проверено: ядро планировщика (около 590 строк) отделено от виджета, рецепты синхронизируются из `AFGRecipeManager::GetAllRecipes`, сборка под SML 3.12. Наличие собранного мода не подтверждает наличие доступного API для сторонних модов.

## 2.1 Решения «не писать заново» и «писать самим»

Не писать заново:

- Систему Work Orders, учётных записей, LLM tool calling и управление историей — всё остаётся в Foreman.
- **Планировщик производства и UI плана** — подключать внешние к стандартизированной обёртке; кандидаты — ядро SBC и линейная система, порядок их подключения выбирается по итогам Spike S3 (§8.3, ADR-013, ADR-028).
- Контроллер конвейеров/труб и сериализатор Blueprint — адаптировать Factory Spawner (v1.1).
- Аудиодвижок, STT и TTS — готовые сервисы (v1.2).
- Рецептурную базу — читать из игры, не переносить вручную.

Писать самим:

- **Адаптер сайдкара** — связка мода с vanilla Foreman (§3.3, ADR-012).
- **Обёртку планировщика и UI плана** — интерфейсы провайдера и представления, контракты, заглушку (§6.4, §8.3, ADR-007, ADR-013).
- **Экранные модули** Dashboard, Chat, Notes, Work Orders, Screens и интерфейс хоста (§6.3, ADR-001).
- **Телеметрию** — напрямую из игровых подсистем, без промежуточного HTTP (§8.2, ADR-003).
- Контракты, валидатор, интеграцию и жизненный цикл состояния.

## 2.2 Лицензии

Мод некоммерческий, и глубокий лицензионный анализ ему не нужен. Ниже — только то, что имеет практические последствия.

**Лицензия проекта — GPL-3.0-or-later** (ADR-031), текст в `LICENSE`. Выбрана на своих основаниях; совместимость с SML, который сам под GPL-3.0, получается попутно, но вопрос о производности мода от загрузчика не разбирается — на решения он не влияет. В `LICENSE.EXCEPTION` короткая оговорка про линковку с игрой и движком: полезна, потому что иначе формально нельзя выдать GPL-права на сборку с проприетарными компонентами.

**Входящее подходит всё, что мы используем:** MIT (слой данных SBC, Factory Spawner, `satisfactory-file-parser`), Apache-2.0 (MCP SDK, sherpa-onnx, пакеты Foreman, quicktype), MPL-2.0 (Eigen), BSD-3-Clause (IXWebSocket), GPL-3.0 (SML, FicsIt-Networks). Единственное исключение — EPL-1.0 у Graphviz, но он из архитектуры убран и так.

**Два практических следствия выбора GPL:**

- `piper1-gpl` стал равноправным кандидатом TTS в v1.2 — прежний план на Apache-2.0 его отсекал. Выбор против sherpa-onnx делается по качеству синтеза.
- Внешние моды обращаются к публичному API по имени класса через Blueprint или рефлексию, без включения наших заголовков (ADR-023). Это та же дистанция, которую мы держим от FIN, и она позволяет моду-клиенту оставаться под любой лицензией. Решение не делать FIN зависимостью при этом сохраняется, но по продуктовой причине: игроку не нужна обязательная установка (§3.7, ADR-024).

**Заимствованный код — в `third_party/<project>/` с исходным файлом лицензии и перечнем изменений.** Это единственное требование, которое стоит соблюдать аккуратно, и не ради формальностей: Factory Spawner и слой данных SBC написаны одиночками, и их авторство должно быть видно.

**У Ficsit Remote Monitoring лицензии нет** — файла в репозитории не существует, в README только разрешение пользоваться API. Важно это не как юридический факт, а как инженерный: **референса по структуре данных фабрики у нас нет**, телеметрия (§8.2) пишется с нуля вслепую. Именно поэтому её объём в v1.0 сокращён. Наблюдать, какие поля FRM отдаёт по своему API, никто не мешает — это и остаётся ориентиром.

## 2.3 Что предоставляет сама платформа

Правило (ADR-027): **перед реализацией любого модуля проверяется, нет ли готового средства SML.** Редакция 2.1-draft планировала собственной разработкой три вещи, которые платформа уже закрывает, — и это прямо относится к R-16, где объём UI назван главным необеспеченным риском.

| Что планировалось писать | Средство платформы | Что остаётся нашей работой |
|---|---|---|
| §6.9 Настройки: пять разделов, язык, единицы, масштаб, тема, уведомления, диагностика | **Mod Configuration** — генерирует UI из декларации свойств и сама сохраняет JSON | Декларация свойств и те разделы, которым нужен нестандартный виджет (диагностика связи, проверка сайдкара) |
| §6.7 нижняя полоса горячих клавиш, переназначение клавиш | **Enhanced Input игры:** `UInputAction` и контекст ввода мода (`UFGInputMappingContext`); переназначение — в штатных настройках управления. Отдельного реестра клавиш в SML 3.12 нет: `RegisterModKeyBind` — API SML 2.x, в текущем дереве SML его нет | Перечень действий, контекст ввода мода, привязка к экранным модулям. Попадание действий мода в штатное меню переназначения проверяет Spike S1 |
| §10 персистентность состояния мода в сохранении по `saveId` | **`AModSubsystem`** с игровым `IFGSaveInterface` сохраняется в save-файл штатным механизмом игры | Выбор, что уходит в сохранение, а что в локальные файлы, и миграции `schemaVersion` |

**Определение сторонности сессии в таблицу не входит** (исправлено 09.11.2026). Первая версия 2.2-draft относила его к Replication Policy, но `ESubsystemReplicationPolicy` (`SpawnOnServer`, `SpawnOnServer_Replicate`, `SpawnOnClient`, `SpawnLocal`) задаёт только, где создаётся сабсистема, и не сообщает, одиночная ли сессия. Для мода выбирается `SpawnOnServer`: в одиночной игре это локальный процесс, а удалённый клиент сабсистему не получает. Сам ADR-016 — проверка `NetMode` при загрузке и отслеживание входа удалённого игрока в ходе сессии (§4.2) — остаётся собственной работой целиком, его проверяет Spike S1.

**Экран «Настройки» уходит из собственной разработки почти целиком**, что снимает одну строку из AC-17 и часть объёма, на который ссылается R-16.

# 3. Логическая архитектура

![Компонентная схема FICSIT AI](assets/components.png){ width=6.0in }

Архитектура состоит из **двух рантаймов**: игровой процесс и локальный сайдкар (Foreman и адаптер, один установщик). В 1.0-draft их было пять (клиент, серверное расширение SML, Game Bridge, Foreman, FRM).

## 3.1 Игровой процесс: презентационный слой

UI строится из **экранных модулей** и **хостов** (ADR-001):

- **Экранный модуль** — самостоятельный UMG-экран с интерфейсом `IScreenModule`: Dashboard, Chat, Notes, Work Orders, Screens, а также обёртки Planning и Graph (v1.0) и Blueprint Builder (v1.1). Модуль не знает, в каком хосте открыт: он получает от хоста контекст (`saveId`, доступ к операциям, размер и раскладку, фокус ввода) и сам адаптируется к размеру.
- **Хост** (`IScreenHost`) — объект, который открывает модули и переключает их. В v1.0 хост один — `AI Terminal` (строительный объект с питанием). В v1.4 тем же интерфейсом станет `AI Assistant` (экипируемый предмет), и он откроет те же модули без доработки; HUD появится вместе с ним.

Кроме того, в слое: отрисовка экрана в мире (render target) и локальные настройки клавиш.

## 3.2 Игровой процесс: authority-слой

Единственный путь от любого внешнего вызова к изменению состояния мода. Содержит: `OperationRegistry`, `CatalogProvider` (на основе слоя данных SBC: `AFGRecipeManager` и зарегистрированные в SML классы), `TelemetrySampler`, `PlannerGateway` (обёртка планировщика: в v1.0 — заглушка, §8.3), `Validator` и — с v1.1 — адаптированное ядро Factory Spawner.

**`OperationRegistry`** — единый реестр операций мода (ADR-018). У каждой операции: идентификатор, JSON Schema аргументов и результата, обработчик и ручная точка входа в UI. Формы UI и инструменты модели вызывают одни и те же операции и проходят один и тот же `Validator`. Описания инструментов для адаптера генерируются из реестра; операция без ручной точки входа не может быть выставлена модели.

**Инвариант.** Набор инструментов модели закрыт и не содержит операций, изменяющих игровой мир: только чтение, заметки, экраны, Work Orders (v1.0), создание и удаление чертежей в библиотеке (v1.1) и расчёт плана (с подключённым планировщиком). Каждый вызов проходит `Validator` (схема, лимиты, сверка с живым каталогом); подтверждений игрока нет (ADR-009). Ни один обработчик ответа сайдкара не вызывает мутирующее API мира. Шов сохраняется ровно в таком виде, чтобы будущий мультиплеер стал портированием, а не переписыванием (ADR-011).

**Этот инвариант — постоянный, а не объём версии** (решение 2.2-draft, ADR-009). Он не «пока у нас нет таких функций», а правило: инструмента, изменяющего игровой мир, у модели не появится ни в одной версии v1.x. Строительство, демонтаж, переключение рецептов, настройка такта, управление транспортом остаются исключительно ручными. Поэтому очередь подтверждений в архитектуре отсутствует не по недосмотру: подтверждать нечего.

## 3.2.1 Разделение на ядро, фасад и UI

Приём ADR-026 (`FicsitAIUI` не видит заголовков игры, нарушение ловится сборкой) обобщается на слой контакта с игрой (ADR-029). Три правила, и все три — скриптами CI, а не ревью:

| Каталог | Что внутри | Правило, проверяемое в CI |
|---|---|---|
| `FicsitAIApi/` | Интерфейсы и типы контрактов | Не зависит ни от игры, ни от SML, ни от UMG |
| `FicsitAIUI/` | Экранные модули | Зависит только от `FicsitAIApi` и UMG/Slate (ADR-026) |
| `GameFacade/` | Чтение подсистем, индекс построек, хуки строительства | **Единственное место, где допустимы типы `AFG*`/`UFG*`** |
| `core/` | Валидатор, обёртка планировщика, решатель, операции | Собирается и тестируется на хосте, без запуска игры |

Два следствия. Первое: модульные тесты валидатора, обёртки и решателя идут за секунды, а не через загрузку мира, — это и есть ответ на вопрос «сколько длится цикл правка → результат». Второе, важнее: **обновление игры 1.2→1.3 превращается в починку одного каталога** вместо поиска по всему коду. Это первая конкретная митигация R-10, который до сих пор закрывался только прозой «минимум связи с внутренними структурами игры».

Каталоги `GameFacade/` и `core/` живут в UE-модуле `FicsitAICore` (§13); `core/` дополнительно собирается на хосте без UE.

Третий инвариант CI — тот же, что у authority-слоя: вызовы мутирующего игрового API не встречаются в обработчиках внешних сообщений. Вместе с тестом паритета (§13) это три проверки, роняющие сборку.

## 3.3 Адаптер сайдкара и канал к моду

Тонкий Node/TS-процесс в составе сайдкара, без игрового состояния (ADR-012). Обязанности:

1. **MCP-сервер для Foreman.** Адаптер — единственный `MCP_URL` Foreman. Он отдаёт модели инструменты мода (§7.1), сгенерированные из `OperationRegistry`, и может проксировать отдельные инструменты `sf-mcp`.
2. **Белый список.** Адаптер выставляет модели только инструменты из белого списка (ADR-018): операции мода и те инструменты `sf-mcp`, у которых есть ручной путь в игровом UI. Остальные инструменты `sf-mcp` (чтение загруженного `.sav`, планирование, справочные запросы по каталогу) скрыты: они дублируют live-операции мода, и модель получила бы два разных ответа на один вопрос. Встроенные инструменты Work Orders живут в самом `ff-server`, через MCP не проходят и адаптером не фильтруются — их ручной путь описан в §7.5.
3. **Чат.** Мод обращается к стабильному API адаптера, адаптер — к API Foreman. Изменения API Foreman гасятся в одном месте.
4. **Авторизация.** Адаптер сам регистрирует локальный аккаунт Foreman (email и пароль генерирует установщик) и держит сессию. Мод ничего не знает о логине.
5. **Сопоставление** `saveId` (§10) с playthrough Foreman: адаптер находит или создаёт playthrough для текущего сохранения.
6. **Согласование версий** с модом (`apiVersion`, §5.5).

**Канал мод ↔ адаптер.** Мод сам открывает исходящее соединение к адаптеру на `127.0.0.1` (WebSocket или HTTP long-poll — выбрать в Spike S2) с токеном из локального конфига. По этому каналу адаптер передаёт моду вызовы инструментов, а мод возвращает ответы и события. Входящего слушателя в игровом процессе нет. Требования к моду: сетевой код вне GameThread; любое обращение к игровому состоянию — через задание в GameThread и снапшот-ответ; переподключение без влияния на игру.

## 3.4 Foreman (локально)

Остаётся как есть: `ff-server`, `sf-mcp`, собственная БД (SQLite), chat-цикл, Work Orders, история. Не форкается и не патчится. Его планировщик и данные `sf-game-data-graph` **не используются для расчётов** — планирование идёт через обёртку мода (§8.3); встроенные данные Foreman остаются для справочных ответов, когда игра не подключена.

**Проверено по исходникам Foreman (05.11.2026)** — эти факты и определили схему с адаптером:

- `ff-server` подключается к **одному** MCP-серверу (`MCP_URL`). Класс `McpAggregateGateway` для нескольких серверов в коде есть, но не подключён.
- MCP-клиент Foreman не отправляет заголовков; токен к адаптеру передаётся в query-строке `MCP_URL`.
- Клиент внедряет `savePath` текущего playthrough в аргументы вызовов; адаптер удаляет его из вызовов инструментов мода.
- Чат (`POST /api/playthroughs/:id/chat`, ответ потоком SSE) закрыт сессией Better Auth через cookie; аккаунты поддерживают MFA.
- Инструменты Foreman по сохранению читают загруженный `.sav`, а не живую игру.
- **`sf-mcp` в режиме HTTP не имеет аутентификации** (его документация; проверено Co2 на P-3), и по умолчанию он работает по stdio — порт слушает только при `MCP_TRANSPORT=http`. Единственная защита порта — петля (§12).
- Инструменты Work Orders (`create_work_order`, `create_child_work_order`, `create_explore_order`) встроены в `ff-server` и добавляются к MCP-инструментам внутри него. У Work Orders есть REST: создание `POST /api/playthroughs/:id/work-orders`, правка плана, шагов и переходы статусов — это ручной путь без LLM.
- Поставка Foreman — три Docker-сервиса (`sf-mcp`, `ff-server`, `ff-client`); Prisma поддерживает SQLite.

Интерфейс: мод → адаптер → `POST /api/playthroughs/:id/chat` и поток SSE; Foreman → адаптер → мод для вызовов инструментов. Все соединения — loopback.

## 3.5 Чего в архитектуре больше нет

| Было в 1.0-draft | Почему убрано |
|---|---|
| Серверное расширение SML как отдельный деплой | В одиночной игре это тот же процесс; остаётся authority-слоем (§3.2) |
| Game Bridge | Его задачи распались: состояние → сохранение и локальные файлы мода, телеметрия → в процессе, изображения → render target. Остался только тонкий адаптер без игрового состояния для связи с Foreman (§3.3) |
| FRM как обязательный мод | Потребитель данных теперь в том же процессе; HTTP-сервер посередине не нужен (§8.1) |
| Канал Bridge → SML server extension | Самая несспроектированная часть прежней редакции; исчезла вместе с сетевой границей |
| TLS, публикация портов, pairing-токены с `worldId`/`playerId` | Всё на loopback, один локальный пользователь (§12) |
| Входящий MCP-слушатель в игре (2.0-draft) | Заменён исходящим каналом мода к адаптеру; закрыт R-13 (§3.3) |
| Очередь подтверждений (2.0-draft) | У модели нет инструментов, изменяющих мир (§7) |
| Собственный планировщик (2.0-draft) | Заменён обёрткой с подключаемым провайдером (§8.3) |

## 3.6 Публичный API мода

Решение (ADR-023): у мода один публичный API (`FicsitAIApi`), и **все его клиенты равноправны**: наши экранные модули, модель (через адаптер), FicsIt-Networks и другие моды. Экраны не обращаются к подсистемам, `CatalogProvider` или `TelemetrySampler` напрямую — только через API. Сам API работает поверх сменного источника данных: живая игра, сохранение, запись или фикстуры (§8.5). Это делает экраны переносимыми между хостами и модами, а API — проверенным собственным UI с первого дня.

Состав API:

- **Запросы (чтение):** метрики и временные ряды, линии и их метрики, каталог (поиск), планы, заметки, экраны, Work Orders (через адаптер), состояние мода. Читают последний снапшот, вызов дешёвый и не задевает GameThread.
- **Операции (запись):** операции `OperationRegistry` (§3.2) — заметки, экраны, привязка линий, расчёт плана, чертежи. Одна и та же валидация и лимиты для любого клиента.
- **События:** `metrics.snapshot`, `line.changed`, `plan.updated`, `screen.updated`, `note.changed`, `mod.inert`. Экраны перерисовываются по событиям, внешние клиенты подписываются на те же события.
- **Внешние поставщики данных:** другой мод или компьютер FIN регистрирует собственную метрику в своём пространстве имён (`ext.<modId>.<name>`) и публикует значения; она появляется в выборе метрик Статистики и Screens наравне с нашими и помечена как внешняя.

Правила:

- **Версионирование:** `apiVersion` (semver). Мажорная версия меняется только при несовместимых изменениях; устаревшие функции живут минимум одну минорную версию с пометкой deprecated.
- **Права клиента:** модель — только инструменты из белого списка (§7.5). Наши экраны, FIN и другие моды — ручные клиенты от имени игрока: им доступны и ручные операции (например, привязка линий из UI). Изменять мир не может никто: таких операций в API нет.
- **Лимиты частоты и размера** — на каждого клиента отдельно; запись от внешних клиентов идёт через тот же `Validator`.
- **Инертность в MP** (§4.2): API отвечает ошибкой `MOD_INERT` и шлёт событие `mod.inert`.

## 3.7 Интеграция с другими модами

**FicsIt-Networks (v1.1).** FIN находит функции других модов через свою reflection-систему без зависимости от FIN (проверено по `FIRSourceUObject.cpp` и документации FIN `ModIntegration.adoc`): актору достаточно компонента с именем `FINConnector` и функций с префиксами `netFunc_` (функция), `netPropGet_`/`netPropSet_` (свойство), `netSig_` (сигнал) и `netFuncMeta_` (описание и режим выполнения).

- **Где:** AI Terminal получает `FINConnector` и становится сетевым компонентом FIN. Его `netFunc_`-функции — тонкие обёртки над публичным API (§3.6), без собственной логики.
- **Что доступно из Lua:** чтение метрик, рядов, линий, планов, заметок и экранов; операции с заметками и экранами; публикация внешних метрик (`pushMetric`), которые затем показывают наши экраны. Сигналы FIN (`netSig_`) повторяют события API: изменение линии, плана, экрана, заметки, переход в инертный режим.
- **Режим выполнения:** функции чтения помечаются как параллельные (`Runtime = 1`), потому что читают снапшот; операции записи — как синхронные и проходят обычную валидацию.
- **Типы:** только базовые типы reflection FIN (строки, числа, логические значения, массивы, структуры). Вариативные аргументы не используются: им нужен тип `FFINAnyNetworkValue` из FIN, то есть жёсткая зависимость.
- **Почему без линковки.** Прежние редакции обходили линковку, чтобы не попасть под GPL-3.0 самого FIN. После выбора GPL для проекта этой причины нет, но решение сохраняется, и причина теперь одна, зато настоящая: жёсткая зависимость заставила бы каждого игрока установить FIN, чтобы наш мод вообще загрузился. Нефункциональная цель §1.1 — «отсутствие обязательных сторонних модов».
- **Без FIN** компонент `FINConnector` просто не используется, мод работает как обычно.

**Другие моды (C++/Blueprint, v1.1).** Тот же API публикуется как world subsystem с Blueprint-вызываемыми функциями и делегатами событий. Мод-клиент обращается к нему через интерфейс по имени класса и проверяет `apiVersion`, то есть не обязан объявлять наш мод жёсткой зависимостью. В v1.0 API уже существует и используется нашими экранами, но внешне не публикуется, чтобы успеть стабилизировать его до первой внешней версии.

**Доступ только на расстоянии вытянутой руки** (уточнено в 2.2-draft, ADR-023). Внешний клиент находит API поиском world subsystem по имени класса и вызывает его через Blueprint или рефлексию UE — он не включает наши заголовки и не линкуется с нашими модулями. Это та же дистанция, которую мы держим от FIN, и она же позволяет моду-клиенту оставаться под любой лицензией при нашей GPL. Опубликованный контракт API — имена, подписи функций и типы контрактов из `FicsitAIApi`, а не C++-заголовки для включения.

**Расширяемость экранов (будущие версии).** Другой мод сможет регистрировать собственный тип виджета или экранный модуль через тот же API. Контракт `IScreenModule` (§6.3) для этого уже не зависит от хоста.

# 4. Развёртывание

| Что | Где | Обязательность |
|---|---|---|
| Satisfactory 1.2 + SML 3.12 + `FicsitAI` | Машина игрока | Обязательно |
| Сайдкар: адаптер + Foreman (`ff-server`, `sf-mcp`) + SQLite | Та же машина, один установщик | Обязательно для AI-функций и Work Orders; остальные ручные функции работают без него |
| STT/TTS | Та же машина или внешний провайдер | v1.2 |

Веб-интерфейс Foreman (`ff-client`) в пакет не входит. Сетевых границ нет: весь обмен идёт по loopback. Порты наружу не публикуются, сертификаты не нужны.

**Платформа разработки отличается от платформы игрока** (ADR-033). У игрока и мод, и сайдкар — Windows. На машине разработки игра идёт под Proton, а сайдкар запускается нативным процессом Linux: мод под Proton подключается к `127.0.0.1` хоста, поэтому канал §3.3 проверяется штатно. Командой не проверяется только **поставка** (§4.1) — её выполняет пилотный тестер на Windows (§13, AC-12, R-27).

## 4.1 Упаковка и установка

**Это главный UX-риск проекта.** В одиночной игре игрок сам себе администратор. Требование «установите Docker и поднимите несколько контейнеров» ограничивает аудиторию мода сотнями человек вместо десятков тысяч.

Решение для v1.0 (ADR-015):

- **Один установщик сайдкара:** портативный Node, бандлы `ff-server`, `sf-mcp` и адаптера, база SQLite и маленький launcher. Объём порядка 50–80 МБ. Поставка нативного движка Prisma проверяется в Spike S5. Мод ставится обычным образом через SMM.
- **Инструмент упаковки, и здесь оценка ухудшается.** Редакция 2.1-draft писала «портативный Node, бандлы», подразумевая существующий общепринятый инструмент. Проверено: **`vercel/pkg` заархивирован 13.01.2024** и использоваться не может. Актуальная замена — **Node SEA** (single executable applications), у которого в документации Node статус Active Development: API может измениться между минорными версиями. Третий путь — не упаковывать вовсе, а поставлять распакованный портативный Node с launcher'ом: больше файлов и объёма, зато ни одной нестабильной зависимости. **Это повышает R-11, а не снижает**, и снимает с S5 характеристику «инженерная, а не исследовательская задача»: выбор между SEA и распакованной поставкой надо сделать измерением, а не из принципа.
- **Установщик генерирует** токен канала мод ↔ адаптер и учётные данные локального аккаунта Foreman, записывает их в конфиги мода и сайдкара. Ключ LLM-провайдера игрок вводит один раз; он хранится у сайдкара.
- **Мод запускает сайдкар** при старте игры: если сайдкар уже работает, мод подключается к нему, иначе стартует процесс. При выходе из игры мод останавливает сайдкар, если сам его запускал.
- **Docker-compose** допустим как альтернативный путь для тех, кто его предпочитает, но не как основной.
- Мод сам обнаруживает неподнятый сайдкар и показывает внятное состояние, а не ошибку соединения.

Критерий приёмки упаковки: от скачивания до первого ответа помощника — без ручного редактирования конфигов, кроме ввода ключа LLM-провайдера.

## 4.2 Поведение в мультиплеерной сессии

Мод регистрирует новые классы акторов (терминал, предмет), поэтому в мультиплеере он принципиально требует установки у всех участников — «client-only мод с размещаемым объектом» в MP невозможен. Промежуточного варианта нет, и это подтверждает решение §1.1.

Важно, что «одиночность» — не постоянное свойство сессии: в Satisfactory к уже идущей игре могут подключиться другие игроки, если это разрешают настройки приватности. Поэтому проверка только при загрузке недостаточна (ADR-016):

1. **Контент регистрируется всегда:** рецепты, схемы, классы терминала и предмета. Снятие регистрации опаснее для сохранений и разблокировок, чем отключение поведения.
2. **Поведение отключается в рантайме.** При входе первого удалённого игрока мод становится инертным: закрывает UI (с v1.4 — и HUD), отключается от адаптера, терминал показывает «недоступно в мультиплеере» с указанием причины. Когда удалённые игроки уходят, мод возобновляет работу. Тот же режим включается сразу, если сессия загружена как мультиплеерная.
3. **Мод помечается в SML как обязательный на удалённой стороне** (`RequiredOnRemote` в `.uplugin`; проверить в Spike S1), чтобы игрок без мода не мог подключиться и вызвать десинк.
4. Уже размещённые терминалы не ломают загрузку сохранения в любой сессии.

Это задача v1.0 и отдельный критерий приёмки (AC-10), а не «потом».

# 5. Модель данных: базовые контракты

## 5.1 `GameCatalog` (read-only)

Нормализованные сущности `Item`, `Recipe`, `Machine`, `Schematic`, `UnlockState`. Ключ — устойчивое игровое `className`; отображаемое имя и локализованная подпись хранятся отдельно. У рецепта: список ингредиентов/продуктов, длительность, производство в минуту, `producedIn`, `isAlternate`, `unlocked`. У машины: класс, семейство, энергопотребление, доступность для строительства, порты.

Источник истинности — **только игровые подсистемы текущего процесса**. Прежнее разделение «FRM даёт перечень, SML даёт статус разблокировки» устранено: оба берутся из одного места, поэтому инвариант «известный рецепт ≠ разблокированный в этом сохранении» теперь поддерживается одним кодом, а не сверкой двух источников.

**Обновление:** полная сборка при загрузке сохранения и после изменения состава модов; инкрементальное обновление разблокировок по игровым событиям; версия каталога (`catalogRevision`) для инвалидации кэшей UI.

**Состав каталога даёт `UModContentRegistry`** — документированный реестр SML, перечисляющий рецепты, предметы и схемы, включая зарегистрированные модами. Он же отвечает на вопрос «этот рецепт из игры или из мода» (`IsRecipeVanilla`) и сообщает о появлении нового контента событием `OnRecipeRegistered`. Разблокировки и числовые параметры читаются из игровых подсистем, как описано выше. Это снимает необходимость опираться на слой данных SBC для **состава** каталога: оттуда берутся числа и нормализация, а не перечень (§8.1).

`GameCatalog` — внутренняя модель мода; наружу (модели) он отдаётся только частями, через поисковые инструменты (§7.1). **Но эти части пересекают границу доверия, поэтому форма страницы результата нормируется схемой** `contracts/schemas/catalog-page.schema.json`: элемент результата, курсор пагинации, флаги `unlocked` и `isVanilla`. Схемы самого `GameCatalog` нет сознательно — наружу он целиком не выходит.

## 5.2 `PlanRequest` и `ProductionPlan`

Это контракт обёртки планировщика (§8.3): любой провайдер принимает `PlanRequest` и возвращает `ProductionPlan` или ошибку с кодом. Контракт фиксируется в v1.0, хотя в v1.0 к обёртке подключена только заглушка.

**`PlanRequest`:** `schemaVersion`, `saveId`, `catalogRevision`, цель (предмет и расход/мин), выбранные альтернативные рецепты, настройки машин по рецептам (Power Shards, Somersloops), необязательные ограничения на сырьё. Пример — `contracts/plan-request.example.json`.

**`ProductionPlan`:** идентификатор, `saveId` сохранения-владельца (§10), версия, `catalogRevision`, целевой ресурс и расход/мин; список производственных групп (машина, рецепт, количество, такт, плановая скорость), соединений (item, source group, target group, quantity/min, единицы), выбранных альтернативных рецептов, источников сырья, сводные показатели энергии и машин, перечень предупреждений планировщика.

План — **вычисляемая модель**, а не рисунок. Таблица, граф и Foreman работают с одним объектом; отрисовка — только представление. План хранит `catalogRevision`, при котором был посчитан: при расхождении с текущим UI помечает план как требующий пересчёта, а не молча показывает устаревшие числа.

Ошибки обёртки: `PLANNER_NOT_CONNECTED` (подключена заглушка), `PLANNER_CAPABILITY_MISSING` (провайдер не поддерживает запрошенное, например Somersloops), `SYSTEM_INFEASIBLE` (выбранный набор рецептов не может дать цель; виновные рецепты — в `scope`, §8.3). Коды предупреждений плана: `BYPRODUCT_NOT_BALANCED` (побочный продукт посчитан, но не сведён в баланс), `RECIPE_LOCKED` (рецепт не разблокирован в этом сохранении), `CATALOG_STALE` (каталог изменился после расчёта). Цикл рецептов у провайдера, который их не поддерживает, — не предупреждение, а ошибка расчёта `RECIPE_CYCLE_UNSUPPORTED`: план не строится (§8.3).

## 5.3 `ScreenDefinition`

Исправления относительно 1.0-draft: `layout` и `area` были несовместимы (`grid` с именованными значениями `left`/`right`/`bottom`), поля темы и прав присутствовали в тексте и отсутствовали в примере, `source` был неструктурированной строкой.

Поля: `schemaVersion`, `id`, `scope`, `title`, `layout`, `theme`, `widgets[]`. Каждый виджет: `id`, `type`, `slot`, `source`, необязательные `options` и `refreshSec`.

- `scope` — `personal` | `terminal`. Значение `shared` удалено вместе с мультиплеером.
- `layout` — **перечисление пресетов** (`slots-1`, `slots-2`, `slots-3`, `hud-compact`), а не свободная сетка. Слоты именованные: `main`, `side`, `foot`. Перечисление вместо произвольной геометрии резко сокращает число невалидных состояний, которые может породить LLM. Свободная сетка — кандидат на следующие версии после накопления реальных экранов. Пресеты, предназначенные для экрана в мире, компонуются в **16:9** — это ограничение меша терминала, а не UI (§6.6, ADR-030).
- `source` — структурированный объект `{"kind": "...", "id": "..."}`, где `kind` — перечисление (`plan`, `metric`, `line`, `work_orders`, `notes`, `static`). Валидируется не только синтаксически: `id` сверяется с живым каталогом метрик, линиями и существующими планами, иначе виджет отклоняется с указанием причины.
- `refreshSec` — необязательное; клиент **зажимает** значение в допустимый диапазон, а не отклоняет определение, и у тяжёлых источников есть нижний порог (§8.2).

Типы виджетов v1.0: `text`, `metric`, `table`, `timeseries`, `production_graph`, `line`, `notes`, `work_orders`. Виджет `line` — карточка производственной линии (§5.7); он добавлен в 2.2-draft, чтобы у карточки линии в чате был ручной путь в Screens (§7.6). Тип `image` удалён — пайплайна изображений в v1.0 нет; вернётся вместе с сайдкаром.

Клиент создаёт виджеты только из белого списка и отвергает незнакомые поля и типы. В JSON нет HTML, JS, Unreal class paths или сетевых URL.

**Правило, отложенное вместе с мультиплеером.** В 1.0-draft `notes` мог попасть на общий терминал, что было утечкой (бывший R-06). В одиночной игре ограничение не нужно, но его надо восстановить как жёсткое правило белого списка (`notes` недопустим при `scope=terminal`) одновременно с появлением MP. Зафиксировано в §15, ADR-005.

## 5.4 `BlueprintRequest`

Исправление относительно 1.0-draft: там текст §5.4 и пример §11.2 перечисляли разные поля (`belts`/`pipes`/`power` плоско против вложенного `connections`; `naming` против `outputName`). Ниже — единственный канонический набор, совпадающий с `contracts/blueprint.example.json`.

Поля: `schemaVersion`, `requestId`, `machineClass`, `recipeClass`, `count`, `layout`, `connections{belts,pipes,power}`, `outputName`; необязательный `clockPercent`. Поле `targetPlayer` удалено — адресат один, поле `clockApplied` — в 2.2-draft (разбор ниже).

- `requestId` обеспечивает идемпотентность: повторный вызов с тем же `requestId` не создаёт второй чертёж.
- **`clockApplied` удалён, `clockPercent` стал необязательным** (решение 2.2-draft). Открытый вопрос остаётся тем же: выставляет ли генератор такт в самом чертеже — оверклок требует Power Shards и задаётся после размещения. Менялся способ, которым контракт об этом сообщает, и прежний был неверен по четырём причинам:

  1. **`clockApplied` — выход в схеме входа.** `BlueprintRequest` — это запрос, а значение `clockApplied` определяется возможностями генератора, не вызывающим. Заполняя его, клиент не просит ни о чём, а сообщает факт о нашей реализации. Место такого сигнала — `PreviewResult`.
  2. **Обязательное поле с неизвестным действием.** Оба поля были в `required`, но при `clockApplied=false` значение `clockPercent` на результат не влияет. Контракт требовал заполнить то, что может ничего не делать.
  3. **Такт уже имеет дом** — `ProductionPlan.groups[].clockPercent` (§5.2), где он нужен для `plannedRate`. Дублирование создавало второй источник истины, то есть ровно тот класс дефектов, против которого вводятся контракты со схемами (§5).
  4. **Несогласованность позиции.** §6.8, §8.2 и AC-04 втроём утверждают, что настройки машин мод только отображает и не меняет. `clockPercent` в запросе чертежа был единственным местом, где мод их задаёт.

  **Как теперь.** `clockPercent` необязателен, по умолчанию 100, и выражает пожелание игрока. Отвечает за правду `PreviewResult`: если генератор такт не выставляет, preview возвращает предупреждение `CLOCK_NOT_APPLIED` с указанием, что значение учтено в расчёте `plannedRate`, но в чертеже такта не будет и его нужно выставить после размещения. Это лучше булева флага тем, что **ответ даётся на каждый конкретный запрос**, а не декларируется схемой один раз для всех.

  **Почему решение безопасно принять до спайка.** По §5.5 добавление необязательного поля аддитивно и мажорную версию не поднимает, а удаление поля — ломающее изменение. Схема замораживается в v1.0, чертежи появляются в v1.1. Поэтому дешёвое направление — не фиксировать сейчас обязательным то, что может не сработать; если спайк v1.1 покажет, что генератор умеет выставлять такт, предупреждение просто перестанет появляться, а схема не изменится вовсе.

  Граница `maximum: 250` в схеме взята из предельного оверклока на трёх Power Shards. Она **не проверена** и уточняется тем же спайком вместе с вопросом о Somersloops, которые влияют не на такт, а на выход.

Отдельные `PreviewResult` и `CreateResult`. `PreviewResult` содержит `valid`, массивы `errors` и `warnings` с машиночитаемыми кодами, оценки входов/выходов, мощности и габаритов, предложение разбиения на модули. Два кода предупреждения обязательны. `MANIFOLD_RAMP_UP`: у манифолда известен эффект разгона и голодающей последней машины, и preview должен об этом сообщать, а не только считать суммарный поток. `CLOCK_NOT_APPLIED`: если в запросе есть `clockPercent`, отличный от 100, а генератор такт в чертеже не выставляет, preview обязан это сказать до создания (разбор выше).

Порядок: dry-run и валидация → создание через authority-слой. Отдельного подтверждения нет: чертёж только появляется в библиотеке, в мир его ставит сам игрок. В ручной форме (v1.1) создание запускает кнопка игрока; при вызове из чата `PreviewResult` и итог показываются в ответе. Запрос с `errors` отклоняется с указанием причины.

## 5.5 Версионирование и совместимость

В 1.0-draft `schemaVersion` был у сущностей, но согласования версий компонентов не было. Теперь:

- У мода и адаптера единый `apiVersion`. Мод присылает свой при подключении; при несовпадении мажорной версии AI-функции отключаются с **видимым игроку сообщением**, ручные продолжают работать.
- Версию Foreman изолирует адаптер: мод не зависит от API Foreman напрямую. Установщик фиксирует проверенную версию Foreman.
- Мод и сайдкар поставляются одним установщиком с согласованными версиями, чтобы пользователь не смешивал сборки.
- У сущностей сохраняется `schemaVersion` и миграции при загрузке.
- JSON Schema контрактов лежат в `contracts/schemas/`, примеры проверяются по ним в CI.

## 5.6 Единицы

Твёрдые предметы — `items/min`, жидкости и газы — `m3/min`, мощность — MW. Игра хранит жидкости во внутренних единицах (1 м³ = 1000); перевод выполняется один раз, на границе `CatalogProvider`. Остальной код и все контракты работают только в единицах выше.

## 5.7 `ProductionLine`

Именованная группа построек в мире — основа метрик «по объекту» и «по линии» на экранах (FR-13). Контракт: `schemaVersion`, `id`, `saveId`, `name`, `source` (`manual` | `auto`), `members[]` (у каждой постройки: `buildingId` и `className`), необязательные `notes`. Пример — `contracts/line.example.json`.

- **`buildingId`** — устойчивый идентификатор постройки в сохранении. Кандидат — путь актора в уровне, который система сохранений игры использует для восстановления объектов; устойчивость между загрузками проверяется в Spike S3.
- **Ручная привязка (v1.0).** В терминале игрок создаёт линию и запускает режим привязки: интерфейс закрывается, игрок наводит прицел на постройки и добавляет или убирает их клавишей, Esc завершает режим. Запасной путь — выбор из списка построек с фильтром по типу и расстоянию до терминала. Референс механики — привязка построек к целям в Satisfactory Build Calculator (клавиши F6 и L).
- **Автоматическое определение** (по связности конвейеров и труб) — в будущей версии; поле `source` заложено заранее.
- Демонтированная постройка удаляется из линии при ближайшем обновлении индекса, линия не ломается.
- Линии хранятся в состоянии мода в сохранении (§10). Модель линии только читает (`list_lines`, `get_line`): привязка требует указать постройки в мире, это ручная операция (§7.5, правило 6).

**Привязка плана (v1.3, FR-14).** После расчёта игрок привязывает группы плана к конкретным машинам или к линии: в `ProductionPlan` у группы появляется `binding` (`lineId` или список `buildingId`). Для привязанных групп телеметрия даёт фактическую скорость и загрузку, а мод вычисляет отношение факта к плану и узкое место — группу с наименьшим отношением. Это вычисленный показатель, а не рекомендация.

**Настройки машин только отображаются.** Такт, Power Shards и Somersloops привязанных машин показываются (в том числе ползунком), но мод их не меняет: ручных операций, изменяющих мир, в v1.0 нет.

## 5.8 `Note`

Контракт заметки закладывается с запасом под богатые заметки, а v1.0 использует только текст. Поля: `schemaVersion`, `id`, `saveId`, `title`, `format`, `body`, `createdAt`, `updatedAt`; зарезервированы: `tags`, `category`, `priority`, `pinned`, `archived`, `links` (на линии и планы), `reminders`. Пример — `contracts/note.example.json`.

- **v1.0:** `format` = `plain`, только заголовок и текст. Зарезервированные поля схема допускает, но Validator v1.0 отклоняет их с кодом `NOTE_FIELD_NOT_SUPPORTED`, чтобы ни UI, ни модель не создали данные, которые v1.0 не умеет показать.
- **Будущие версии:** `format` = `markdown` (заголовки, списки, чекбоксы, ссылки, код), изображения, теги, категории, архив, закрепление, поиск, связи с линиями и планами, напоминания. Время напоминаний (игровое или реальное) решается вместе с ними.
- Текст заметки, как и раньше, передаётся модели как данные, а не как инструкции (§7.3).

# 6. Интерфейсы игрока и UX

## 6.1 AI Terminal (v1.0)

Строительный объект и единственный хост экранных модулей в v1.0. По E открывает интерфейс терминала: навигация между экранными модулями (§6.3) во весь экран. У физического экрана два режима: лёгкий world-display (render target, обновляется по изменению, §6.6) и полный интерактивный UMG при открытии. Настройка терминала хранится как ссылка `terminalId → screenId`, не как копия разметки.

**Питание.** Терминал подключается к электросети как обычная машина и потребляет **10 MW**. Поведение без питания (согласовано): экран в мире гаснет и не рендерится, по E открывается только статус «нет питания». Данные мода (заметки, экраны, Work Orders) от питания конкретного терминала не зависят и не теряются; сбор телеметрии продолжается, потому что он не привязан к терминалу.

## 6.2 AI Assistant (v1.4)

Экипируемый предмет — второй хост тех же экранных модулей (ADR-001). Крафтится обычным игровым способом и занимает стандартный ручной слот. ЛКМ открывает интерфейс, горячая клавиша переключает HUD. Критерий активности — «в активном слоте/выбран в руке», а не наличие в инвентаре: это даёт однозначное включение и скрытие HUD при переключении оборудования. Не зависеть от PowerSuit или сторонних расширений слотов.

**Компактная раскладка.** У терминала (большой экран, мышь, игрок стоит) и у экипировки (быстрый доступ, возможно на ходу) разная эргономика. Поэтому модули с первого дня адаптируются к размеру, который им сообщает хост, а не рассчитаны на один экран терминала. Для пользовательских экранов раскладку задаёт пресет: `slots-3` для терминала, `hud-compact` или `slots-1` для экипировки (поле `layout` в `ScreenDefinition`).

## 6.3 Экранные модули

Каждый экран — самостоятельный модуль с интерфейсом `IScreenModule`, который открывается в любом хосте (ADR-001). В v1.0 все модули живут в AI Terminal; в v1.4 те же модули без доработки откроются в AI Assistant.

Карта фабрики и быстрые предупреждения — в будущих версиях | v1.0 |

**Требования к модулю:** не зависеть от конкретного хоста; получать контекст (`saveId`, размер и раскладку, фокус ввода) только через интерфейс хоста, а данные и операции — только через публичный API мода (§3.6), без прямого доступа к подсистемам; адаптироваться к размеру; хранить своё состояние в состоянии мода (§10), а не в хосте; жить в модуле `FicsitAIUI` без зависимостей от игры, чтобы открываться в Screen Lab (§13, ADR-026). Переиспользование проверяется до появления второго хоста: в автотестах каждый модуль открывается в тестовом хосте (Spike S1, AC-14).

## 6.3.1 Вариант реализации: веб-экраны во встроенном браузере (ADR-032, предложено)

**Предложение.** Экранные модули и рендерер `ScreenDefinition` пишутся на вебе (HTML/CSS/JS) и показываются в игре встроенным браузером на Chromium (CEF) через плагин [BLUI](https://github.com/getnamo/BLUI) (форк getnamo, MIT), который поставляется **отдельным модом-библиотекой** «FicsitAI Web Runtime». Решение не принято: оно зависит от Spike S8. До его результата базовым планом остаётся UMG.

**Почему не браузер движка.** Проверено 09.11.2026 в установке игры: каталогов `Engine\Binaries\ThirdParty\CEF3` и `Engine\Plugins\Runtime\WebBrowserWidget` нет, в `FactoryGame.uproject` плагина тоже нет — Coffee Stain CEF не поставляет. Собрать модуль WebBrowser движка внутри мода нельзя: это исходники Unreal Engine, а выкладывать их в наш публичный GPL-репозиторий лицензия Epic не разрешает. BLUI — самостоятельный плагин без кода движка.

**Что даёт BLUI** (проверено по репозиторию 09.11.2026): MIT, последний коммит 24.09.2026, поддержка UE 5.8, CEF 128. Рендер без окна (offscreen) в текстуру материала, обновление только при перерисовке страницы — подходит и для интерактивного экрана, и для render target терминала. Мост в обе стороны: выполнение JavaScript из игры и событие `blu_event` со страницы в UE. Локальные страницы по `local://`. С версии 5.1.0 его CEF переименован (`blucef.dll`) и не конфликтует с CEF движка в том же процессе. Рендер программный (`disable-gpu`): для дашбордов достаточно, для анимаций дорого. Бинарники CEF — в релизах, не в репозитории.

**Почему архитектура к этому готова.** По ADR-023 экраны — клиенты публичного API и не обращаются к подсистемам напрямую. Веб-экран — ещё один такой клиент: мост BLUI передаёт вызовы между JavaScript и UE, и страница вызывает те же операции и подписывается на те же события, что и UMG-экран. Интерфейс `IScreenModule` сохраняется, меняется только реализация: «страница плюс мост к API».

**Что даёт.**

- **Объём UI — главный риск (R-16).** Паритет ручного пути делает объём UI пропорциональным числу операций, а UMG в C++ многословен (это признаёт документация SML). Веб-экраны с готовыми библиотеками графиков, таблиц и карт пишутся заметно быстрее.
- **Screen Lab упрощается до обычного браузера** с горячей перезагрузкой на тех же источниках Fixture, Recording и Save (§8.5); R-22 (сборка движка Coffee Stain) для экранов перестаёт существовать.
- **Те же экраны вне игры** — на втором мониторе или телефоне через адаптер, без второй реализации.
- **Экран в мире:** браузер UE рисует страницу в текстуру, то есть прямо в render target меша терминала (§6.6).
- **Рендерер `ScreenDefinition` и карточки чата** проще на вебе. Белый список виджетов сохраняется: модель по-прежнему не присылает HTML (ADR-005).

**Условия, без которых вариант не принимается.**

1. **BLUI загружается под SML в готовой игре** — как плагин мода-библиотеки, с бинарниками CEF в его каталоге; менеджер модов ставит библиотеку как зависимость основного мода. Публичных модов Satisfactory со встроенным браузером не найдено, так что это главный вопрос S8. **Размер поставки ограничением не считается** (решение 09.11.2026): CEF добавляет порядка 150–200 МБ, порог не вводится. Отдельный мод-библиотека нужен не ради размера, а чтобы CEF обновлялся независимо от основного мода; цель §1.1 «нет обязательных сторонних модов» не нарушается — библиотека наша.
2. **Работа без сайдкара (FR-10).** Страницы не раздаются адаптером: статика лежит в моде и грузится локально, данные идут через привязку JavaScript к `FicsitAIApi`, а не по HTTP.
3. **Изоляция.** Навигация только по локальным страницам мода; внешние URL, сторонние скрипты и загрузка удалённого кода запрещены.
4. **Бюджет процессов, памяти и процессора.** CEF поднимает свои процессы, а рендер в BLUI программный. Живой браузер — только у открытого интерактивного экрана и у ближайших терминалов; остальные терминалы показывают кэшированную картинку (§10.1).
5. **Proton — основная платформа проверки, а не дополнительная.** Под Proton запускается Windows-сборка, то есть CEF работает под Wine, а там он капризен (процессы песочницы, GPU). Программный рендер BLUI снимает часть проблем. Поскольку Windows-машины в команде нет (ADR-033), Proton — единственная среда, в которой S8 проверяется своими силами, а отрицательный результат в ней не отличим от поломки wine. Поэтому отклонению ADR-032 обязательно предшествует прогон сборки S8 у пилотного тестера на Windows.
6. **Ощущение игры:** фокус ввода, геймпад, стиль под интерфейс Satisfactory, одна система локализации для веба.

**Форма решения при успехе S8 — гибрид.** Каркас терминала (хост, нижняя полоса клавиш, состояние питания и инертности, §6.7) остаётся на UMG; экранные модули и рендерер `ScreenDefinition` — веб внутри каркаса. Модуль `FicsitAIUI` в этом случае содержит мост и веб-контейнер на BLUI, а страницы — отдельный фронтенд-проект в репозитории; BLUI вендорится в `third_party/blui/` и собирается в мод-библиотеку. Обновления CEF — постоянная работа, но срочность ниже обычной: страницы только локальные, в интернет браузер не ходит. **При провале S8** остаётся UMG, и ничего не теряется: граница API та же.

Альтернативные HTML-движки вместо CEF (например, Ultralight) легче, но проприетарны: их пришлось бы вписывать в `LICENSE.EXCEPTION` рядом с GPL. Не рассматриваются.

## 6.4 Представление производственного плана: обёртка

Решение изменено (ADR-007). Экраны Planning и Graph в v1.0 — **стандартизированные обёртки**, к которым позже подключается внешний UI плана; собственной таблицы и раскладки графа в v1.0 нет.

- **Интерфейс представления** (`IPlanView`): получает `ProductionPlan` и состояние расчёта, отправляет `PlanRequest` через операцию `compute_plan`, сообщает о выборе узла или группы. Данные и операции — только через обёртку, никакого прямого доступа к планировщику.
- **Заглушка v1.0** показывает статус «планировщик не подключён» и не выставляет модели инструменты планирования (правило паритета, §7.5).
- **Кандидаты UI:** виджет графа SBC (`SBCCalculatorWidget`, pan/zoom, около 1600 строк) в паре с ядром SBC; собственная таблица и послойный граф в UMG. Интерактивный редактор графа (бывшая v1.4) — возможность подключаемого UI, а не отдельная версия.
- Виджет `production_graph` в пользовательских экранах (§5.3) рисуется через тот же `IPlanView`; пока подключена заглушка, он показывает статус «не подключено».

## 6.5 HUD (v1.4, вместе с AI Assistant)

Набор маленьких прозрачных виджетов, а не второй независимый UI: текстовые подсказки, задачи, показатели мощности, мини-представление плана, временные графики, уведомления. Готовые профили `minimal`, `production`, `power`, `work-order`; виджеты включаются, скрываются и переставляются. Управление — назначаемыми клавишами и инструментом `set_hud_profile`. HUD локален игроку и активен, пока AI Assistant выбран в руке, поэтому выходит вместе с ним.

## 6.6 Экран в мире

Решение упрощено относительно 1.0-draft. Прежняя схема (внешний рендер PNG, доставка клиенту по подписанному адресу, запрет на создание текстур на DS) существовала из-за headless-сервера. В одиночной игре композиция рендерится в **render target** в том же процессе и применяется к материалу меша терминала — штатный приём UE, без внешнего сервиса и без пайплайна изображений.

Обновление — по изменению содержимого (`renderRevision`), не покадрово. Никаких высокочастотных стримов. Терминал без питания экран в мире не рендерит. Подход Image Screens остаётся референсом на случай нетривиальностей с материалом, но зависимостью не является.

**Ассет терминала входит в объём v1.0** (ADR-030). Модель командного центра разрабатывается в ветви `art/command-center`, владелец — Co3. К моменту этой редакции ветвь прошла stage 7: game-ready сборка (LOD0 с коллизией UCX, LOD1 и LOD2, разделение exterior / interior / holo, сокеты, меш под render target, отчёты по масштабу и UV), экспорты для UE, скрипт импорта, карта материалов и проверка против API SML 3.12 и UE 5.6. Работа продолжается, поэтому состав ассета здесь не фиксируется — фиксируется одно его следствие для контрактов.

**Ограничение 16:9.** Все экранные поверхности меша приведены к соотношению 16:9 ради того, чтобы одна текстура подходила любому экрану модели. Для архитектуры это значит:

- **На экране в мире рисуется содержимое модуля и верхняя полоса статуса, без бокового рельса и полосы клавиш** (решение 10.11.2026 по Co3-2). Полоса статуса — единственное, что имеет смысл читать с расстояния: мощность, связь, активные линии. Рельс и подсказки клавиш суть органы ввода, которого у меша нет, а рельс при 1920 занимает девятую часть ширины. При `bWorldSurface = true` хост их не создаёт.
- **Render target экрана в мире — 16:9.** Пресеты `layout` из §5.3 должны компоноваться в этом соотношении; пресет, рассчитанный на другую пропорцию, в мире обрезается или получает поля, и это надо увидеть на этапе редактора экранов, а не в игре.
- **Интерактивный UMG по E ограничением не связан:** он открывается в разрешении окна игры, а не на меше. Один `ScreenDefinition` обслуживает оба случая, поэтому редактор Screens показывает предпросмотр в обеих пропорциях.
- Проверка пресетов на 16:9 — задача Screen Lab (§13): у него уже есть выбор размеров хоста, и к ним добавляется размер экрана в мире.

Поскольку ассет ещё в работе, его интеграция идёт отдельным треком и не блокирует v0.1: вертикальному срезу достаточно меша-заготовки с правильной пропорцией экрана.

**Ветвь `art/base-nodes` в объём v1.0 не входит** (решение King 09.11.2026). В ней голограммные меши узлов и связей между ними — задел под отображение производственных цепочек в будущих версиях, конкретная версия не определена. На экраны v1.0, контракты и пропорцию render target она не влияет; владелец, как и у ассета терминала, — Co3.

## 6.7 Каркас терминала

Общие элементы хоста, одинаковые для всех экранных модулей (концепт — `concepts/`):

- **Боковое меню:** Обзор, Планировщик, Производство, Логистика, Статистика, Чат с ИИ, Задачи, Записки, Настройки; плюс Lines и Screens. Пункты будущих версий скрыты, пока раздел не реализован (Логистика до v1.5); Планировщик до v1.3 открывает заглушку.
- **Верхняя полоса статуса:** состояние телеметрии и связи с сайдкаром, мощность (потребление к производству), активные линии, загрузка фабрики. Источник — телеметрия (§8.2), модель не участвует.
- **Нижняя полоса:** горячие клавиши текущего экрана (R — обновить, F — фокус на объекте, C — экспорт или копирование, Esc — назад). Место для счётчика предупреждений зарезервировано под будущую систему оповещений.
- **Экспорт данных** (CSV) из отчётов — ручная операция, без изменения мира.

# 7. Граница доверия LLM

Эта граница — главная причина, по которой authority-слой сохраняется в одиночной игре. Отказ от мультиплеера снял угрозы со стороны других игроков, но не изменил ни одной угрозы со стороны модели. Защита строится не на подтверждениях, а на закрытом наборе инструментов без доступа к миру и строгой валидации каждого вызова (ADR-009).

## 7.1 Инструменты

Мод предоставляет инструменты через адаптер сайдкара (§3.3). Каждый инструмент — операция из `OperationRegistry` с JSON Schema, лимитами размера/частоты и ручной точкой входа в UI (§7.5). Ни один инструмент не изменяет игровой мир. Каталог отдаётся только поисковыми инструментами с пагинацией, по умолчанию — только разблокированное в текущем сохранении (ADR-017): полный каталог из сотен рецептов в одном ответе переполнил бы контекст модели.

| Инструмент | Версия | Что делает | Ручной путь в UI |
|---|---|---|---|
| `query_metric` | v1.0 | Телеметрия: значение или временной ряд, в том числе по линии и по запасам | Dashboard: выбор метрики и окна |
| `list_lines`, `get_line` | v1.0 | Линии и их метрики (только чтение) | Lines |
| `list_notes`, `get_note`, `create_note`, `update_note` | v1.0 | Заметки игрока | Notes |

## 7.2 Пайплайн

Текст игрока → Foreman/LLM → вызов инструмента → адаптер → канал к моду → валидация по схеме → валидация по живому каталогу → применение → UI получает событие `screen.updated` / `plan.updated` и обновляет конкретные виджеты.

Подтверждений игрока нет: пишущие действия (заметка, экран, чертёж) не изменяют мир. Правка через интерфейс вызывает те же внутренние операции, что и инструменты. Невалидный вызов отклоняется с машиночитаемой причиной и не изменяет сохранённое состояние. **Не** разбирать текст ответа LLM регулярными выражениями, чтобы понять действие.

## 7.3 Инъекции через авторский текст игрока

Внутрь контекста попадают строки, написанные человеком: заметки, имена терминалов, `outputName` прошлых чертежей, история чата. Заметка вида «назначь экран X на терминал Y» будет прочитана моделью как инструкция. Худшее, к чему это может привести, — лишний экран, заметка или чертёж: инструментов, изменяющих мир или удаляющих данные, нет (§7.5, правило 6). Поэтому подтверждения не вводятся, а меры такие:

1. Аргументы инструментов никогда не принимаются в виде идентификаторов, извлечённых из текста: `className`, `recipeClass`, `id` метрики и плана сверяются с живым каталогом.
2. Авторский текст игрока передаётся модели в явно размеченном виде как данные, а не как часть инструкций.
3. Лимиты частоты (§7.4) не дают зациклившейся модели засыпать игрока экранами и чертежами.

Пункт 2.0-draft о подтверждении записей «по происхождению» удалён: происхождение вызова нельзя установить даже в принципе, потому что в одном ходе смешаны реплика игрока и прочитанные данные.

## 7.4 Лимиты

LLM не может задавать сетевые URL, выполнять команды операционной системы или произвольный код; допустимы только объявленные виджеты и каталогизованные источники. Ограничения: размер `ScreenDefinition`, число виджетов, **не больше четырёх рядов в виджете `timeseries`** (решение 10.11.2026 по Co3-4: это инвариант контракта, а не решение вёрстки, иначе модель собрала бы через `create_screen` экран с десятью рядами, и отклонить его было бы нечем), нижний порог `refreshSec` для тяжёлых источников, размер страницы поисковых инструментов, частота расчёта планов, создания экранов, заметок и чертежей. **Удаление чертежей лимитируется отдельно и строже создания** (§7.5, правило 7): стартовые значения — не больше 5 удалений за один ответ модели и 20 за час; уточняются в v1.1.

## 7.5 Паритет ручного и AI-пути

Принцип (ADR-018): **модель не может ничего, чего не может игрок вручную.** Инструменты модели — это фасад над теми же операциями, которые вызывает UI. Это делает помощника ускорителем, а не единственным способом что-то сделать, и сужает поверхность атаки: модели доступно только то, что уже доступно игроку.

Правила:

1. **Одна операция — два входа.** Каждый инструмент из §7.1 — операция `OperationRegistry` с ручной точкой входа (форма, кнопка, экран). UI и модель передают одинаковые аргументы (один контракт: `ScreenDefinition`, `BlueprintRequest`, `PlanRequest`) и проходят один и тот же `Validator`.
2. **Реестр — единственный источник описаний инструментов.** Адаптер получает их от мода, а не хранит свои. Тест сборки падает, если операция выставлена модели без ручной точки входа.
3. **Одинаковый результат.** Объект, созданный моделью, — обычный объект мода: экран открывается в редакторе Screens, заметка — в Notes, Work Order — в Work Orders, чертёж — в библиотеке, план — в Planning. Игрок правит его вручную так же, как созданный им самим.
4. **Ручной путь не зависит от LLM.** Операции мода работают и без сайдкара (FR-10); операции планирования — без сайдкара, если подключён провайдер в моде. Work Orders живут в Foreman, поэтому их ручной путь требует запущенного сайдкара, но не LLM: формы экрана Work Orders → адаптер → REST Foreman.
5. **Версии.** Инструмент появляется не раньше своего ручного пути (§1.2).
6. **Обратное не требуется.** Не каждая ручная операция становится инструментом: удаление заметок, экранов и планов, настройки клавиш и конфигурация остаются только ручными. Это дополнительно ограничивает возможный вред от модели (§7.3).
7. **Удаление — только для чертежей библиотеки** (решение 2.2-draft). Модель создаёт и удаляет чертежи в библиотеке мода; экраны и заметки она создаёт и правит, но не удаляет. Границу определяет восстановимость: чертёж описывается `BlueprintRequest` и пересоздаётся тем же вызовом за секунды, а текст заметки, написанный игроком, не восстановим ничем. Для `delete_blueprint` поэтому действуют дополнительные правила: удаляются только чертежи, созданные через мод (чужие и построенное в мире недоступны), операция идемпотентна по `requestId`, удалённое попадает в корзину мода (последние 20 удалённых чертежей, старые вытесняются; восстановление — вручную в библиотеке; хранение — §10), а лимит §7.4 на удаления строже, чем на создание.

**Пример: чертёж из n плавилен.** Вручную: Blueprint Builder → машина «Плавильня», рецепт «Железный слиток», количество n, коллекторы и питание, имя → «Предпросмотр» (`PreviewResult` с потоками, габаритами и предупреждениями) → «Создать». Быстрее, когда планировщик подключён: у группы плавилен в плане кнопка «Чертёж» заполняет ту же форму машиной, рецептом и количеством из группы. Через модель: фраза в чате → `preview_blueprint` → `request_blueprint_creation` с тем же `BlueprintRequest`. Во всех трёх случаях вызывается одна операция, и результат одинаков.

**Пример: график мощности.** Вручную: Статистика → метрика `power.consumption`, окно 15 минут. Через модель: `query_metric` возвращает ряд, и модель отвечает текстом, показывает график карточкой в чате через `show_card` или ставит его на пользовательский экран через `create_screen` — везде тот же виджет `timeseries`, что игрок добавляет в редакторе Screens. Всё это — v1.0.

## 7.6 Карточки в ответах модели

Решение (ADR-021): ответ модели — текст плюс **карточки из белого списка**, которые модель выводит инструментом `show_card`. Foreman не меняется: это обычный инструмент мода через адаптер.

- **Карточка — это один виджет** того же белого списка, что и в `ScreenDefinition` (§5.3): `metric`, `timeseries`, `table`, `text`, `production_graph`, `line` — карточка производственной линии. Виджеты `notes` и `work_orders` в карточках не используются: у чата для них есть собственные экраны. Отдельного рендеринга нет: чат использует те же виджеты, что Статистика и Screens.
- **Два вида данных.** Карточка со ссылкой (`source`: метрика, линия, план) показывает живые значения мода — модель не может ошибиться в цифрах. Карточка с данными (`data`: заголовки и строки таблицы, текст) несёт значения модели — например, прогноз «до/после» или требования для разблокировки; она помечается в UI как «оценка ассистента».
- **Валидация** как у любой операции: схема (`contracts/schemas/chat-card.schema.json`), лимиты на размер и число карточек в ответе, сверка `source.id` с живым каталогом метрик, линий и планов.
- **Паритет:** ручной аналог каждой карточки — тот же виджет на экране Статистика или в редакторе Screens (ссылочная карточка — виджет с тем же источником, карточка с данными — статический виджет).
- Карточки хранятся вместе с историей чата у Foreman как результат вызова инструмента; при повторном открытии ссылочные карточки показывают текущие значения.

**Позже:** ссылки на живые данные прямо в тексте (`[[metric:power.consumption]]`) — модель не пишет цифры вообще, мод подставляет значение. Требует научить модель формату через system prompt Foreman, который мы не меняем, поэтому отложено.

# 8. Данные и вычисления

## 8.1 Каталог из игры

`CatalogProvider` собирает каталог из двух источников в том же процессе. **Состав** — `UModContentRegistry` из SML: документированное перечисление рецептов, предметов и схем, включая зарегистрированные модами, плюс `IsRecipeVanilla` и событие `OnRecipeRegistered` (§5.1). **Разблокировки и числовые параметры** — `AFGRecipeManager` и связанные подсистемы напрямую. Это охватывает альтернативные и корректно зарегистрированные модовые рецепты и даёт точный ответ на вопрос «можно ли использовать это прямо сейчас». Слой данных SBC остаётся источником нормализации и числовых констант, но не перечня: перебор реестра — забота SML, и дублировать её не нужно.

Отправная точка реализации — слой данных SBC (`FSBCProductionData::SynchronizeRuntimeRecipes`): он уже обходит `AFGRecipeManager::GetAllRecipes`, читает продукты, ингредиенты, длительность и машины рецептов и подхватывает рецепты других модов в рантайме. `CatalogProvider` становится единственным владельцем этих данных уже в v1.0: на него опираются валидация экранов и метрик, Dashboard, а позже — провайдеры планировщика (§8.3) и Blueprint Builder.

Прежняя схема с `getRecipes`/`getSchematics` из FRM устранена, и вместе с ней — необходимость сверять два источника. Бывший R-03 (`getRecipes` возвращает и закрытые рецепты) закрыт не обходным путём, а исчезновением второго источника.

## 8.2 Телеметрия

`TelemetrySampler` собирает фактические значения из игровых подсистем. Состав v1.0 (FR-15):

- **Энергия:** производство, потребление, ёмкость и резерв по сетям; генераторы по типам (в работе, ограничены, отключены); топливо в генераторах и запас по времени; заряд батарей и время до разряда; пики потребления; время работы сети без срабатывания предохранителя; стабильность сети (определение метрики фиксируется в Spike S3).
- **Ресурсы:** добыча и потребление по предметам, баланс и тренд; запасы на складах и их заполнение; прогноз «на сколько хватит» при текущем балансе.
- **Линии (§5.7):** число машин, активные, загрузка (фактический выпуск к номинальному), выпуск по продуктам; настройки машин (такт, Power Shards, Somersloops) — только чтение.
- **Производство:** общий выпуск и его динамика; машины по типам (плавильни, конструкторы, ассемблеры и т. д.) с загрузкой.
- **История:** **в пределах текущей сессии игры**, в памяти мода, без персистентности. Окна графиков v1.0 — 5, 15 и 60 минут от момента запуска. Персистентный ряд за 24 ч с понижением разрешения перенесён в v1.1 (§1.2).
- **Логистика (v1.5):** поезда и станции, грузовики и автостанции, дроны и дрон-порты, конвейеры (загрузка участков), хранилища как узлы сети, задержки и потоки ресурсов между узлами. Объём этой телеметрии оценивается отдельно до начала v1.5 (R-05).

Значения несут источник (`source`: `live`, `planned`, а при работе вне игры — `save`, `save-estimated`, `recorded`, `fixture`, §8.5), временную метку, единицу, точность и scope.

**Решение об объёме (2.2-draft).** История за 24 ч вынесена из v1.0 — это принятое решение, а не отложенная задача. Две причины сложились. Первая: **референса больше нет.** Структура данных фабрики нетривиальна, FRM знает, где в подсистемах что лежит, но его код использовать нельзя — лицензии у проекта нет (§2.2). Телеметрия становится самым большим собственным модулем v1.0, причём пишется вслепую. Вторая: персистентный ряд — это не только сбор, но и хранение, ротация по `saveId`, понижение разрешения, миграции формата и бюджет на запись, то есть отдельная подсистема рядом с самой дорогой.

Что это даёт: AC-04 упрощается до окна сессии; из §10 уходит хранение и ротация ряда; **R-05 возвращается к уровню 2.0-draft** вместо выросшего; вертикальный срез v0.1 не затрагивается вообще — Dashboard и `show_card` работают без изменений, `timeseries` просто короче. Что теряется: после перезапуска игры графики начинаются заново, и сравнить «сегодня против вчера» в v1.0 нельзя.

Из FRM остаётся законная часть: **наблюдать, какие поля он отдаёт по своему публичному API**, и использовать это как перечень того, что вообще имеет смысл собирать. Поиск подсистем делается самостоятельно по заголовкам игры.

**Референсы из экосистемы FRM** (проверено 09.11.2026, §18). Все проекты ниже — внешние программы поверх HTTP API FRM; ни один не становится зависимостью или источником кода, у двух главных лицензии нет. Используются только как перечни — та же граница, что для самого FRM:

- **Что собирать.** В README FRM Companion — 71 метрика с метками. Это самый полный в сообществе ответ на вопрос «что вообще имеет смысл собирать»: батареи (процент, время до разряда и до заряда), срабатывание предохранителя, мощность против максимума по типам потребителей, загрузка машин в процентах, входные и выходные буферы машин, производство и потребление по предметам против мощности, Resource Sink, поезда, дроны и транспорт. Перечень служит чек-листом каталога метрик v1.0 и v1.5. Он отвечает на «что», но не на «где лежит в подсистемах», поэтому телеметрия по-прежнему пишется без референса кода, хотя уже не вслепую по составу.
- **Правила предупреждений** (для будущей версии, §1.2) — из сборки satisfactory-monitoring: батарея разряжена и разряжается, сработал предохранитель, потребление на пределе мощности, перерасход, недопроизводство, сход поезда.
- **Группировка по квадратам сетки** (дашборд Factory Production там же) — дешёвая первая эвристика для автоматического определения линий.
- **Перевод игровых координат в координаты карты** (`MapProjections.md` там же) — референс для карты фабрики на «Обзоре» и Логистики v1.5; формулы пересчитываются заново под наш виджет карты.

**Нагрузка на GameThread остаётся риском и меняет только форму.** HTTP-раунд-трипа больше нет, но тяжёлая агрегация по подсистемам в игровом потоке каждый тик просадит FPS так же надёжно, как частый опрос FRM. Правила:

- Сбор по расписанию, не по запросу UI; UI читает последний снапшот.
- В GameThread выполняется только снятие значений; агрегация, расчёт производных и сглаживание — на воркере.
- Предлагаемые интервалы до измерения: мощность 2–5 с, агрегаты фабрик 5–15 с, каталог только по событию изменения.
- Кольцевой буфер временных рядов в памяти мода. В v1.0 он **не персистится**: ряд живёт столько, сколько сессия (решение выше). Запись в локальные файлы по `saveId` появляется вместе с историей 24 ч в v1.1 (§10).
- **Индекс построек** обновляется по событиям строительства и демонтажа, а не полным обходом мира каждый цикл.
- **Сбор нарезается по кадрам:** склады, генераторы и машины обходятся порциями в пределах бюджета кадра, а не все разом.
- Тяжёлые метрики (запасы на складах, баланс ресурсов) собираются реже — предлагаемый интервал 15–30 с.
- **Порог устаревания значения — `max(3 × SampleIntervalSec, 10 с)`, а не единое число** (решение 10.11.2026 по Co3-3). Фиксированные 30 с помечали бы мощность свежей, когда она устарела вшестеро, и склады устаревшими, когда они в норме. Интервал каждой метрики приходит в её описании через API, поэтому UI считает порог сам; переопределение — одним множителем в настройках.
- **Частота обновления виджета не выше частоты данных.** В 1.0-draft HUD обновлялся «1–2 раза/с» при данных раз в 2–5 с, то есть перерисовывал интерполяции устаревших чисел. Виджет показывает значение с метаданными свежести и перерисовывается при поступлении нового снапшота.

## 8.3 Планировщик: стандартизированная обёртка

Решение изменено (ADR-013). В v1.0 мод содержит не планировщик, а **обёртку** `PlannerGateway`, к которой позже подключается внешний планировщик. Вместе с обёрткой UI плана (§6.4) это позволяет выбрать и сменить реализацию, не трогая экраны, инструменты модели и контракты.

**Состав обёртки:**

- **Контракт:** `PlanRequest` → `ProductionPlan` или ошибка с кодом (§5.2). JSON Schema обоих — в `contracts/schemas/`.
- **Интерфейс провайдера** (`IPlannerProvider`): `ComputePlan(PlanRequest)`, `Capabilities()` — что провайдер умеет (альтернативы, Power Shards, Somersloops, ограничения на сырьё, баланс побочных продуктов, циклы, оптимизация). Обёртка отклоняет запрос, требующий отсутствующей возможности, с кодом `PLANNER_CAPABILITY_MISSING`.
- **Каталог:** провайдер получает данные только из `CatalogProvider` (§8.1), то есть считает по рецептам, реально разблокированным в текущем сохранении. Это сохраняет закрытым бывший R-04 (расхождение live-данных и статического графа). Провайдер в сайдкаре получает снимок каталога через адаптер.
- **Где живёт провайдер:** в моде (C++, работает без сайдкара — FR-10 выполняется) или в сайдкаре за адаптером (тогда планирование требует запущенного сайдкара, но не LLM).
- **Операции:** `compute_plan` и `get_plan` в `OperationRegistry` вызывают обёртку; планы сохраняются в состоянии мода (§10) независимо от провайдера.
- **Заглушка v1.0:** провайдер, который на любой запрос отвечает `PLANNER_NOT_CONNECTED`. Экраны Planning и Graph показывают статус «планировщик не подключён», инструменты планирования модели не выставляются.
- **Тестовый провайдер:** в автотестах через обёртку проходит фиктивный провайдер, который возвращает `contracts/plan.example.json`. Так контракт и обёртка проверяются до появления настоящего планировщика.

**Кандидаты провайдера** (поиск 05.11.2026):

| Вариант | Где работает | Оценка |
|---|---|---|
| **Ядро Satisfactory Build Calculator** | В моде, C++, SML 3.12, MIT | **Кандидат; порядок против линейной системы — по Spike S3** (см. ниже). `FSBCProductionCalculator` строит дерево от цели вниз с учётом такта, Power Shards, Somersloops и генераторов, данные из live-каталога; ядро отделено от виджета. Ограничения: побочные продукты не сводятся в баланс (`BYPRODUCT_NOT_BALANCED`), на цикле — ошибка `RECIPE_CYCLE_UNSUPPORTED`. В паре с ним — виджет графа SBC как UI (§6.4) |
| **Линейная система на Eigen** | В моде, C++, MPL-2.0 | **Второй кандидат, добавлен в 2.2-draft.** Снимает оба ограничения SBC, и для этого LP-решатель не нужен — см. разбор ниже. Объём: сборка матрицы стехиометрии плюс решатель, который либо берётся готовым, либо пишется в несколько десятков строк |
| LP-модель на HiGHS | В моде, C++, MIT | Нужна **не** для циклов и байпродуктов, а только для автоподбора альтернатив и минимизации сырья — это вне объёма v1.x. Библиотека, а не готовый планировщик |
| Планировщик Foreman (`ingredient_tree`, `full_production_line`) | Сайдкар, TS, Apache-2.0 | Статические данные, не знает разблокировок; нужен запущенный сайдкар |
| FactorioLab | Браузер, Angular | LP через GLPK (GPL), статические данные, привязка к Angular |
| KirkMcDonald satisfactory-calculator | Браузер, JS, Apache-2.0 | Свой симплекс, последний коммит 10.2024 |
| ERP for Factory Games | Хостинг, .NET, OR-Tools | Тяжело для локального мода |
| SatisfactoryTools | Браузер, удалённый API | Офлайн не работает |
| Ficsit Companion | Десктоп, C++ | Ручной узловой редактор без решателя |
| satisfactory-solver (kiligir) | Django, HiGHS | Нет лицензии |

**Почему для циклов и байпродуктов не нужен LP** (ADR-028, вставка из линии 3.0-draft). Редакция 2.1-draft назначала решением ограничений SBC провайдера на HiGHS. Это переоценка задачи, и причина — в самом контракте `PlanRequest`: **альтернативные рецепты выбирает игрок** (`selectedAlternates`). При фиксированном наборе рецептов задача линейна:

- неизвестные — интенсивности выбранных рецептов и излишки побочных продуктов;
- **правило «один рецепт на предмет»:** каждый промежуточный предмет балансирует ровно один выбранный рецепт; сырьё — свободный вход (`rawInputs`);
- для каждого предмета, кроме сырья, записывается балансовое уравнение;
- побочный продукт, у которого нет потребителя или который производится сверх спроса, получает переменную излишка `s ≥ 0`;
- решается система `A·x − s = d` при `x ≥ 0`, `s ≥ 0`, где `A` — матрица стехиометрии.

Деревья, побочные продукты и циклы (переработанные пластик и резина) выпадают из одного и того же решения, потому что **цикл в матрице — это просто записи в обе стороны.** «Нет решения» и «недоопределено» становятся диагностируемыми состояниями, а не специальными случаями в коде. LP и MILP начинают требоваться ровно там, где появляется выбор: автоподбор альтернатив, минимизация сырья или энергии, несколько рецептов на один продукт. Это вне объёма v1.x, и постановка при их появлении не меняется — меняется только решатель.

**Отрицательная интенсивность чаще означает излишек, чем неразрешимость** (исправлено 09.11.2026). Типичный случай — Heavy Oil Residue: побочный продукт рецептов Plastic и Rubber перекрывает спрос Residual Fuel, и рецепт, балансирующий HOR, получает отрицательное значение. План при этом выполним: этот рецепт надо выключить, а предмет перевести в излишек. Поэтому провайдер работает по активному множеству:

1. решить систему;
2. рецепт с отрицательной интенсивностью, чей предмет производится где-то ещё как побочный, зафиксировать на нуле, а предмет перевести в излишек;
3. решить заново; число итераций ограничено числом рецептов.

Диагноз `SYSTEM_INFEASIBLE` с перечнем виновных рецептов в `scope` остаётся только для отрицательной интенсивности, которую излишком не объяснить: выбранный набор рецептов не может дать цель. Излишек возвращается в плане предупреждением `BYPRODUCT_NOT_BALANCED` с количеством — игроку нужно его куда-то девать (склад, AWESOME Sink). Если на реальных планах активное множество не сходится, следующий шаг — NNLS или LP на HiGHS; постановка задачи при этом не меняется.

**Следствие для R-14 и для приоритета v1.3.** Риск закрывается постановкой задачи, а не интеграцией решателя, и линейный провайдер оказывается дешевле адаптации калькулятора SBC — при этом сразу без `RECIPE_CYCLE_UNSUPPORTED`. `BYPRODUCT_NOT_BALANCED` у него меняет смысл: это не ограничение провайдера, а сообщение об излишке. Порядок подключения в v1.3 выбирается по результату Spike S3: если слой данных SBC и так вендорится, его калькулятор даёт работающий план быстрее, но остаётся промежуточным шагом; если нет — линейный провайдер становится первым.

**Адаптация ядра SBC при подключении** (код в `third_party/sbc/` с перечнем патчей, §2.2): вход из `CatalogProvider` вместо собственных `Data/*.json`; выход — наш `ProductionPlan`; отвязка от локализации SBC (`ESBCLanguage`); закрытый рецепт даёт `RECIPE_LOCKED`.

Планировщик Foreman моделью не используется: адаптер не включает его инструменты в белый список (§3.3), и `compute_plan` остаётся единственным источником расчёта.

## 8.4 `plannedRate` против `actualRate`

Две независимые величины: `plannedRate` = рецепт × число машин × такт; `actualRate` = наблюдаемое в игре. В таблице, графе и HUD не смешивать без подписи. Числа считает мод (планировщик и телеметрия); LLM только объясняет результат.

## 8.5 Источники данных API

Решение (ADR-025): публичный API (§3.6) работает поверх сменного **источника данных** (`IFicsitAIDataSource`). Экраны и другие клиенты не знают, откуда пришли данные: каждое значение несёт `source`, и экран показывает его в метке свежести.

| Источник | Где работает | Что даёт | Ограничения |
|---|---|---|---|
| **Live** | В игре | Всё из §8.1–8.2, история по ходу сессии | Нужна запущенная игра |
| **Save** | В адаптере сайдкара, без игры | Снимок по файлу `.sav`: машины с рецептом, тактом и Somersloop, добытчики, генераторы и топливо, батареи и заряд, склады и содержимое, граф конвейеров и труб, электросети, разблокированные рецепты | Один момент времени. Скорости — номинальные (рецепт × такт × усиление, `source=save`) или оценочные установившиеся по решателю потоков Foreman (`save-estimated`). История — только по нескольким сохранениям (ротация автосохранений) |
| **Recording** | Без игры | Воспроизведение записи потока API (снимки и события) из живой сессии: история, события, переходы состояний | Только то, что было записано |
| **Fixture** | Без игры, в автотестах | Подготовленные наборы JSON: примеры контрактов и крайние случаи — пустая фабрика, фабрика на тысячи построек, сайдкар недоступен, заглушка планировщика, инертный режим MP, терминал без питания | Синтетические данные |

**Save — переиспользование, а не своя разработка.** Адаптер использует пакет Foreman `@foreman/sf-save-data` (Apache-2.0; нормализует `.sav` в модель `SaveState`) поверх парсера `@etothepii/satisfactory-file-parser` (MIT, обновлён 07.2026), а для оценки фактических скоростей — решатель потоков Foreman `sf-flow` (Apache-2.0). Адаптер переводит `SaveState` в снимок API в тех же контрактах, что и Live. У каждой постройки в сохранении есть устойчивое имя экземпляра — тот же кандидат на `buildingId`, что и в игре (§5.7), поэтому линии и привязки плана из сохранения совпадают с живыми (совпадение проверяется в Spike S3).

**Recording.** Мод по включённой в настройках диагностике (§6.9) пишет поток API в файл `JSONL` по `saveId` и сессии: периодические снимки и все события. Запись служит и для отладки экранов, и как приложение к отчёту об ошибке. Ключи, токены и текст чата в запись не попадают.

**Формат снимка API** — JSON в контрактах из `contracts/` плюс заголовок (`apiVersion`, `source`, `saveId`, время). Один формат у всех источников, поэтому любой экран можно открыть на любом из них.

# 9. Создание Blueprint (v1.1)

## 9.1 Ядро

Используется проверенное ядро Factory Spawner: `FBuildPlanGenerator::Generate(TArray<FFactoryCommandToken>)`. Чатовый ввод заменяется программным API, компоновка `single_row` ограничивается известными типами машин. Существующая реализация создаёт splitter/merger, pipe cross, belt/lift, power wire и пишет Blueprint через игровой subsystem.

**Главное упрощение относительно 1.0-draft.** Бывший R-01 состоял в том, что генератор опирается на `FirstPlayerController` и пишет чертёж в текущий subsystem, а на Dedicated Server локального игрока нет. В одиночной игре `FirstPlayerController` — это и есть игрок, и Factory Spawner именно так и работает сегодня. Spike D прежней редакции из «может опрокинуть архитектуру» превращается в обычную задачу интеграции.

## 9.2 Изменения в адаптированном ядре

Экспорт/обёртка программного API; идемпотентность по `requestId`; генерация уникального имени, не перезаписывающего чертежи `FactorySpawner`; валидация количества, класса, рецепта и разблокировки; проверка габаритов; расчёт нагрузки по лентам и трубам с предупреждением `MANIFOLD_RAMP_UP`; корректная обработка ошибок без частично связанных объектов; выяснение, применим ли `clockPercent` в самом чертеже (§5.4).

## 9.3 Ограничения v1.1

Только шаблонные ряды; ввод и вывод в отдельных коллекторах; раздельные входы для нескольких ингредиентов; питание; предлагаемое разбиение превышающего размер ряда на модули. Распределение напора в трубах и идеальный баланс сложных заводов не гарантируются: игрок видит ограничения и решает вручную. **Такт машин в чертеже не выставляется, пока спайк не покажет обратного:** `clockPercent` из запроса участвует в расчёте `plannedRate`, а preview возвращает `CLOCK_NOT_APPLIED` (§5.4). Power Shards и Somersloops чертёж не содержит. **Удаление чертежа в ходе сессии** (`delete_blueprint`, §7.5): обновляет ли игра меню чертежей и Blueprint Designer, если файлы `.sbp`/`.sbpcfg` убраны на ходу, проверяет спайк v1.1 вместе с генератором. Fallback — чертёж сразу скрывается из библиотеки мода, а файлы переносятся в корзину при следующей загрузке.

# 10. Хранение и жизненный цикл

Решение изменено в 2.1-draft (ADR-014). FR-10 по-прежнему требует, чтобы состояние было доступно без сайдкара, поэтому оно хранится у мода. Но ключ по имени файла сохранения ненадёжен: автосохранения ротируются, файлы переименовывают и копируют. Поэтому компактное состояние хранится **прямо в сохранении**, а снаружи остаётся только объёмное и восстановимое.

**Идентификатор сохранения.** Save-persistent subsystem мода при первой загрузке генерирует GUID `saveId` и хранит его в сохранении. Все внешние данные и playthrough Foreman привязаны к `saveId`.

| Где | Что хранится | Не хранить |
|---|---|---|
| Satisfactory save (subsystem мода) | `saveId`, `ProductionPlan`, `ScreenDefinition`, линии (`ProductionLine`), HUD-профили, заметки, привязки `terminalId → screenId`; установленные терминалы и их игровые параметры | токены, ключи, переписка, телеметрия |
| Локальные файлы мода (ключ — `saveId`) | кэш отрендеренных экранов; кольцевые буферы телеметрии — с v1.1, в v1.0 ряд живёт только в памяти (§8.2); корзина удалённых чертежей — с v1.1 (§7.5) | ключи LLM-провайдера |
| Foreman DB | аккаунт, playthrough (сопоставлен с `saveId`), переписка, Work Orders | игровые значения каждого тика, копии каталога |
| Локальный конфиг (Mod Configuration SML) | аудио, адрес адаптера, токен канала мод ↔ адаптер; клавиши — в настройках управления игры (Enhanced Input, §2.3) | — |

Состояние в сохранении — килобайты JSON, поэтому прежнее возражение «не хранить длинные JSON-схемы в save» к нему не относится. Следствия: загрузка старого сохранения возвращает его планы и экраны (ветвление сохранений корректно само собой); копия сохранения на другой машине переносит и состояние; у копий одного сохранения общий `saveId`, поэтому они делят внешнюю телеметрию и playthrough — это допустимо.

Порядок восстановления: загрузка сохранения (с ним — состояние мода) → сборка каталога → отрисовка экранов из кэша → подключение к адаптеру, если сайдкар поднят → доступность AI-функций.

Безопасное удаление: терминал пропадает из save, но его `ScreenDefinition` остаётся в состоянии мода, чтобы не терять дизайн. Удаление мода не должно повреждать сохранение.

## 10.1 Кэш отрендеренного экрана

§14 1.0-draft обещала «физический экран показывает последнюю PNG», но клиентское хранение этого изображения нигде не описывалось, то есть обещание деградации было невыполнимым. Теперь: кэш по ключу `saveId + screenId + renderRevision`, персистентный, читается до подключения сайдкара. Терминал, у которого содержимого ещё не было, показывает документированное пустое состояние, а не ошибку.

**Начальные, проверяемые нагрузочные цели** (не гарантии до измерений): открытие кэшированного UI без обращения к сайдкару; перерисовка виджета по поступлению снапшота, не по таймеру; снятие телеметрии в GameThread в пределах бюджета доли миллисекунды на выборку, агрегация вне GameThread; экран в мире обновляется по `renderRevision`; десятки размещённых терминалов не создают линейного роста затрат в кадре (неактивные и обесточенные терминалы не рендерят). Перед релизом профилировать GameThread и GPU.

# 12. Доступы и безопасность

Мультиплеерные пункты 1.0-draft (pairing-токены с привязкой к `worldId`/`playerId`, ACL терминалов, роли owner/editor/viewer, запрет публикации портов) удалены вместе с топологией. Пункты, относящиеся к изоляции LLM, сохранены полностью — они не зависели от мультиплеера.

1. В игровом процессе нет входящих слушателей. Адаптер слушает только loopback (`127.0.0.1`, не `0.0.0.0`: заодно это избавляет игрока от запроса брандмауэра, AC-12); мод подключается к нему с токеном из локального конфига, сгенерированным установщиком.
2. MCP-эндпойнт адаптера для Foreman слушает только loopback; токен передаётся в query-строке `MCP_URL`, потому что MCP-клиент Foreman не отправляет заголовков. Foreman пишет `MCP_URL` в локальный лог при старте целиком, вместе с токеном: это его код, и мы его не патчим (ADR-012). Для петли с одноразовым токеном в файле с правами 600 это **принято осознанно**, а требование «логи без секретов» (V-7) относится к нашим логам. **Целевой вариант — заголовок, query переходный** (решение 10.11.2026 по Co2-2): upstream-PR фоллбэка S2 добавляет и `MCP_EXTRA_URLS`, и поддержку заголовков, после чего заголовок становится основным.
2a. **Порт `sf-mcp` в режиме HTTP доступен любому локальному процессу без аутентификации** (§3.4). Белый список адаптера закрывает то, что видит модель, но не сам порт: единственная защита — петля, поэтому лаунчер не поднимает `sf-mcp` ни на каком адресе, кроме `127.0.0.1` (AC-12).
3. Ключ LLM-провайдера хранится у сайдкара, не в игровых файлах и не в сохранении. Учётные данные локального аккаунта Foreman — в конфиге сайдкара.
4. Все внешние вызовы валидируются JSON Schema; действуют лимиты размера и частоты (§7.4).
5. У модели нет инструментов, изменяющих мир. Создание экранов, заметок и чертежей проходит authority-слой; идемпотентность через `requestId`.
6. Модель не может ничего, чего не может игрок вручную: инструменты генерируются из `OperationRegistry` и выставляются только при наличии ручной точки входа (§7.5).
7. Идентификаторы в аргументах инструментов сверяются с живым каталогом, а не принимаются из текста (§7.3).
8. Запрещены блокирующие сетевые вызовы в GameThread и зависимость игрового тика от внешнего сервиса.
9. Состояние привязано к `saveId` и хранится в самом сохранении: план из другого сохранения не применяется молча.
10. Внешние клиенты API (FIN, другие моды) — ручные клиенты от имени игрока: та же валидация, отдельные лимиты, никаких операций над миром. Lua-код FIN пишет или загружает сам игрок, поэтому его вызовы не получают больше прав, чем UI.

S7 идёт своим темпом параллельно всему, но его предпосылка изменилась: экспорты для UE в `art/command-center` уже есть (stage 7), поэтому пробный импорт можно делать не «если успеет к неделе 8», а в любую свободную неделю Gf начиная со второй. v0.1 по-прежнему обходится мешом-заготовкой с экраном 16:9, так что на критический путь S7 не попадает.

**Screen Lab — отдельный инструмент экранов** (ADR-026). Экраны отлаживаются без запуска игры:

- **Разделение кода.** Экраны живут в UE-модуле `FicsitAIUI`, который зависит только от `FicsitAIApi` (интерфейсы и типы контрактов) и UMG/Slate — без заголовков игры (FactoryGame) и SML. Всё, что требует игры (подсистемы, телеметрия, постройки), — в модуле `FicsitAICore`. Нарушение зависимостей ловится сборкой.
- **Screen Lab** — отдельный UE-проект на той же версии движка, что игра, в который входят `FicsitAIUI`, `FicsitAIApi` и офлайн-источники данных. Запускается в редакторе или как приложение для рабочего стола.
- **Возможности:** выбор экранного модуля; размеры хоста (терминал во весь экран, компактная раскладка AI Assistant, HUD); выбор источника данных (Fixture, Recording с перемоткой и скоростью, Save — через адаптер сайдкара); принудительные состояния (сайдкар недоступен, заглушка планировщика, инертный режим, нет питания); снимок экрана.
- **Тестовый хост.** Хост Screen Lab — тот же тестовый хост, на котором проверяется переиспользование модулей (AC-14).
- **Визуальная регрессия (позже):** автоматические снимки каждого модуля на наборе Fixture и сравнение с эталоном.
- **Почему не веб-просмотрщик:** при UMG-экранах отдельная веб-отрисовка была бы второй реализацией UI и расходилась бы с игрой. Если по итогам S8 экраны станут вебом (ADR-032, §6.3.1), возражение снимается: веб — единственная реализация, и Screen Lab для них сводится к браузеру с теми же источниками данных.

**Автоматические проверки в игре** живут в основном моде за флагом диагностики, выключенным по умолчанию, а не отдельным модом для разработки (решение King 10.11.2026): отдельный мод разъехался бы с тем, что запускают игроки, и проверки подтверждали бы работу другого бинаря. Два ограничения: проверки ходят только через `OperationRegistry`, как любой клиент, и ни одна не изменяет игровой мир (ADR-009) — иначе игрокам достаётся код, умеющий больше публичного API. Результаты пишутся в формат и каталог Recording (JSONL по `saveId`) отдельным типом записи: у Gf2 остаётся один разборщик, и прогон проверки можно приложить к отчёту об ошибке без конвертации.

**Тестирование.** Валидатор, обёртка планировщика и операции тестируются UE Automation (Spec) без загрузки мира. Обёртка проверяется тестовым провайдером, возвращающим `contracts/plan.example.json`. Каждый экранный модуль открывается в тестовом хосте (AC-14). Фикстуры — примеры из `contracts/` и снимок каталога, выгруженный из игры в JSON. Адаптер покрывается интеграционными тестами против зафиксированной версии Foreman. Примеры контрактов проверяются по JSON Schema в CI. **Тест паритета:** сборка падает, если операция выставлена модели без ручной точки входа (§7.5); для каждой операции один и тот же набор аргументов, поданный из UI и через инструмент, даёт одинаковый результат.

Критический путь v1.0 не содержит ни одного spike'а, способного опрокинуть архитектуру: S1 и S4 — штатные приёмы UE; S2 — исходящее соединение из мода и Node-процесс с официальным MCP SDK, без изменений Foreman; S3 опирается на документированный `UModContentRegistry` и работающий мод SBC того же стека; S7 — обычный пайплайн ассетов. Планировщик с критического пути v1.0 снят: в v1.0 подключена заглушка. **Исключение одно — S5:** характеристика «инженерная задача» из 2.1-draft снята, потому что общепринятого инструмента упаковки Node больше нет (§4.1). Опрокинуть архитектуру S5 не может, но способен сорвать обещание установки в один шаг, то есть AC-12.

**Правило fallback.** Если spike опровергает выбранное решение, ADR о замене принимается до реализации зависящей функции. Для S2 fallback — upstream PR в Foreman: переменная `MCP_EXTRA_URLS`, подключающая уже готовый `McpAggregateGateway`, плюс поддержка заголовков. Для S3 — собственное чтение `AFGRecipeManager` без слоя данных SBC (каталог) и сужение набора метрик до дешёвых (телеметрия). Для S5 — документированный docker-путь с явным предупреждением о сужении аудитории.

# 14. Acceptance criteria для v1.0

**AC-01.** Игрок строит AI Terminal и подключает его к электросети; терминал потребляет энергию. По E открывается интерфейс с навигацией между экранами. Без питания экран в мире погашен, а по E показывается статус «нет питания». Повторное открытие восстанавливает последнее состояние.

**AC-02.** Экран в мире на меше терминала отображается в соотношении 16:9: пресет `layout`, выбранный для мирового экрана, компонуется без обрезки и без полей, а редактор Screens показывает предпросмотр и в этой пропорции, и в пропорции интерактивного окна. LOD'ы меша переключаются без артефактов на экране, коллизия UCX не мешает взаимодействию по E (§6.6, ADR-030, Spike S7).

**AC-03.** Экраны Planning и Graph — обёртки: при подключённой заглушке они показывают статус «планировщик не подключён», а инструменты планирования модели не видны. Контракты `PlanRequest` и `ProductionPlan` зафиксированы JSON Schema; тестовый провайдер проходит через обёртку, и результат валиден по схеме.

**AC-04.** Dashboard показывает отчёты по энергии и по ресурсам: производство и потребление электричества, генераторы по типам, топливо и батареи, пики сети; добычу, потребление и баланс ресурсов, запасы на складах. Значения отмечены `live` и временем актуальности, плановые — `planned`. Графики работают за **5, 15 и 60 минут от начала сессии**; после перезапуска игры ряд начинается заново, и UI сообщает об этом, а не показывает пустой график как сбой. Настройки машин отображаются, но не меняются. Частота перерисовки не превышает частоту поступления данных. **Персистентная история за 24 ч — критерий v1.1** (§8.2).

**AC-05.** Экран Chat: текстовый диалог с Foreman внутри игрового UI — потоковый ответ, отмена, история. Экран Work Orders показывает задачи Foreman и позволяет создавать и править их вручную. Инструменты v1.0 (`query_metric`, заметки, экраны) вызываются моделью через адаптер и возвращают данные текущего сохранения; инструменты Foreman вне белого списка модели не видны.

**AC-06.** Экран Screens: игрок создаёт пользовательский экран из виджетов (метрика, временной график, текст, заметки, Work Orders), сохраняет его в библиотеке и назначает терминалу; модель делает то же через `create_screen` и `assign_screen`, а результат открывается в том же редакторе.

**AC-07.** После перезапуска игры экраны, заметки и привязки терминалов восстанавливаются вместе с сохранением, в том числе после переименования файла и ротации автосохранений. Открытие другого сохранения не подмешивает чужое состояние.

**AC-08.** Экран терминала показывает актуальное содержимое, обновляется по изменению, а не покадрово, и читается из кэша до подключения сайдкара. Терминал без содержимого показывает документированное пустое состояние.

**AC-09.** При остановленном сайдкаре работают Dashboard, Notes и Screens, Chat и Work Orders показывают состояние «не подключено», метки устаревших данных корректны, игра не падает и не фризит.

**AC-10.** Если сессия мультиплеерная или к одиночной игре подключается другой игрок, мод становится инертным: UI закрыт, связь с адаптером разорвана, игрок видит внятное сообщение, сессия стабильна. После ухода удалённых игроков мод возобновляет работу. Игрок без мода подключиться не может. Сохранение с размещённым терминалом открывается в любой сессии без повреждений.

**AC-11.** Профилирование подтверждает соблюдение бюджета GameThread (§11) при десятках размещённых терминалов и активном сборе телеметрии.

**AC-12.** Установка: от скачивания до первого ответа помощника без ручного редактирования конфигов и без Docker, кроме ввода ключа LLM-провайдера. Сайдкар запускается модом при старте игры. Брандмауэр Windows не запрашивает разрешений: ни один процесс сайдкара не слушает адреса, кроме `127.0.0.1` (у FRM Companion, который слушает на всех интерфейсах, игрок подтверждает запрос для каждого исполняемого файла). **Критерий проверяется пилотным тестером на одной машине** (ADR-033, R-27), поэтому «брандмауэр не запрашивает разрешений» означает «не запросил у пилотного тестера»: его поведение зависит от настроек. Повторяемая проверка — вместе с установщиком на этапе 3.

**AC-13.** Паритет: для каждого инструмента v1.0 из §7.1 игрок выполняет то же действие вручную через UI без LLM-провайдера, а для операций мода — и без сайдкара. Результат совпадает с результатом вызова модели (тот же контракт), а объект, созданный моделью, игрок открывает и правит вручную. Тест паритета (§13) проходит в CI. **Отдельно проверяется, что у модели нет инструмента, изменяющего игровой мир** (§3.2, ADR-009), и что `delete_blueprint` (v1.1) не затрагивает чертежи, созданные вне мода, идемпотентен по `requestId` и кладёт удалённое в корзину (§7.5, правило 7).

**AC-14.** Переиспользование экранов: Обзор, Производство, Статистика, Chat, Notes, Work Orders, Lines, Screens и Настройки реализованы как экранные модули с интерфейсом хоста; в автотестах каждый модуль открывается в тестовом хосте, отличном от AI Terminal, без изменений кода модуля.

**AC-15.** Линии: игрок создаёт линию в терминале, привязывает постройки в режиме привязки или из списка, видит метрики линии на Dashboard; после перезагрузки сохранения состав линии сохраняется, демонтированные постройки из неё исключены.

**AC-16.** Заметки v1.0: только заголовок и текст; попытка записать зарезервированное поле (тег, напоминание и т. д.) из UI или моделью отклоняется с кодом `NOTE_FIELD_NOT_SUPPORTED`.

**AC-17.** Экраны v1.0: Обзор, Производство (без цепочки и узкого места), Статистика, Настройки и каркас терминала (боковое меню, верхняя полоса статуса, нижняя полоса с горячими клавишами) работают без сайдкара, кроме панели ассистента; ни один элемент этих экранов не меняет мир.

**AC-18.** Карточки в чате: модель выводит карточку `show_card`; ссылочная карточка показывает живые значения мода, карточка с данными помечена как оценка ассистента; невалидная карточка отклоняется, а ответ показывается текстом.

**AC-19.** API: экраны v1.0 получают данные и выполняют операции только через публичный API (проверяется тестом: модули экранов не зависят от подсистем мода). В v1.1 Lua-компьютер FicsIt-Networks подключается к AI Terminal, читает метрики и линии, создаёт заметку и публикует внешнюю метрику, которая появляется в Статистике; без установленного FIN мод работает без изменений.

**AC-20.** Отладка без игры: каждый экран v1.0 открывается в Screen Lab на источниках Fixture, Recording и Save (снимок из реального `.sav`) в размерах терминала и компактной раскладки; значения помечены своим источником; запись потока API из живой сессии воспроизводится с перемоткой. Модуль `FicsitAIUI` собирается без заголовков игры.

**AC-21.** Инварианты CI выполняются: примеры контрактов валидны против схем; типы `AFG*`/`UFG*` не встречаются вне `GameFacade/`; `FicsitAIUI` собирается без заголовков игры и SML; вызовы мутирующего игрового API не встречаются в обработчиках сообщений сайдкара; операция, выставленная модели без ручной точки входа, роняет сборку (§3.2.1, §13, ADR-029).

**Критерии отложенных версий.** AI Assistant и HUD (v1.4): игрок создаёт предмет, экипирует в ручном слоте, ЛКМ открывает те же экранные модули в компактной раскладке; при переключении предмета HUD скрывается и возвращается после повторной активации; HUD показывает подсказку, метрику и временной график мощности. Планировщик (v1.3): после подключения провайдера игрок без сайдкара (для провайдера в моде) получает план по рецептам, разблокированным в этом сохранении, включая модовые; ограничения провайдера показаны, а не скрыты.

# 17. История изменений

## 17.1 2.2-draft относительно 2.1-draft

Редакция сводит две линии, развивавшиеся параллельно от одной базы. Ведущей выбрана 2.1-draft, потому что она опирается на чтение исходников (Foreman, SBC, FicsIt-Networks), а её `OperationRegistry` с паритетом и обёртка планировщика сильнее того, что предлагала линия 3.0-draft. Закрытая линия сохранена в ветви `docs/architecture-3.0-salvage`.

**Что принесла закрытая линия:**

| Вставка | Эффект |
|---|---|
| Лицензии у FRM нет (проверено) | **R-12 закрыт отрицательно**, Spike S3 разблокирован, телеметрия — полностью собственная (§2.2) |
| Готовые средства SML и игры + `UModContentRegistry` | **Единственное уменьшение объёма v1.0**, прямо по R-16: экран «Настройки» уходит в Mod Configuration (§2.3, ADR-027) |
| Линейная система вместо LP | **R-14 закрыт постановкой задачи**, новый кандидат провайдера (§8.3, ADR-028) |
| `GameFacade/` с инвариантом CI | Первая конкретная митигация R-10, обобщение ADR-026 (§3.2.1, ADR-029) |
| `vercel/pkg` заархивирован, SEA в Active Development | **R-11 повышен**, с S5 снята характеристика «инженерная задача» (§4.1) |
| Схема страницы результата поиска по каталогу | Закрыт пробел на границе доверия (§5.1) |

**Что из закрытой линии отвергнуто и почему** — это важнее списка принятого:

- **Форк SBC целиком как база мода.** Ставил весь код проекта на репозиторий с одним контрибьютором, 27 коммитами, нулём звёзд и форков и нулём PR за историю, причём оценку качества этого кода выносил в спайк *после* решения. Разделение на слой данных (v1.0) и калькулятор за `IPlannerProvider` (v1.3) даёт ту же возможность при строго меньшем риске (ADR-013).
- **Очередь подтверждений игрока.** Защита процедурная, её надёжность равна внимательности игрока на двадцатом подтверждении. `OperationRegistry` с обязательной ручной точкой входа и тестом сборки ограничивает поверхность структурно (ADR-018). Отдельно отвергнут «подтверждать записи по происхождению»: происхождение вызова нельзя установить в принципе, потому что в одном ходе смешаны реплика игрока и прочитанные данные (§7.3).
- **MCP в моде как собственное решение** — дубль ADR-012, который в 2.1-draft обоснован чтением `ff-server`.
- **Переименование сайдкара в «компаньон».** Вокабуляр 2.1-draft точнее: адаптер — отдельный тонкий процесс, и смешивать его с Foreman незачем.

**Решения, принятые в этой редакции:**

- **Телеметрия v1.0 сокращена до текущей сессии**, персистентная история 24 ч — в v1.1. Причины: референса больше нет (FRM), а ряд требует хранения, ротации, понижения разрешения и миграций рядом с самым дорогим модулем. R-05 возвращается к уровню 2.0-draft, v0.1 не затронут (§8.2).
- **«Модель не изменяет игровой мир» — постоянный инвариант.** Не объём версии, не «пока нет таких функций». Строительство, демонтаж, рецепты, такт, транспорт остаются только ручными во всех версиях v1.x (§3.2, ADR-009).
- **Модель управляет экранами и библиотекой чертежей, включая удаление чертежей.** Добавлен инструмент `delete_blueprint` (v1.1) с ограничениями: только созданные через мод, идемпотентность по `requestId`, корзина, отдельный лимит. Заметки модель создаёт и правит, но не удаляет — границу определяет восстановимость (§7.5, правило 7).
- **Ассет командного центра входит в v1.0** (ADR-030). Работа в `art/command-center` продолжается, поэтому зафиксировано единственное следствие для контрактов: экраны меша 16:9, значит render target и пресеты `layout` для мирового экрана держат эту пропорцию (§6.6, §5.3). Добавлены Spike S7 и R-24.
- **Лицензия проекта — GPL-3.0-or-later** (ADR-031). Попутно исправлен факт, который обе прежние редакции передавали неверно: **SML под GPL-3.0, а не под MIT.** Практические следствия всего два: `piper1-gpl` вернулся в кандидаты TTS, а внешние моды обращаются к нашему API без линковки заголовков (ADR-023), поэтому могут быть под любой лицензией. Обоснование ADR-024 заменено с лицензионного на продуктовое.
- **`clockApplied` удалён из `BlueprintRequest`, `clockPercent` стал необязательным.** Прежняя пара полей была выходом в схеме входа и требовалась обязательной при неизвестном действии. Правду о каждом конкретном запросе теперь говорит `PreviewResult` кодом `CLOCK_NOT_APPLIED` (§5.4). Это заодно убрало единственное место, где мод задавал настройку машины, тогда как §6.8, §8.2 и AC-04 втроём заявляют обратное.

**Решения King 09.11.2026** (приняты после первой правки редакции, вне ворот):

- **Платформа разработки — Linux, игра под Proton** (ADR-033). Прежняя строка «Целевой стек: Windows game client» смешивала платформу игрока и платформу команды, из-за чего AC-12 читался как выполнимый своими силами. Windows-машины в проекте нет: проверка упаковки уходит пилотному тестеру, Proton становится основной средой S8, правило ворот W меняется на обратное (§6.3.1, §13, R-27). Попутно уточнено, что сборка движка из исходников не нужна — есть готовый архив редактора под Linux, и это снижает R-22.
- **Язык интерфейса v0.1 — английский**, строки с первого дня через UE Localization (§6.9). Тестеры набираются из международного сообщества моддинга; русский добавляется позже. Вопрос снят из перечня §15.4.
- **Контракт публичного API v0 замораживается на неделе 1–2**, а не на неделе 6: типы `FicsitAIApi` и схемы `list_metrics` и `query_metric` фиксируются до того, как Co2 начнёт фасад API для страниц в S6 (§3.6, §13, [PLAN-v0.1.md](PLAN-v0.1.md)). Реализация V-2 остаётся на неделе 6.

**Исправления 09.11.2026** (сверка с исходниками SML 3.12, MCP SDK и FicsIt-Networks, затем сквозная проверка согласованности):

- **Mod Key Bind Registry в SML 3.12 нет** — `RegisterModKeyBind` относится к SML 2.x. Клавиши мода — Enhanced Input игры, попадание в меню переназначения проверяет S1 (§2.3, ADR-027).
- **Replication Policy не определяет сторонность сессии:** `ESubsystemReplicationPolicy` задаёт только место спавна сабсистемы. ADR-016 остаётся собственной работой целиком (§2.3).
- **Линейный провайдер получил переменные излишка и активное множество:** отрицательная интенсивность в типичном случае (Heavy Oil Residue) означает излишек, а не `SYSTEM_INFEASIBLE` (§8.3, ADR-028).
- **Удаление экранов вернулось в список только ручных операций;** для `delete_blueprint` заданы лимит (§7.4), размер корзины и её хранение (§7.5, §10), проверка удаления на ходу (§9.3).
- **Граница контракта и схем уточнена 10.11.2026** (Gs-3.2): канонические формы запросов, ответов, ошибок и событий — часть контракта и работа Co; файлы JSON Schema и примеры в `docs/contracts/schemas/` пишет Co2 в V-3. Прежняя формулировка «схемы фиксируются вместе с контрактом» расходилась с планом.
- **Инструменты модели закрыты по паритету и по данным:** добавлен `list_metrics` (v1.0) — без него модель не могла заполнить `source.id`; `list_machines` и `get_recipes` перенесены в v1.1 — без них модель не могла заполнить `BlueprintRequest`, а ручной путь у них появляется вместе с формой Blueprint Builder (§7.1).

- «Первый кандидат — ядро SBC» заменено на «кандидаты SBC и линейная система, порядок по S3» везде, где расходилось с §8.3; `SYSTEM_INFEASIBLE` внесён в ошибки обёртки (§5.2).

## 17.2 2.1-draft относительно 2.0-draft

Сводка для ревью. Причины: проверка исходников Foreman (§3.4), поиск готовых планировщиков (§8.3) и разбор документа.

**Изменено:**

- **Связка с Foreman** (ADR-012). Вместо MCP-эндпойнта в игре — адаптер сайдкара: единственный MCP-сервер Foreman, белый список инструментов, авторизация, стабильный API для мода. Мод подключается к адаптеру исходящим соединением. Причина: Foreman подключается только к одному MCP-серверу, не шлёт заголовков, закрывает чат сессией Better Auth.
- **Планировщик** (ADR-013): вместо собственной разработки — стандартизированная обёртка с интерфейсом провайдера и контрактом `PlanRequest` → `ProductionPlan`; в v1.0 подключена заглушка. Первый кандидат провайдера — ядро Satisfactory Build Calculator, затем LP на HiGHS. Механизм «закрепить ставку» для циклов удалён.
- **Представление плана** (ADR-007): экраны Planning и Graph — обёртки для подключаемого UI (`IPlanView`), в v1.0 — заглушка; собственной таблицы и раскладки графа в v1.0 нет.
- **UI** (ADR-001): вместо единого UI-контроллера — переиспользуемые экранные модули (Dashboard, Chat, Notes, Work Orders, Screens) и интерфейс хоста. В v1.0 хост — AI Terminal.
- **Объём v1.0** (§1.1, §1.2): AI Terminal потребляет 10 MW; экраны Dashboard, Chat, Notes, Work Orders и Screens — в v1.0; редактор экранов и экранные инструменты модели перенесены из v1.2 в v1.0; дальше v1.1 — Blueprint Builder, v1.2 — голос (был v1.3), v1.3 — подключение планировщика и UI плана, v1.4 — AI Assistant и HUD; интерактивный редактор графа (бывшая v1.4) стал возможностью подключаемого UI плана.
- **Подтверждения игрока удалены** (ADR-009, §7). У модели нет инструментов, изменяющих мир; заметки, экраны и чертежи создаются после валидации. Правило §7.3 о подтверждении «по происхождению» удалено как нереализуемое.
- **Хранение** (ADR-014): компактное состояние — в сохранении, `saveId` вместо ключа по имени файла.
- **Мультиплеер** (ADR-016, §4.2): определение в ходе сессии, контент регистрируется всегда, `RequiredOnRemote`.
- **Каталог для модели** (ADR-017): поисковые инструменты вместо `get_catalog`.
- **Паритет ручного и AI-пути** (ADR-018, §7.5, FR-11): `OperationRegistry`, ручной путь для каждого инструмента (столбец в §7.1), инструменты планирования и каталога — только вместе с подключённым UI плана, ручные формы Work Orders через REST Foreman, инструменты заметок, правило версий, тест паритета. Фильтр адаптера переведён с чёрного списка на белый.
- **Упаковка** (§4.1): конкретизирована — портативный Node, бандлы, SQLite, launcher; сайдкар запускает мод; `ff-client` не поставляется.

## 17.3 2.0-draft относительно 1.0-draft

Причина большинства изменений — решение §1.1 об отказе от мультиплеера.

**Удалено:**

- Game Bridge как компонент (ADR-004 отозван); его задачи распределены между модом и локальными файлами.
- FRM как обязательный серверный мод (ADR-003 заменён).
- Канал Bridge → серверное расширение SML — самая несспроектированная часть прежней редакции.
- Серверное расширение как отдельный деплой; осталось authority-слоем в процессе.
- ACL, роли, scope `shared`, pairing-токены, TLS, публикация портов.
- Прежние AC-01 (второй игрок), AC-10 (независимость игроков), AC-11 (late-join).
- Пайплайн изображений для экрана в мире; заменён render target'ом.
- Тип виджета `image`; поле `targetPlayer` в `BlueprintRequest`.
- ADR-010.

**Изменено:**

- Объём v1.0 сужен до ручного контура плюс текстовый чат; Blueprint, AI-экраны, голос и интерактивный граф разнесены по v1.1–v1.4 (§1.2).

- Хранение состояния — локальные файлы мода, а не БД внешнего сервиса (ADR-014). Это сознательный разворот относительно промежуточного варианта «всё в БД Foreman»: он противоречил бы FR-10.

- `ScreenDefinition`: `layout` стал перечислением пресетов с именованными слотами (прежние `layout:"grid"` и `area:"left"` были несовместимы), `source` стал структурированным, добавлены `theme` и клампинг `refreshSec`, `scope` сокращён.
- `BlueprintRequest`: приведён к одному каноническому набору полей (текст и пример прежней редакции расходились), добавлены `requestId` и `clockApplied`.
- `PreviewResult` специфицирован, добавлены машиночитаемые коды предупреждений, включая `MANIFOLD_RAMP_UP`.
- Частота обновления виджетов привязана к частоте данных.
- Spike'и сокращены с пяти до пяти других: исчезли транспорт и Blueprint-на-DS, появились MCP-эндпойнт и упаковка.

**Добавлено:**

- §4.1 упаковка и установка, §4.2 поведение в MP — обоих не было.
- §5.5 согласование версий мода и сайдкара.
- §7.3 инъекции через авторский текст игрока.
- §8.3 планировщик с честной оценкой побочных продуктов и циклов.

- Риски R-10 (обновление игры), R-11 (упаковка), R-12 (лицензия FRM), R-13 (слушатель в процессе), R-14 (циклы рецептов), R-15 (загрузка в MP), R-16 (ёмкость команды).

**Итог архитектуры.** Релиз состоит из одного мода и одного локального сайдкара: Foreman используется как есть, а тонкий адаптер связывает его с модом. Сложные части берутся из готовых проектов там, где извлечение объективно дешевле реализации: генератор чертежей — из Factory Spawner, LLM-оркестрация — из Foreman, слой данных каталога — из SBC. Там, где средство есть у платформы — конфигурация, клавиши, персистентность, реестр контента, — берётся средство SML или игры, а не свой код.

Два решения определяют форму проекта сильнее остальных. **`OperationRegistry` с обязательной ручной точкой входа** делает модель ускорителем, а не отдельным путём: поверхность, доступная LLM, равна поверхности, доступной игроку, и это проверяется сборкой. **Обёртка планировщика** снимает самую тяжёлую вычислительную часть с критического пути v1.0, оставляя её подключаемой. Вместе они дают архитектуру, в которой ни один спайк не способен опрокинуть целое.

Отказ от мультиплеера убрал с критического пути v1.0 все интеграционные неизвестные. Из оставшегося проект не контролирует два риска: совместимость с обновлениями игры (R-10, снижен до починки одного каталога) и ёмкость команды (R-16, не закрыт — и это главный риск релиза, потому что паритет ручного пути делает объём UI пропорциональным числу операций). Один риск вырос: телеметрия пишется без референса, потому что у FRM нет лицензии, — поэтому её объём в v1.0 сознательно сокращён.
