# Зачем один канал на всё

**Чат идёт тем же каналом, что и вызовы инструментов,** а не отдельными маршрутами `POST /mod/saves/:saveId/chat` из [#50](https://github.com/kkkingqz/ficsit-ai-helper/pull/50). Причины:

1. **Запасной транспорт меняется в одном месте.** §3.3 обещает, что переход с потока на long-poll или IXWebSocket протокол не меняет. Отдельный потоковый маршрут чата пришлось бы переводить на запасной транспорт отдельно.
2. **Одно состояние связи.** Вызовам инструментов поток адаптер → мод нужен в любом случае. Будь у чата свой поток, во время хода жили бы два соединения с независимыми отказами. Игрок видел бы, что чат отвечает, а ассистент «не видит игру», и причины нигде бы не было. Один поток даёт один признак `bSidecarConnected`.
3. **Доставка.** Кадры чата получают номер и подтверждение. Короткий обрыв посреди ответа не теряет текст. У потока, привязанного к запросу, хвост пропадает, и его пришлось бы восстанавливать из истории.
4. **Одно место в моде** держит токен, версию и переподключение.

Цена — входы в логику чата из #50. Сама логика остаётся: один ход на сохранение, отмена с дочитыванием, история. Маршруты становятся сообщениями, кадры получают конверт. `encodeFrame` в #50 для этого и вынесен.

# Участники и адрес

- Адаптер слушает `127.0.0.1:<порт>`. Порт берётся из локального конфига мода (§10), все маршруты канала начинаются с `/mod/`.
- Клиент один — мод. Процесс игры один, поэтому и сессия канала в каждый момент одна.
- Токен идёт в заголовке `Authorization: Bearer <токен>` каждого запроса. Его генерирует установщик (§4.1). Неверный токен — `401` без подробностей.
- **Токен не попадает в веб-страницы.** Страница говорит с `FicsitAIApi` через мост (ADR-032), а у моста канала нет.
- Все тела запросов и ответов — JSON в UTF-8.

# Транспорт: основной вариант

| Вызов | Что делает |
|---|---|
| `POST /mod/hello` | рукопожатие, открывает сессию канала |
| `GET /mod/stream?session=…&ack=N` | долгий ответ: сообщения адаптер → мод, по одному JSON на строку (NDJSON) |
| `POST /mod/send` | пачка сообщений мод → адаптер и подтверждение принятого из потока |

## Рукопожатие

```json
POST /mod/hello
{ "protocol": 1, "apiVersion": "0.4.0", "modVersion": "0.1.0",
  "saveId": "8f2c…", "inert": false,
  "tools": [ { "name": "query_metric", "description": "…", "inputSchema": { } },
             { "name": "list_metrics", "description": "…", "inputSchema": { } } ] }

200
{ "session": "s-5d1e…", "protocol": 1, "apiVersion": "0.4.0", "adapterVersion": "0.1.0",
  "limits": { "maxMessageBytes": 1048576, "maxBatchMessages": 64, "bufferMessages": 1024,
              "pingSec": 15, "toolDeadlineSec": 10, "sessionIdleSec": 120 } }
```

- **Каждое рукопожатие открывает новую сессию**, счётчики обоих направлений начинаются с 1. Прежняя сессия закрывается:
  - её поток получает `bye` с причиной `superseded`;
  - её недоставленные сообщения отбрасываются;
  - её незавершённые вызовы инструментов Foreman получает с ошибкой `CHANNEL_RESET`.
- **`tools` — определения инструментов из `OperationRegistry`.** Так выполняется правило 2 §7.5: описания генерируются из реестра, а не пишутся в адаптере. Форма — та же, что у схем V-3.
  - Пока сессия жива, адаптер показывает модели ровно эти инструменты мода. Нет сессии — в `tools/list` нет инструментов мода.
  - Совпадение имени с инструментом `sf-mcp` решается в пользу мода: инструмент `sf-mcp` с тем же именем скрыт. Это уже так в `MOD_TOOL_NAMES` адаптера, набор просто становится динамическим.
- **`saveId`** — текущее сохранение, пустая строка до входа в мир.
- **Отказы.** Отказ рукопожатия мод показывает как «несовместимая версия сайдкара», а не «не подключено», и пишет в `ApiVersionMismatch` статуса API. Повторяет попытку раз в 60 с: сайдкар могли обновить, не выходя из игры.
  - `409 {code: "PROTOCOL_MISMATCH", protocol}` — версия протокола не поддерживается.
  - `409 {code: "API_VERSION_MISMATCH", apiVersion}` — не совпала мажорная версия API (§5.5).

## Поток адаптер → мод

- **`GET /mod/stream?session=S&ack=N`.** `N` — номер последнего сообщения, принятого подряд; в начале сессии 0. Адаптер освобождает из буфера всё до `N` включительно, отдаёт сообщения с `N + 1` и дальше новые по мере появления.
- **Формат.** Ответ `200`, `content-type: application/x-ndjson`; строка — один объект JSON и `\n`.
- **Поток в сессии один.** Новый `GET` закрывает прежний строкой `bye` с причиной `replaced`.
- **Служебные строки** идут без `seq`, не буферизуются и не подтверждаются:
  - `{"type":"ping"}` — каждые `pingSec`, если других строк не было;
  - `{"type":"bye","reason":"…"}` — перед намеренным закрытием потока: `replaced`, `superseded`, `shutdown`.
- **Ошибки до начала потока.** На обе ошибки мод отвечает новым рукопожатием:
  - `410 {code: "SESSION_UNKNOWN"}` — адаптер перезапущен, либо сессия вытеснена или истекла;
  - `409 {code: "STREAM_LOST", oldest}` — `N + 1` уже вытеснен из буфера.
- **Сторона мода.** Строки читаются вне GameThread. Тишина дольше `3 × pingSec` значит обрыв: мод переоткрывает поток с той же сессией и своим `ack`.

## Мод → адаптер

```json
POST /mod/send
{ "session": "s-5d1e…", "ack": 41,
  "messages": [ { "seq": 7, "type": "tool.result", "re": "c-7f3a", "body": { } } ] }

200
{ "ack": 7 }
```

- **`ack` в теле** — последний номер из потока, принятый подряд. Он освобождает буфер адаптера, не переоткрывая поток. Мод шлёт пачку без сообщений, с одним `ack`, если с прошлого подтверждения пришло больше `bufferMessages / 4` сообщений или прошло 5 с. Иначе длинный ответ переполнил бы буфер.
- **Сообщения в пачке** идут по возрастанию `seq` без пропусков.
- **Ответ** `{ack}` — последнее сообщение мода, принятое подряд.
- **Правила Co-37 без изменений:**
  - `seq ≤ ack` — `200` с тем же `ack`, повторной обработки нет;
  - пропуск, то есть первое `seq > ack + 1`, — `409 {code: "SEQ_GAP", ack}`, и мод переотправляет с `ack + 1`.
- **Частичный приём.** Адаптер берёт непрерывное начало пачки и возвращает его `ack`, остальное мод отправит снова.
- **Ошибки:**
  - `410 SESSION_UNKNOWN` — новое рукопожатие;
  - `413 {code: "TOO_LARGE"}` — пачка или сообщение больше предела.
- **Сторона мода.** Мод держит неподтверждённые сообщения до `ack` и переотправляет их при сбое. Порядок обеспечивается тем, что одновременно в полёте не больше одного `POST`.

# Конверт

```json
{ "seq": 12, "type": "tool.call", "id": "c-7f3a", "body": { } }
{ "seq": 8,  "type": "reply", "re": "m-19", "body": { } }
{ "seq": 9,  "type": "reply", "re": "m-20", "error": { "code": "TURN_IN_PROGRESS", "message": "…" } }
```

| Поле | Смысл |
|---|---|
| `seq` | целое с 1, своё у каждого направления в каждой сессии, без пропусков. У служебных строк его нет |
| `type` | тип сообщения, через точку: `chat.send`, `tool.call` |
| `id` | задаётся, когда отправитель ждёт ответа; уникален в сессии у своего отправителя |
| `re` | `id` запроса, на который это ответ |
| `body` | содержимое; при ошибке отсутствует |
| `error` | `{ code, message, details? }` — та же форма, что в [API v0](public-api-v0.md#канонические-формы) |

Правила:

- **Незнакомый `type`.** Если у сообщения есть `id` — ответ с ошибкой `UNKNOWN_TYPE`. Если нет — сообщение пропускается с записью в отладочный лог. Незнакомые поля пропускаются всегда. Поэтому новое сообщение не требует нового `protocol`.
- **Подтверждение — не выполнение.** `ack` значит «принято к обработке». Результат приходит отдельным сообщением.
- **В пределах сессии** каждое сообщение обрабатывается ровно один раз: повторы отсекаются по `seq`. **Между сессиями гарантии нет** (Co-37). Запросы, бывшие в полёте при смене сессии, потеряны, и ждущая сторона завершает их видимой ошибкой `CHANNEL_RESET`. Ход чата заканчивается ошибкой, вызов инструмента модель повторит сама.

|---|---|---|

| `chat.done` | `{ turnId, model, latencyMs }` | ход закончен; задержка — от `chat.send` до конца ответа. Строка состояния §5 берёт модель и задержку отсюда |
| `chat.failed` | `{ turnId, code, message }` | ход сорван ошибкой Foreman или провайдера |
| `chat.cancelled` | `{ turnId }` | вещание хода остановлено по `chat.cancel`; ответ ляжет в историю |
| `reply` | по запросу | ответ на запрос мода |

## Мод → адаптер

| `type` | `body` | Ответ |
|---|---|---|
| `mod.status` | `{ saveId, inert }` | нет; шлётся при изменении: загрузка сохранения, инертный режим |
| `chat.send` | `{ saveId, saveName?, text }`, с `id` | `{ turnId }`; ошибки `TURN_IN_PROGRESS`, `TURN_DRAINING`, `FOREMAN_UNAVAILABLE`, `INVALID_ARGUMENT` |
| `chat.cancel` | `{ saveId, turnId }`, с `id` | `{ state: "cancelled" \| "alreadyCancelled" }`; ошибки `NO_TURN`, `TURN_MISMATCH` |
| `chat.history` | `{ saveId, limit }`, с `id`; `limit` 1–100, по умолчанию 50 | `{ messages: [ { id, role: "user" \| "assistant", text, createdAt } ] }` — от старых к новым |
| `tool.result` | `re` — `id` вызова; `body` — каноническая форма результата из API v0 или `error` | нет |

## Ход чата

Семантика хода из #50 не меняется:

- **Один ход на сохранение.** Второй `chat.send` во время хода получает `TURN_IN_PROGRESS`.
- **`chat.cancel`** останавливает вещание: мод сразу получает `chat.cancelled`. Foreman доигрывает ход, и ответ попадает в историю. Объяснить это игроку — задача экрана чата (Co3).
- **Следующий ход ждёт**, пока отменённый допишется, до 30 с. Дольше — ошибка `TURN_DRAINING`.
- **После `chat.cancelled`** сообщений `chat.*` с этим `turnId` больше нет. Мод пропускает `chat.*` с незнакомым или отменённым `turnId`.

**Имена событий Foreman в протокол не выходят** (§3.3 п. 3: изменения API Foreman гасятся в одном месте). Соответствие:

| Foreman (SSE) или кадр #50 | Канал |
|---|---|
| `text` | `chat.text` |
| `tool_use` | `chat.tool` — только имя. Аргументы экрану не нужны и бывают большими |
| `done` | `chat.done` с моделью и задержкой от адаптера |
| `error` | `chat.failed` с кодом `FOREMAN_ERROR` |
| `work_order` | в v0.1 не передаётся: экран Work Orders — Milestone 2. Адаптер пишет его в лог |
| `accepted` (кадр #50) | `reply` на `chat.send` |
| `cancelled` (кадр #50) | `chat.cancelled` |
| `ping` (кадр #50, на каждый ход) | служебная строка `ping` потока |

# Вызов инструмента

1. **Foreman вызывает инструмент.** Модель Foreman зовёт `tools/call` адаптера. Адаптер удаляет `savePath` (§3.4) и проверяет белый список.
2. **Адаптер отправляет вызов моду.** Если сессии или потока нет, Foreman сразу получает ошибку `MOD_DISCONNECTED` с текстом для модели «игра не подключена», без ожидания. Иначе уходит `tool.call` со сроком `toolDeadlineSec`.
3. **Мод выполняет вызов** как операцию реестра, тем же `Validator`, что для любого клиента (§3.6), на последнем снимке. Действуют лимиты клиента «модель», 2 запроса в секунду (API v0). Возможные ошибки: `RATE_LIMITED`, `MOD_INERT`, `SAVE_MISMATCH` (ниже).
4. **Ответ мода.** `tool.result` превращается в результат MCP: `content: [{ type: "text", text: <каноническая форма JSON> }]`. Ошибка становится `isError: true` с текстом `{ code, message }`.
5. **Срок вышел** — адаптер отвечает `MOD_TIMEOUT`. Поздний результат отбрасывается.

**Чьё сохранение.** Адаптер ставит в `tool.call` `saveId` единственного идущего хода. Мод сверяет его с текущим сохранением; при расхождении — `SAVE_MISMATCH`. Иначе дочитываемый ход сохранения A получил бы данные сохранения B, которое игрок успел загрузить. Остальные случаи:

- **Идущих ходов нет**, например фоновый вызов Foreman — `saveId` не передаётся, мод отвечает по текущему.
- **Идущих ходов несколько**, то есть отмена, загрузка другого сохранения и новый вопрос за время дочитывания — адаптер сам отвечает `AMBIGUOUS_TURN`, не спрашивая мод. Случай редкий, ошибка видимая.

# Коды ошибок канала

Коды API v0 проходят в `tool.result` без изменений. К ним канал добавляет:

| Код | Где | Когда |
|---|---|---|
| `PROTOCOL_MISMATCH` | рукопожатие | версия протокола не поддерживается |
| `API_VERSION_MISMATCH` | рукопожатие | не совпала мажорная версия API, тот же код, что в API v0 |
| `SESSION_UNKNOWN` | `410` | адаптер перезапущен, сессия вытеснена или истекла |
| `STREAM_LOST` | `409` | запрошенный номер вытеснен из буфера |
| `SEQ_GAP` | `409` | пропуск в номерах пачки мода |
| `TOO_LARGE` | `413` | сообщение или пачка больше предела |
| `UNKNOWN_TYPE` | `reply` | незнакомый тип запроса |
| `CHANNEL_RESET` | ход, вызов | запрос потерян при смене сессии |
| `MOD_DISCONNECTED`, `MOD_TIMEOUT` | ответ адаптера Foreman | мод не подключён, мод не ответил в срок |
| `SAVE_MISMATCH` | `tool.result` | вызов адресован не текущему сохранению |
| `AMBIGUOUS_TURN` | ответ адаптера Foreman | вызов нельзя отнести к одному ходу |
| `TURN_IN_PROGRESS`, `TURN_DRAINING`, `NO_TURN`, `TURN_MISMATCH` | `reply` | правила хода из #50 |
| `FOREMAN_UNAVAILABLE`, `FOREMAN_ERROR` | `reply`, `chat.failed` | Foreman не отвечает или вернул ошибку |

Незнакомый код — общая ошибка, как в API v0.

# Связь в моде

- **`bSidecarConnected` в `GetStatus` и событии `api.status`.** Истинно, пока сессия есть и поток открыт или переоткрыт меньше `3 × pingSec` назад.
- **Переподключение.** Паузы 0,5 → 1 → 2 → 4 → 10 с со случайным разбросом, без предела числа попыток. Игра от этого не зависит: GameThread не ждёт сеть, рукопожатия не идут лавиной.
- **Сеть и потоки.** Чтение и разбор строк идут вне GameThread. Вызовы инструментов v0 читают неизменяемый снимок (`list_metrics`, `query_metric`) и в GameThread не заходят. В GameThread попадают только события для экранов.
- **Чего в API v0 пока нет.** Состояния Foreman и модели из `adapter.status`. Запросов чата (отправить, отменить, история) и событий чата для экранного модуля. Это добавления минорной версии 0.5.0, они ложатся в API вместе с мостом (S8, блок 4).

# Пределы

Стартовые значения. Действующие адаптер присылает в рукопожатии; источник чисел — README адаптера (Co-37).

| Предел | Значение |
|---|---|
| Сообщение | 1 МиБ |
| Пачка `POST /mod/send` | 64 сообщения и 1 МиБ |
| Буфер адаптера | 1024 сообщения или 8 МиБ |
| `ping` | 15 с; поток считается оборванным после 45 с тишины |
| Срок вызова инструмента | 10 с |
| Сессия без потока и без `POST` | 120 с, дальше `SESSION_UNKNOWN` |
| `chat.history` | до 100 сообщений |
| Текст `chat.send` | до 8000 знаков (#50) |

**Переполнение буфера** (мод не подтверждает) закрывает сессию. Мод получает `STREAM_LOST` или `SESSION_UNKNOWN` и делает новое рукопожатие: отказ видимый, а не тихий.

# Запасные транспорты

Рукопожатие, конверт и `POST /mod/send` у всех вариантов одни и те же.

- **Long-poll.** `GET /mod/poll?session=S&ack=N&waitSec=25` возвращает `{ messages: [ … ] }`; после ожидания список может быть пустым. Служебные строки не нужны: признак жизни — сам опрос.
- **WebSocket (IXWebSocket, MODULES E1).** Рукопожатие — первый кадр, дальше текстовые кадры с теми же объектами в обе стороны. Подтверждение — внутри канала: `{"type":"ack","ack":N}`.

Смена транспорта меняет класс транспорта в моде и точку входа в адаптере. Типы сообщений и конверт остаются прежними.

# Логи и секреты

- **Токен** не пишется в лог ни одной стороной и не ездит в URL. `session` секретом не считается: без токена она бесполезна.
- **Тексты чата, аргументы и результаты инструментов** на уровне info в лог не пишутся. Отладочный лог видит тип, `seq` и размер. Это то же правило, что у записи Recording (§8.6).

# Результаты Spike S2: сторона мода

Проверено 13.11.2026 под Proton на CL 517554. Сторона мода — `FFicsitAISidecarChannel` в `FicsitAICore/Sidecar/` (ветка `mod/s2-channel`). Адаптер — #51 на `c5afd7d`, отдельный экземпляр на петле, без Foreman и `sf-mcp`. Вызовы MCP шлёт сценарий вместо Foreman: `initialize`, затем `tools/call`, с токеном в query, как это делает Foreman. За обработчиком инструментов в моде стоит заглушка API v0 — тот же случай, что у моста S8: проверяется канал, а не данные.

**Выбор транспорта: основной вариант работает, запасной не нужен.** Модуль `HTTP` игры под Windows — это libcurl (WinHttp там только для настроек прокси). Под Wine он держит долгий `GET` и отдаёт тело кусками по мере прихода. Чтение и разбор строк идут на потоке HTTP, GameThread получает готовые сообщения из очереди. Общего тайм-аута у потока нет (`SetTimeout(0)`), тайм-аут активности — `3 × pingSec + 5` с; живость мод проверяет сам — по `ping`.

**Что не проверено:**

- **Настоящий Foreman с моделью.** Сквозной путь «вопрос в чате → `query_metric` → ответ модели с числом мода» с игрой ещё не прогонялся: у Co2 он пройден с поддельным модом, у меня — с поддельным Foreman. Нужен совместный прогон с работающим `ff-server` и ключом провайдера.
- **Чат через игру.** `chat.*` с текстом ответа без Foreman не появляются, проверен только путь запроса и ошибки.
- **Запасные транспорты** не нужны: основной работает. В адаптере их нет (#51), в моде тоже.
- **Подключение к API мода.** В продукте канал пока никто не создаёт: обработчик инструментов придёт из реестра операций вместе с `FicsitAIApi` (V-2), конфиг — из Mod Configuration SML (§10). Сейчас канал поднимает проба S2, адрес и токен — из `Saved/FicsitAI/adapter.json`.

**Найдено по адаптеру (#51).** Без `sf-mcp` `tools/list` падает целиком (`fetch failed`), и вместе с ним пропадают инструменты мода: модель не видит игру, хотя канал жив. Вызов `tools/call` при этом работает. Передано Co2.

# Отличия от Co-37

1. **Рукопожатие — отдельный `POST /mod/hello`, а не первый `GET`.** Отказ по версии становится обычным ответом JSON, а не оборванным потоком. И рукопожатие одно для всех трёх транспортов.
2. **Сессия вместо эпохи.** Эпоха ловила только перезапуск адаптера. После перезапуска игры при живом адаптере его счётчики ждали бы продолжения от мода, который начинает с 1. Сессия заводится на каждое рукопожатие и закрывает оба случая. Правило «то, что было в полёте, потеряно, ошибка видимая» не меняется.
3. **`ack` ещё и в `POST /mod/send`.** Иначе буфер освобождался бы только при переоткрытии потока, которого в нормальной работе не бывает, и длинный ответ переполнил бы буфер.
4. **Пределы приходят в рукопожатии.** Источник чисел остаётся один — README адаптера: мод их не дублирует, а получает.
