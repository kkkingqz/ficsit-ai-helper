# Как мы работаем в репозитории

Правила веток и ревью этапа 1. Что делаем — [docs/PLAN-v0.1.md](docs/PLAN-v0.1.md) и задачи
[milestone v0.1](https://github.com/kkkingqz/ficsit-ai-helper/milestone/1); с чего начинает каждый —
[docs/team/KICKOFF.md](docs/team/KICKOFF.md). Здесь — только порядок работы с репозиторием.

## Ветки

- Код попадает в `main` через PR, работа идёт в ветке.
- Имя ветки — `<область>/<тема>`: `mod/`, `web/`, `sidecar/`, `docs/`, `ci/`, `test/`, `art/`.
  Тема — короткая, латиницей, через дефис, с номером работы из плана: `sidecar/p-3-foreman-local`.
- Одна ветка — одна задача milestone; в описании PR ссылка на неё (`#10`).
- Документы и правки задач King разрешил коммитить прямо в `main`.
- Художественные ветви (`art/*`) живут долго и вливаются по готовности ассета. До слияния их код не
  считается кодом проекта, а при слиянии проходит обычное ревью Co, включая инвариант `GameFacade/` (ADR-029).

## PR и ревью

- **Каждый PR в мод — ревью Co**; для задач Gf это часть плана, а не формальность. **Код Co ревьюит Gs.**
- **Сайдкар ревьюится не весь** (решение King 09.11.2026): контрактная поверхность адаптера —
  инструменты из реестра, белый список, `apiVersion`, формат канала — проходит ревью Co, потому что
  ошибка там стоит дороже всего. Лаунчер, сборка архива и вёрстка экранов ревью не проходят: второго
  веб-программиста в команде нет. Вместо ревью — чек-лист Gf2 и тесты с fake-LLM. Это сознательное
  ограничение, а не покрытие.
- PR не должен ждать ревью больше дня.
- Работа готова по чек-листу Gf2 из тест-плана P-7, а не по ощущению. Чек-лист существует до начала работы.
- Задержка больше чем на день по задаче критического пути — сразу Co и King.
- Заимствованный код — в `third_party/<project>/` с исходной лицензией и перечнем изменений, не копипастой.
- Решения по итогам спайков пишет Co в `docs/ARCHITECTURE.md` на воротах, утверждает King. Не в переписке
  и не в задаче: источник истины один.

## Защита `main`

**Технической защиты нет — так решил King 09.11.2026.** Репозиторий приватный на бесплатном личном
плане, и GitHub отдаёт `403 Upgrade to GitHub Pro or make this repository public` и на branch protection,
и на rulesets. Пока правило держится соглашением: код — через PR, напрямую в `main` только документы
и правки задач.

Чтобы включить, нужно два условия:

1. GitHub Pro на аккаунте владельца **или** публичный репозиторий;
2. обязательные проверки из P-4 ([#5](https://github.com/kkkingqz/ficsit-ai-helper/issues/5)).

Нынешний `contracts.yml` обязательной проверкой сделать нельзя: он срабатывает только на
`docs/contracts/**`, и PR без изменений контрактов повиснет навсегда в ожидании проверки, которая
не запускалась. Обязательными делаются проверки, которые запускаются на любом PR.

## CI

Сам мод в CI на этапе 1 не собирается: движок Coffee Stain слишком велик для бесплатных раннеров
GitHub, сборку для альфы делает Gf локально. В CI идут контракты, адаптер, `core/` на Windows и Linux,
инварианты и автотесты веб-экранов на Fixture.
