# Чек-лист спайка S8: Веб-экраны через BLUI (P-7, #32)

## 1. Паспорт спайка и контекст

- **Цель:** Проверить, можно ли писать экранные модули на вебе (HTML/CSS/JS) и отображать их встроенным браузером на Chromium (CEF) через плагин BLUI (форк getnamo, MIT) в отдельном моде-библиотеке `FicsitAIWebRuntime` под SML 3.12 в готовой игре.
- **Главный результат:** Объективные измеримые данные для принятия решения на **воротах W** (конец недели 3) — принять или отклонить **ADR-032**. При отклонении спайка активируется штатный fallback — реализация экранов на UMG.
- **Ведущий спайка:** Co.
- **Распределение задач спайка (PLAN-v0.1.md §5.2):**
  - **Co:** модули `WebSockets` и `HTTP` в SML; плагин `FicsitAIWebRuntime` (BLUI v5.1.0, CEF 128); загрузка в готовой игре и зависимость мода; локальная схема `local://`; блокировка внешней навигации; рендер в UMG-окно по E.
  - **Co, Co2:** двусторонний мост `blu_event` ↔ stub API ↔ `ExecuteJavaScript`, замер задержки круга.
  - **Gf:** рендеринг страницы в текстуру Render Target меша терминала (пропорция 16:9, ADR-030).
  - **Gs2:** тестовая страница с библиотекой графиков в стилистике дизайн-системы D-2.
  - **Gf2:** чек-лист готовности, протокол замеров кадрового времени под Proton, отчёт для ворот W.
  - **Пилотный тестер (внешний):** резервная проверка Windows-сборки на чистой Windows (только если под Proton возникнет специфичный сбой Wine).

## 2. Чек-лист спайка S8

### Блок 1. Сборка, упаковка и дистрибуция (`FicsitAIWebRuntime`)

Отвечает: **Co**

- [ ] **1.1. Базовые модули платформы:** Модули `WebSockets` и `HTTP` успешно подключаются и инициализируются в готовой сборке игры под SML 3.12 (проверка первым днём недели 2; результат передаётся в S2).
- [ ] **1.2. Сборка плагина:** Плагин BLUI (форк getnamo v5.1.0, CEF 128) успешно собирается под целевую платформу Win64 через MSVC 17.8 под wine через Alpakit.
- [ ] **1.3. Состав бинарников CEF:** Все необходимые библиотеки и ресурсы CEF объявлены в `FicsitAIWebRuntime.Build.cs` через `RuntimeDependencies` и попадают в каталог плагина:
  - `blucef.dll` (переименованный бинарник CEF 128, не конфликтующий с движком);
  - `chrome_elf.dll`, `d3dcompiler_47.dll`, `libEGL.dll`, `libGLESv2.dll`, `vk_swiftshader.dll`, `vulkan-1.dll`;
  - `icudtl.dat`, `v8_context_snapshot.bin`;
  - каталоги `locales/` и `resources.pak`.
- [ ] **1.4. Мод-библиотека:** `FicsitAIWebRuntime` упакован как самостоятельный плагин-мод Satisfactory с корректным манифестом `data.json`.
- [ ] **1.5. Межмодовая зависимость:** Основной мод `FicsitAI` объявляет `FicsitAIWebRuntime` в списке `Dependencies` в своём `data.json`.
- [ ] **1.6. Установка через менеджер модов:** Satisfactory Mod Manager (SMM) корректно определяет зависимость и устанавливает библиотеку вместе с основным модом.
- [ ] **1.7. Бесконфликтная загрузка:** При старте готовой игры под SML оба мода загружаются в адресное пространство процесса без падений, коллизий имён и сбоев линковки.

### Блок 2. Локальная изоляция, автономность и безопасность (FR-10, ADR-032)

Отвечает: **Co**

- [ ] **2.1. Локальная файловая схема:** Страницы мода загружаются исключительно из локального каталога файлов мода через схему `local://` (или кастомную схему BLUI).
- [ ] **2.2. Блокировка внешних переходов:** Попытки перехода по внешним сетевым протоколам (`http://`, `https://`, `ftp://` и др.) перехватываются и безусловно блокируются в `CefRequestHandler::OnBeforeBrowse`.
- [ ] **2.3. Запрет удалённых ресурсов:** Загрузка внешних скриптов, стилей, изображений или веб-шрифтов (CDN, внешние хосты) блокируется в `CefRequestHandler::OnBeforeResourceLoad`. Страница полностью автономна.
- [ ] **2.4. Автономность без сайдкара (FR-10):** При полностью остановленном или незапущенном процессе сайдкара веб-экраны открываются штатно, статика загружается без сетевых таймаутов, UI отображает корректное состояние «не подключено».

### Блок 3. Интерактивность, фокус ввода и рендеринг

Отвечают: **Co, Gf**

- [ ] **3.1. Открытие в UMG (Co):** По нажатию клавиши взаимодействия (E) создаётся/показывается UMG-виджет терминала, содержащий активный viewport встроенного браузера BLUI.
- [ ] **3.2. Перехват фокуса ввода (Co):** При открытии экрана фокус ввода клавиатуры и мыши передаётся в веб-контейнер (`SetInputMode UIOnly` / `GameAndUI`); координаты курсора мыши точно соответствуют элементам DOM.
- [ ] **3.3. Освобождение фокуса (Co):** При закрытии экрана по Escape или E фокус ввода корректно возвращается игроку (`SetInputMode GameOnly`), управление персонажем восстанавливается без залипания клавиш.
- [ ] **3.4. Рендеринг в текстуру меша (Gf):** Страница рендерится в offscreen-текстуру (Render Target) материала экрана терминала в соотношении сторон **16:9** (ADR-030).
- [ ] **3.5. Оптимизация перерисовки (Co, Gf):** Обновление текстуры происходит только по событию фактического изменения содержимого страницы (`OnPaint` / dirty rects), без холостого копирования буфера каждый графический кадр при статичном изображении.

### Блок 4. Двусторонний мост JS ↔ UE и задержка круга

Отвечают: **Co, Co2**

- [ ] **4.1. Вызов из JS в UE:** Страница генерирует событие моста (через `blu_event` или биндинг `FicsitAIApi`), которое перехватывается и обрабатывается в C++ обработчике мода.
- [ ] **4.2. Ответ из UE в JS:** C++ обработчик передаёт данные обратно на страницу через вызов JavaScript (`ExecuteJavaScript` / callback-функцию промиса).
- [ ] **4.3. Соответствие контракту:** Формат тестовых вызовов моста соответствует замороженным структурам [docs/interfaces/public-api-v0.md](../../docs/interfaces/public-api-v0.md).
- [ ] **4.4. Замер задержки круга (Roundtrip Latency):**
  - Схема замера: метка времени $t_0$ в JS перед отправкой → `blu_event` → обработчик в моде (возврат заглушки) → `ExecuteJavaScript` → метка времени $t_1$ в JS при получении.
  - **Критерий:** среднее время круга $t_{roundtrip} \le 16$ мс (не более одного кадра при 60 FPS), 99-й перцентиль $\le 33$ мс.

### Блок 5. Протокол замеров кадрового времени и нагрузки

Отвечают: **Gf2, Gs2**

#### 5.1. Параметры тестовой страницы нагрузки (поставка Gs2 к середине недели 2)
- **Разрешение вьюпорта:** базовое 1280×720 (масштабируется до 1920×1080).
- **Состав элементов на странице:**
  - 2–4 графика временных рядов (энергосеть: производство и потребление; баланс ресурсов: вход и выход);
  - 8–12 информационных плиток метрик с числовыми значениями и статусами;
  - таблица со списком активных генераторов/производств (10–20 строк).
- **Объём данных временных рядов:**
  - Стандартный режим: 60 точек на ряд (окно 1 минута с шагом 1 с);
  - Стресс-режим: 300–600 точек на ряд (эмуляция окна 5–10 минут).
- **Частота обновления данных:**
  - **1 раз в секунду (1 Гц)** — штатный интервал обновления телеметрии v0.1 (`metrics.snapshot`, §8.2).

#### 5.2. Сценарий тестового прогона (стенд замеров)
- Тестирование проводится на тестовом сохранении фабрики среднего масштаба (1–2 тыс. построек, P-5).
- Замеряются 3 конфигурации нагрузки:
  1. **Конфигурация A (Baseline):** Игра без открытых терминалов и экранов.
  2. **Конфигурация B (Single Interactive):** Открыт 1 полноэкранный интерактивный терминал (UMG 1280×720 / 1920×1080).
  3. **Конфигурация C (Triple Browser Stress):** 1 открытый интерактивный терминал + 2 размещённых терминала в мире с активным рендерингом страниц в текстуру меша в поле зрения игрока (всего **3 активных браузера 1280×720**, §5.2 PLAN-v0.1.md).

#### 5.3. Измеряемые метрики и допустимые бюджеты

| Метрика | Способ замера | Критерий готовности | Недопустимое отклонение |
|---|---|---|---|
| **GameThread Frame Time** | Консоль UE: `stat Unit`, `stat Game` | Прирост $\Delta \le 1.5$ мс (конфиг B), $\Delta \le 3.5$ мс (конфиг C) | $\Delta > 5.0$ мс на GameThread |
| **RenderThread Frame Time** | Консоль UE: `stat Unit`, `stat GPU` | Прирост $\Delta \le 2.0$ мс (конфиг B), $\Delta \le 4.0$ мс (конфиг C) | $\Delta > 6.0$ мс на RenderThread |
| **FPS Drop** | Встроенный FPS-счётчик / MangoHud | Просадка FPS $\le 10\ \%$ от базового уровня | Просадка FPS $> 20\ \%$ |
| **Потребление RAM (RSS)** | Системный монитор / `ps`, `top` | Прирост RAM $\le 150$ МБ на 1 инстанс CEF | Прирост RAM $> 250$ МБ на инстанс |
| **Стабильность памяти** | Прогон 30 мин при обновлении 1 Гц | Отсутствие линейной утечки (рост $\le 15$ МБ за 30 мин) | Непрерывный рост RAM (утечка) |
| **Процессы ОС** | `pgrep -c blucef` / `pstree` | Число процессов соответствует числу вкладок/контекстов; корректное завершение при закрытии | Зависание зомби-процессов CEF |

### Блок 6. Среда выполнения Proton и правила эскалации (ADR-033)

Отвечает: **Gf2**

- [ ] **6.1. Запуск под Proton как основной платформой:**
  - Игра с модом и CEF запускается под Proton (Wine) на машине разработки Linux.
  - Дочерние процессы `blucef` стартуют под Wine без фатальных ошибок песочницы (sandbox/GPU flags).
  - Offscreen-текстуры корректно передаются в графический стек Vulkan/DXVK без графических артефактов, мерцания или чёрного экрана.
- [ ] **6.2. Резервная ветка эскалации на Windows (при сбое под Proton):**
  - **Правило ADR-033 / §6.3.1:** Если под Proton выявляется критическая несовместимость CEF с Wine, спайк S8 **НЕ бракуется автоматически**.
  - Сборка мода передаётся **внешнему пилотному тестеру на чистой Windows**.
  - Пилотный тестер проходит проверку по Блокам 1–5 на Windows-машине.
  - Решение об отклонении ADR-032 принимается только в том случае, если сбой подтвердился и на нативной Windows. Если на Windows всё работает — King принимает решение об условном принятии ADR-032 с фиксацией ограничения Wine в известных рисках.
- [ ] **6.3. Инвариант команды:** Команда не ищет Windows-машину у себя и не ищет специальное устройство под Proton (ADR-033: основная платформа команды — Linux под Proton).

## 3. Критерии готовности к воротам W (Gate W Checklist)

Спайк S8 считается завершённым, когда получены факты для заполнения матрицы решений ворот W:

| Условие | Вердикт по ADR-032 | Дальнейшие шаги |
|---|---|---|
| Блоки 1–4 закрыты, замеры Блока 5 укладываются в бюджет, запуск под Proton успешен | **ПРИНЯТЬ ADR-032** (Веб-экраны) | Экраны v0.1 и Screen Lab реализуются на вебе (HTML/CSS/JS) внутри UMG-каркаса. S6 строится на обычном браузере. |
| Сбой под Proton, но пилотный тестер на Windows подтвердил Блоки 1–5 в бюджете | **РЕШЕНИЕ KING** (ADR-032 с оговоркой) | King решает: принять для целевой платформы игроков (Windows) с багом под Proton в бэклоге, либо откат на UMG. |
