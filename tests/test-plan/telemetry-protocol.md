# Протокол замеров телеметрии и бюджета GameThread (S3, V-09)

Настоящий протокол регламентирует методику инструментального замера производительности подсистемы телеметрии мода FICSIT AI, проверку бюджета GameThread и определение порогов актуальности данных для UI.

---

## 1. Целевые бюджеты производительности (ARCHITECTURE.md §11)

| Параметр | Целевой бюджет | Допустимый пик | Недопустимая деградация |
|---|---|---|---|
| **GameThread Time (Телеметрия)** | $\le 1.0$ мс/кадр | $\le 2.0$ мс/кадр | $> 3.5$ мс/кадр |
| **RenderThread Time (UI / Рендер)** | $\le 1.5$ мс/кадр | $\le 2.5$ мс/кадр | $> 4.0$ мс/кадр |
| **Частота тика телеметрии** | 1 Гц (1 раз в секунду) | 1 Гц | $> 2$ с между тиками |
| **Дроп FPS (по сравнению с чистой игрой)** | $\le 5\ \%$ | $\le 10\ \%$ | $> 15\ \%$ |
| **Микрофризы кадра (Frame Stutter)** | 0 событий $> 20$ мс | 0 событий | Появление заиканий при сборе |

## 2. Тестовый стенд и сохранения (P-5)

Замеры проводятся на аппаратно фиксированном стенде команды под управлением Linux / Proton на 4 типовых сохранениях:

1. **Save A (Ранняя база):** Стартовая база, до 500 построек, 1 локальная энергосеть на биомассе/угле.
2. **Save B (Средняя фабрика):** 1 000 – 2 000 построек, угольная/топливная энергосеть, батареи, базовая логистика.
3. **Save C (Мегабаза):** 5 000+ построек, разветвлённая глобальная энергосеть, ядерная энергетика, максимальная нагрузка на индекс построек.
4. **Save D (Модовое сохранение):** База с активным модом на альтернативные рецепты для проверки стабильности `CatalogProvider`.

## 3. Методика проведения замеров

### 3.1. Инструменты профилирования
- **Unreal Insights:** Трассировка `Timing Insights` с включёнными каналами `cpu,frame,bookmark`.
- **Консольные команды UE:**
  - `stat Unit` — общее кадровое время, GameThread, RenderThread, GPU.
  - `stat Game` — детальная разбивка тика игрового потока.
  - `stat FicsitAI` — кастомная группа статистики подсистемы мода.
- **Внешний профилировщик:** MangoHud (отслеживание 1% и 0.1% low FPS, фреймтайм-график).

### 3.2. Сценарий прогона
1. Загрузка сохранения и стабилизация мира в течение 60 секунд (прогрев кэшей, выход на стабильный FPS).
2. Запись базового кадрового времени в течение 120 секунд без активных модулей мода ($T_{base}$).
3. Активация сборщиков телеметрии (`TelemetrySampler`) с интервалом тика 1 Гц.
4. Запись кадрового времени в течение 300 секунд при непрерывном сборе телеметрии ($T_{telemetry}$).
5. Расчёт показателей:
   $$\Delta T = T_{telemetry} - T_{base}$$
   $$\text{Spike Rate} = \frac{N_{\text{frames} > 25\text{ms}}}{N_{\text{total}}}$$

### 3.3. Проверка нарезки по кадрам (Time-slicing)
Сбор телеметрии на фабриках Save B и Save C не должен выполняться синхронно за один тик:
- Перебор массива построек индекса распределяется на $K$ последовательных кадров ($K = 10\dots30$).
- За один кадр опрашивается не более фиксированного числа машин ($N_{batch} = 100\dots200$).
- Проверяется отсутствие «зубьев пилы» на графике фреймтайма с периодом в 1 секунду.

### 3.4. Замеры стоимости мутаций и локального обхода связей (решения King 11.11.2026, Co-45)
В рамках того же прогона на Save B выполняются два дополнительных микрозамера:
1. **Запись состояния на машину (`SetCustomData`):** Измерение накладных расходов записи пользовательских данных/тегов на актор постройки в GameThread. Бюджет: $\le 0.05$ мс на операцию.
2. **Локальный обход связей от одной машины:** Измерение стоимости графового обхода конвейерных и трубопроводных соединений (BFS/DFS на глубину до 15 звеньев) для выявления кандидатов производственных линий. Бюджет: $\le 0.5$ мс на один вызов обхода в GameThread.

## 4. Определение «Стабильности энергосети» (S3, V-02)

В рамках задачи S3 зафиксировано формальное измеримое состояние стабильности энергосети (согласовано с Gs по каталогу `metrics-v0.1.md` и вопросу Gs-12):

### Показатели и формулы расчёта
Стабильность вычисляется на основе метрик одного снимка телеметрии:
- $P_{\text{capacity}}$ — доступная мощность генераторов (`UFGPowerCircuit::GetPowerProductionCapacity`, МВт).
- $P_{\text{consumption}}$ — текущее фактическое потребление сети (`Consumed`, МВт).
- $P_{\text{consumption\_max}}$ — максимальная потенциальная нагрузка при включении всех машин (`UFGPowerCircuit::GetMaximumPowerConsumption`, МВт).
- $P_{\text{battery\_out}}$ — текущая мощность отдачи батарей (`UFGPowerCircuit::GetBatterySumPowerOutput`, МВт).
- $E_{\text{battery}}$ — текущий запас энергии в батареях сети (МВт·ч).

Коэффициент покрытия максимальной потенциальной нагрузки:
$$\text{CapacityRatio} = \frac{P_{\text{capacity}}}{P_{\text{consumption\_max}}}$$

Оценка времени до полного исчерпания батарей ($T_{\text{drain}}$, секунды):
- **Первичный источник:** штатный метод движка/SML `UFGPowerCircuit::GetTimeToBatteriesEmpty()` (возвращает `float` в секундах).
- **Расчётная формула проверки (размерность):**
  $$T_{\text{drain}} = 3600 \times \frac{E_{\text{battery}}}{P_{\text{battery\_out}}}\quad\text{(секунд)}$$
  *(где множитель $3600$ переводит отношение $\text{МВт}\cdot\text{ч} / \text{МВт}$ из часов в секунды; например, при $E = 5\ \text{МВт}\cdot\text{ч}$ и отдаче $P = 100\ \text{МВт}$ получаем $3600 \times 5 / 100 = 180$ с).*

### Приоритетный порядок классификации статусов энергосети:
Состояние определяется первым подошедшим условием из списка (сверху вниз):

1. **TRIPPED (Авария / Предохранитель, красный):**
   - Сработал предохранитель сети (`bCircuitBreakerTripped == true` / `IsFuseTriggered`). Сеть обесточена.
2. **CRITICAL (Критический разряд батарей, оранжевый):**
   - Батареи отдают мощность ($P_{\text{battery\_out}} > 0$) и время до разряда $T_{\text{drain}} < 300$ с (до отключения фабрики менее 5 минут).
3. **BATTERY_DRAIN (Штатный разряд батарей, жёлтый):**
   - Батареи отдают мощность ($P_{\text{battery\_out}} > 0$), но запас энергии превышает 5 минут ($T_{\text{drain}} \ge 300$ с, либо оценка времени формируется).
4. **STABLE (Стабильно с запасом, зелёный):**
   - Батареи не разряжаются ($P_{\text{battery\_out}} \le 0$) и доступная мощность генераторов покрывает максимальную потенциальную нагрузку:
     $$P_{\text{capacity}} \ge P_{\text{consumption\_max}}$$
5. **OPTIMAL (Оптимально / Условно стабильно, синий):**
   - Батареи не разряжаются ($P_{\text{battery\_out}} \le 0$), генерация покрывает текущую нагрузку ($P_{\text{capacity}} \ge P_{\text{consumption}}$), но ниже максимальной потенциальной нагрузки ($P_{\text{capacity}} < P_{\text{consumption\_max}}$). При одновременном запуске всех потребителей возможен дефицит, требуются батареи или расширение генерации.

## 5. Порог устаревания данных (Метка STALE для UI)

В ответ на вопрос Co3 о метке `STALE` на экране «Статистика»:

1. **Штатный режим (LIVE, зелёный индикатор):**
   - Возраст данных $t_{\text{age}} \le 2.0$ с при штатном тике 1 Гц.
   - Значения отображаются нормальной яркостью.
2. **Устаревшие данные (STALE, жёлтый индикатор):**
   - $2.0\text{ с} < t_{\text{age}} \le 10.0\text{ с}$.
   - Возникает при временном подвисании адаптера или фоновом сохранении игры.
   - Текст значений приглушается на 40% яркости, рядом выводится метка `STALE (Xs назад)`.
3. **Нет связи (OFFLINE, серый/красный статус):**
   - $t_{\text{age}} > 10.0\text{ с}$.
   - Сборщик телеметрии сообщает об обрыве связи; графики останавливают сдвиг времени, виджет показывает плашку «Нет свежих данных телеметрии».
